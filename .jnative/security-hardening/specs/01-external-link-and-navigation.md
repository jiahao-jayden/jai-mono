# 01: 外链与导航边界

要先完成:无 · 状态:⬜

## 交付什么

Agent 在回复里给出的链接，点击后只可能打开 `http:`、`https:` 或 `mailto:`。其他任何协议（`file:`、`vscode:`、本机注册过的自定义 scheme）点了没有反应，不会交给操作系统。主窗口也不会被导航到应用自身以外的地址。

这一项做完，评审里最严重的那条链就断了。

## 范围

做:

- 渲染层收协议。给 transcript 的 markdown 渲染显式提供 URL 变换，把白名单外的 href 变成不可点击。Streamdown 2.5.0 的默认 URL 处理是恒等函数，而且只有传了特定 prop 才会运行，所以必须显式传。
- 主进程收协议。新窗口打开请求在交给 `shell.openExternal` 之前先判协议，白名单外直接丢弃并记一条日志。
- 拦截顶层导航。注册 `will-navigate`，只放行应用自身的地址，其余阻止。
- 补测试，覆盖白名单内外的协议各至少一个，以及顶层导航被拦截。

不做:

- CSP 和远程字体（第 02 项）。
- `shell.openExternal` 在 OAuth 流程里的调用。那条路径的 URL 来自 Runtime Host 而非 agent 输出，已有协议校验，本项不碰。
- `jai:` 深链回调。它走 `open-url` 事件，不经过新窗口处理，不受影响。确认这一点即可，不要顺手改。

## 需要遵守的整体选择

- 协议白名单为 `http:`、`https:`、`mailto:`，见 plan.md 的「已确认的关键选择」第 3 条和「外部产品或规范的约定」。
- Electron 安全清单按「行为参考」落地，只做限制导航和限制新窗口两条，不逐条对齐整份清单。

## 必须遵守的项目规则

> - `app/desktop/electron/main.ts`、`preload.ts`、`runtime.ts` 是 Electron 入口与 composition root；`logger.ts`、`theme.ts`、`windows.ts` 是进程级系统能力。不要把新的产品领域文件继续平铺在 `electron/` 根目录。

窗口导航与外链属于进程级系统能力，留在 `windows.ts`，不新建目录。

> 7. 修改 Desktop UI 后，至少检查 Shell 中是否新增了无合理例外的原生 `<button>` 或直接图标库引用，并运行 TypeScript 检查与相关测试。

> - 不要仅为了"看起来模块化"提取两三行命名函数。

协议判断有两个调用点（渲染层和主进程），且是安全边界，抽成共享判定函数是合理的；但不要为「构造白名单数组」这种一行的事再包一层。

> 2. 选能满足当前需求的最简单实现。不要预防性抽象，不要多此一举的配置层。

白名单写死，不做成可配置项。

## 风险

- 协议白名单可能收掉正常功能。收紧前确认 UI 里没有依赖非白名单链接的既有功能。已知 `jai:` 用于 OAuth 深链，但它由 `open-url` 处理，不经过新窗口路径。
