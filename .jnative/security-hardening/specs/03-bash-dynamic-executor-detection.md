# 03: Bash 动态执行器识别

要先完成:无 · 状态:⬜

## 交付什么

`eval 'rm -rf /'`、`node -e "..."`、`base64 -d payload | sh` 这类通过动态求值绕开静态分类的命令，会被判为危险操作。它们不再能在 `bypassPermissions` 模式或已有 allow 规则下静默执行，删除根目录和 home 的固定熔断也能识别到藏在 `eval` 里的 `rm`。

## 范围

做:

- 给危险命令判定补上 `eval`、`source`、`.` 这三个动态执行器。它们目前完全不在被检查的可执行文件列表里。
- 给解释器的参数检查补上 `-e` / `-E`。现在只查 `-c`、`$()` 和反引号，所以 `node -e`、`perl -e`、`ruby -e` 全部漏掉。
- 判断 `sh script.sh` 这类「解释器执行脚本文件」要不要一并纳入，把结论写进「决策记录」。它和 `-c` 的区别在于脚本内容不在命令行里，静态分析看不到。
- 复查 root/home 熔断在补完之后能否识别 `eval 'rm -rf /'`。如果 tokenizer 仍然只看到 `eval` 这一个可执行文件名，熔断需要一起改。
- 补测试矩阵。现有测试覆盖了 `&&`、管道、引号操作符、`$()`、重定向、`/bin/rm` basename、`find -exec`，唯独没有动态执行器这一类。

不做:

- 改扫描架构。tree-sitter 解析加规则分类的结构是对的，本项只补规则。
- 追求完备。静态分析挡不住所有动态求值，目标是把常见形式从「静默放行」拉回「需要审批」，不是证明无法绕过。这个边界要在实现时保持清醒，不要为了多挡一种写法把规则复杂化到难以维护。
- Bash 只读命令白名单的路径检查。它是已声明的边界，见 intent.md。

- 这是唯一改动权限判定语义的工作。补规则不改架构，见 plan.md 的「方案」第二条线。

## 长期保存的数据与维护方

无。判定规则本身不持久化。

需要注意一个间接影响：Bash 的「总是允许」会写进项目的 `.jai/settings.local.json`。规则收紧后，用户此前为某个解释器保存过的 allow 规则仍然存在且仍会匹配。这不是本项要清理的东西，但要在实现时确认收紧后的判定顺序是「危险判定优先于配置规则」，而不是反过来。

## 必须遵守的项目规则

> - 不要仅为了"看起来模块化"提取两三行命名函数。

危险判定属于领域校验，拆成小的具名判定函数是允许的。

规则写死，不做成可配置的危险命令表。

## 风险

- 收紧后可能让原本顺畅的日常操作开始弹审批。补规则时确认没有把 `source` 在常见开发场景（例如激活虚拟环境）里的使用一并变成高摩擦。如果确实变高摩擦，把权衡写进「决策记录」，不要偷偷放宽。
