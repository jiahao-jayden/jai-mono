# 04: Attachment 路径来源约束

要先完成:无 · 状态:⬜

## 交付什么

主进程只把用户确实通过文件选择器选过的文件当作附件。renderer 声称的任意绝对路径不再被接受，`~/.ssh/id_rsa` 这类路径即使被提交也拿不到内容。

## 范围

做:

- 让 attachment 注册只接受来源可追溯的路径。目前主进程收到路径后只做「是不是文件」和「大小对不对」两项检查，没有任何来源约束；正常 UI 从 `webUtils.getPathForFile` 取路径，但主进程没有强制这一点。
- 选一个能表达「这个路径确实来自用户选择」的机制。候选是主进程维护一个本次会话内用户选过的路径集合，或者改成由主进程发起文件选择并直接返回句柄。哪种更贴合现有 RPC 形态，实现时定，把理由写进「决策记录」。
- 把注册流程里的两处裸 `throw new Error(...)` 换成 `TaggedError`。它们目前会被外层 catch 包成 `TaggedError`，行为上没错，但违反项目错误处理规则。
- 补测试，覆盖「未经选择的路径被拒绝」和「正常选择流程仍然可用」。

不做:

- 附件内容本身的校验（类型、大小上限）。既有行为不变。
- IPC 层的通用 sender/frame origin 校验。那是更大的改动，本项只解决路径来源。

## 长期保存的数据与维护方

无。附件注册表是 RPC 生命周期内的内存状态，不持久化。

## 必须遵守的项目规则

> - 领域错误使用 `TaggedError`，`_tag` 采用 `<subsystem>.<reason>`；不要新建裸 `Error` / `TypeError` 作为业务错误。
> - `cause` 仅用于进程内诊断。`TaggedError.toJSON()` 不可跨进程直接使用；RPC、事件和 UI 边界必须通过显式白名单 DTO 投影，禁止传递 stack、cause 或未筛选的 SDK 错误对象。

拒绝路径时给 renderer 的错误消息不能回显被拒绝的路径本身，避免把主进程的文件系统探测能力变成一个探针。

> - `rpc/` 持有 IPC router、验证、错误 DTO、renderer 事件广播与 RPC 生命周期内的 attachment registry。

来源集合归 `rpc/`，不要另起目录。

> - `*Registry` 只索引运行中对象，不持久化领域事实。

## 风险

- 改动会碰到用户发送附件这条主流程。拖拽、粘贴、点击选择三种入口都要验证，漏掉一种就是可感知的功能回归。
