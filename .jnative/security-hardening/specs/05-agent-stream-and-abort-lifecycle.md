# 05: Agent 流与中断的生命周期

要先完成:无 · 状态:⬜

## 交付什么

用户点「停止」之后，即使某个扩展工具不理会中断信号，运行也会在 5 秒内收尾。SDK 消费者遍历事件流时，失败会在迭代处抛出而不是变成没人处理的 rejection；提前退出遍历也能真正取消上游。

## 范围

做:

- 给工具执行加 abort 后的宽限超时，5 秒。超时后放弃等待，把该次工具调用标记为 aborted，让运行继续收尾。核心循环目前直接等待工具返回，没有 race 也没有超时；内置工具都正确处理了中断信号，风险在 MCP 和 Agent Plugin 这些第三方工具。
- 让 `EventStream` 的失败在迭代时抛出，同时实现 iterator 的 `return()`，使消费者提前 break 能取消上游。现在失败只 reject 一个独立的 result Promise，只遍历不调 `result()` 的消费者会得到未处理的 rejection。
- 补测试。`packages/ai` 目前没有任何中断相关测试，`packages/agent` 也没有「工具忽略中断信号」的场景。

不做:

- 给工具执行加常规超时（非 abort 场景）。现有 bash 工具自带超时，其他工具的常规超时是另一个话题。
- 改动内置工具的中断处理。它们已经正确，bash 的进程组清理尤其完整。
- 并行工具执行的语义。`Promise.all` 等待全部完成这一点不变，宽限超时是加在等待之上的上限。

## 需要遵守的整体选择

- 宽限超时 5 秒，理由是内置工具最慢的清理路径（bash 的 SIGTERM 到 SIGKILL）共 1 秒，留 5 倍余量。见 plan.md「已确认的关键选择」第 5 条。
- `EventStream` 的行为改变按项目规则「不保留向后兼容」直接改，不加开关。见「已确认的关键选择」第 4 条。

## 长期保存的数据与维护方

无直接改动。但要留意：超时后被标记为 aborted 的工具调用，其结果会不会进入会话 journal，取决于现有的收尾路径。实现时确认一次，不要产生「同一次工具调用先写 aborted、真实结果晚到又写一次」的重复记录。

## 必须遵守的项目规则

> 1. 不保留向后兼容。过时的直接删，别加兼容层、别写migration、别留fallback。

> - 可恢复、调用方可处理的失败使用 `better-result` 的 `Result<T, E>`；跨多个步骤优先使用 `Result.gen` / `Result.await`。
> - `Panic` 与原生异常只表示 invariant、程序缺陷或未知基础设施故障，不能伪装成 `Err`。

超时不是程序缺陷，是可预期的失败，按可恢复失败处理。

> - `core` 不依赖 `runtime`、adapter、host 或 UI。

宽限超时加在核心循环里，不能因此引入对 harness 或 adapter 的依赖。

> 2. 选能满足当前需求的最简单实现。不要预防性抽象，不要多此一举的配置层。

超时时长写死，不做成配置项。

## 风险

- 超时后运行收尾但工具进程可能还在跑。要确认不会产生重复的工具结果，也不会让监听者收到已结束运行的事件。
- `EventStream` 改动影响公开 SDK 的对外接口面。改完要跑 `packages/coding-agent` 的 `test:consumer`；该脚本曾因 workspace 协议环境限制不可用（见 `.jnative/archive/sweep-thin-wrappers` 第 03 项的记录），跑不起来时改为核对 dist 类型面并在「决策记录」里注明。
