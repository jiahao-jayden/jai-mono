# 07: MCP 工具副作用声明

要先完成:无 · 状态:⬜

## 交付什么

远程 MCP server 提供的工具，按它自己声明的 annotation 判定副作用；读不到 annotation 时按有破坏性处理，需要用户审批。一个会写文件或调外部接口的 MCP 工具，不会因为被统一标成只读而绕过审批。

## 范围

做:

- 让官方 MCP 扩展在投影工具时读取 MCP 协议的 tool annotation，据此决定副作用等级。现在所有动态 MCP 工具一律标成只读，而只读加无敏感标记会直接放行。
- 读不到 annotation 时按破坏性 + 敏感处理。Agent Plugin 那条路径已经是这么做的，两边保持一致。
- 补单元测试，覆盖有 annotation、无 annotation、annotation 声明只读三种情况。

不做:

- 打通官方 MCP 扩展的配置来源。Desktop 的 runtime adapter 目前只为 connector 扩展提供配置，官方 MCP 扩展拿到空配置，这条路没接通。接通它是另一个需求。
- 改动 Agent Plugin 的 MCP 路径。它的声明已经正确。
- 远程 MCP 内容的其他治理（工具名冲突、描述注入）。不在本轮。

## 必须遵守的项目规则

> - 依赖方向固定：`core` 不依赖 `runtime`、adapter、host 或 UI；`runtime` 可以依赖 `core` 和自己的 contract；adapter 依赖 contract 但不携带宿主业务规则。

MCP 扩展是 adapter，副作用判定规则要贴着 MCP 协议本身，不要把宿主的产品策略写进来。

> - 不要仅为了"看起来模块化"提取两三行命名函数。
> - 不按行数机械内联。类型守卫、事件处理器、递归、协议边界、错误 DTO 投影、领域校验及多处复用函数可以保持短小。

annotation 到副作用等级的映射是协议边界，抽成具名函数合理。

## 风险

- MCP 协议的 annotation 字段是可选的，而且不同 server 的填写质量参差。保守默认（读不到就当破坏性）会让部分只读工具也弹审批。这是有意的取舍，不要为了减少审批而反过来默认放行。
