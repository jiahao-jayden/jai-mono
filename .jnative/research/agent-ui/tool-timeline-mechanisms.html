Agent 工作过程时间线的实现机制

好看的工作过程不是模型假装写日志，而是界面把实际发生的文字、工具和子代理按顺序排进同一条可展开的任务流。

核验日期：2026-09-10。源码固定到文中 SHA；在线文档以当天访问内容为准。证据笔记：Markdown。

结论

  1. 一轮用户请求里发生的每一件事，都应是一条可更新的记录。

    前提：宿主能获得 started、delta、completed 等事件。

  2. 工具的开始、参数完成和结果是不同事件，必须用调用 ID 连接。

    前提：不能只用工具名字，因为同名调用可以并发。

  3. 只有模型真的说了话，才显示模型的中间说明。

    限制：文本在协议中通常没有“中间”或“最终”的专用标签。

  4. 子代理在主列表里是一条短任务，明细放到展开区或侧栏。

    前提：必须有父调用 ID，不能靠标题猜嵌套。

  5. 历史记录可恢复；正在转的状态不可恢复。

    spinner、计时器和订阅只属于当前进程。

  6. “用时”应由本机量出来，而不是猜成供应商的工具耗时。

    Response 时间戳只覆盖整条 response。

事件驱动，而不是事后排版

界面像施工看板：工人开工、进展和验收各有一笔，而不是等工程结束后凭照片猜发生顺序。

类比的边界：模型流会并发、重试和中断，不能把屏幕上的相邻两行当作因果关系；要靠稳定 ID 和顺序字段。

证据与原文

Codex App Server（访问于 2026-09-10）定义了可流式工作过程的层级：

- Thread: A conversation between a user and the Codex agent. Threads contain turns.
- Turn: A single user request and the agent work that follows. Turns contain items and stream incremental updates.
- Item: A unit of input or output (user message, agent message, command runs, file change, tool call, and more).

工具、文本与子代理的结构边界

工具和文字都有自己的身份证；子代理还带着“我是谁派来的”这张关系卡，UI 不需要靠猜。

所以主时间线应为 subagent 保留一行，点击后再显示下级活动；没有 parent ID 时只能平铺，不能伪造树。

可重放事实与易失状态

会话历史像收据，重开后还能读；加载动画像服务员手势，窗口一关就应消失。

工具耗时需在实际执行器前后记录单调时间；provider 的 response 时间只能用于粗略的整轮耗时。

术语表

turn
用户发出一次请求后，agent 为完成这次请求所做的整段工作。
item
这段工作中的一件可单独显示和更新的事，例如一段文字或一次工具调用。
父调用 ID
标记某个子代理由哪次工具调用创建的编号，用它才能可靠显示上下级关系。

对本项目的影响

要做出图二、图三的层次感，关键是把现在已有的事件整理成可靠条目，而不是增加更多卡片、颜色或模型提示词。

  • 工具和子代理进入同一个 turn 内列表；子代理默认是父工具行，点击才开侧栏/明细。
  • 真实 narration 作普通文本段；没有 narration 时保守显示系统状态。
  • 不要持久化 spinner、订阅或 in-flight 状态；不要从标题字符串推测关系或用工具名配对结果。
