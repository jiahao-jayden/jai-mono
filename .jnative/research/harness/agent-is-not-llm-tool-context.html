Agent Harness · 源码级对照

Agent 不等于 LLM + Tool + Context：循环之外的那部分才拉开差距

写于 2026-09-04。八个框架的源码都钉了版本：Tardigrade c338df7、DeepSeek Harness 76fda72、pi dd7e816（main）、Claude Code 2.1.260、opencode 70f7411、LangGraph 81bf17b、we0-agent-x 本地工作树、JAI 212a098。每条论断后面给的都是这些版本上的行号，完整证据在同目录的 agent-harness-comparison.md。

那句话是谁说的

「Agent 就是 LLM 加工具加一个循环」这句话有出处，说的人也不是外行。

Anthropic 在 2024 年 12 月的 Building effective agents 里写：

Agents can handle sophisticated tasks, but their implementation is often straightforward. They are typically just LLMs using tools based on environmental feedback in a loop.

Thorsten Ball 在 2025 年 4 月的 How to Build an Agent 里写得更直接：

It's an LLM, a loop, and enough tokens. It's what we've been saying on the podcast from the start. The rest, the stuff that makes Amp so addictive and impressive? Elbow grease.

Simon Willison 2025 年 9 月收敛成一句：

An LLM agent runs tools in a loop to achieve a goal.

这三句话都对。它们定义的是 agent 的行为：模型自己决定下一步做什么，做完把结果喂回去。但 Ball 那句话的后半句常被漏掉：剩下的部分是 elbow grease。这篇文章讲的就是那个「剩下的部分」，以及它在八个框架里长成了多么不一样的形状。

同一批人后来都在写这个「剩下的部分」。Anthropic 2025 年 11 月发了 Effective harnesses for long-running agents，OpenAI 2026 年 2 月发了 Harness engineering，DeepSeek 的官方页直接写 Agent = Model + Harness。Harness 这个词指的就是包在循环外面、让它能在真实环境里跑完的那一层。

第一步：十行循环，以及它在哪一秒出问题

任何教程里的 agent 都长这样：

messages = [system_prompt, user_query]
while True:
    response = llm.chat(messages)
    if not response.tool_calls:
        return response.content
    for call in response.tool_calls:
        result = execute_tool(call)
        messages.append(tool_result_message(call, result))

这段代码能跑。你让它改一个文件、查一个 API，它工作得很好。问题出在第 7 行和第 8 行之间。

设想模型决定执行 bash("rm -rf dist && npm run build")。execute_tool 开始跑，dist 目录在第 1 秒被删掉，npm run build 跑到第 3 秒，这时进程被杀了。原因可以是容器 OOM、机器断电、或者用户按了 Ctrl-C 之后关了终端。

新进程起来，读你存的 messages。它看到最后一条是 assistant 说「我要执行 rm -rf dist && npm run build」。它看不到任何工具结果，因为第 8 行 messages.append 还没执行到。对新进程来说，这个工具调用看起来从未发生过。

于是它再跑一次。rm -rf dist 这次报 No such file or directory，问题不大。换成 git push --force、stripe.charges.create(...)、DROP TABLE 呢？

这里有个容易混的地方。很多人会说「我们有记录，每条消息都存了 JSONL」。存的是会话记录（transcript）：人和模型说了什么。它在工具返回之后才写结果。崩在中间，记录上是空白。你需要的是另一种东西：在工具开始之前就写下「我要跑这个了」。这两种记录长得很像，都是一行行 JSON，但回答的问题不同。前者回答「聊到哪了」，后者回答「做到哪了」。

Claude Code 就是前者的典型。我在本机 ~/.claude/projects/ 下一份 1478 行的 transcript 上跑了统计：

$ jq -r '.type' 8a78d37e-….jsonl | sort | uniq -c | sort -rn
 610 assistant
 374 user
  82 last-prompt
  81 permission-mode
  ...
$ jq -r 'if has("seq") then "has_seq" else "no_seq" end' … | sort | uniq -c
1478 no_seq
intent_records 0

没有序号，没有意图记录。tool_use 那一行是 assistant 消息的一部分，tool_result 在下一条 user 消息里。官方文档给了 --resume 和 --continue，但没有一页写工具执行中途崩掉怎么办。这不是批评，Claude Code 的定位是交互式终端工具，人就坐在旁边。但如果你拿 Agent SDK 去跑无人值守的长任务，就要知道它的记录是这一种。

第二步：先写一行再干活

把上面那段循环改 4 行：

for call in response.tool_calls:
    journal.append({"type": "tool_dispatched", "call_id": call.id,
                    "tool": call.name, "args": call.args})   # 先写
    result = execute_tool(call)
    journal.append({"type": "tool_result", "call_id": call.id,
                    "result": result})                       # 再写

现在同样的崩溃，新进程读到的是「有一条 tool_dispatched，没有对应 call_id 的 tool_result」。它知道这一步可能做了。它不知道做没做完。这个「不知道」就是后面所有分歧的起点。

在继续之前把两个词说清楚，后面要反复用。

幂等：一个操作做一次和做十次结果一样。mkdir -p 幂等，rm -rf dist 大致幂等，git push --force 不幂等，stripe.charges.create 不幂等。有些外部服务允许你带一个唯一的 idempotency key，它靠这个键去重，这时不幂等的操作也能安全重试。前提是那个服务支持，bash 不支持。

at-least-once：系统保证这一步至少执行一次，可能更多。这是「崩了就重跑」的代价。和它对应的 exactly-once 在有外部副作用时几乎做不到，除非副作用和记录写在同一个数据库事务里。

第三步：模型调用本身也是要花钱的副作用

上面只说了工具。模型调用同样是「跑完才知道结果」的外部操作，而且每次都计费。崩在 provider 返回之前，新进程重新调一次，就是重复付费；连崩三次就是四倍账单。

所以「先写一行再干活」的框架，对模型调用也写。Tardigrade 在打 provider 之前先追加一条 ModelCalled，注释写得很清楚（machine.ts#L456-L469）：

// The mark records the attempt BEFORE the inference, appended by the act itself: a
// died attempt leaves its mark, the next derivation counts it, the bound holds.
// callId is the provider idempotency key (shared across retries of one logical
// attempt); ordinal is the occurrence the dedup key reads.
const mark = modelCalled({ callId: input.attempt, model: selected, ordinal: input.ordinal, … })
yield* events.append([mark])

有了这条标记，重启后能数出「这个 attempt 已经死过几次」，超过 giveUpAfter 就判 TurnFailed，不会无限重调。JAI 的对应物是 model_attempted，预分配 assistantEntryId，恢复时同样按 id 点查。

这一节要说的是：「会话记录」和「执行日志」的差别，从模型调用这一层就开始了，不只是工具。

第四步：八个框架把「事实」存成了三种形状

看完前三步，你已经能问出对的问题：这个框架的 durable 事实是什么形状，写在执行之前还是之后。我把八家的答案分成三类。

事件日志。 一张只追加的表，每一行是「发生了什么」，当前状态靠从头折叠算出来。Tardigrade 最纯粹，它的存储只有一张三列表（platform/bun/src/host.ts#L175-L183）：

yield* sql`CREATE TABLE events (
  seq INTEGER NOT NULL PRIMARY KEY,
  key TEXT,
  event TEXT NOT NULL
) WITHOUT ROWID`
yield* sql`CREATE UNIQUE INDEX events_key ON events (key) WHERE key IS NOT NULL`

key 上的唯一索引是它整套机制的地基：同一个 key 只能落一次，所以「有没有做过」等价于「这个 key 在不在表里」。DeepSeek Harness 的 SessionEvent 日志、JAI 的两本 journal、pi 在 main 分支上的 AgentHarness 都属于这一类。

状态快照。 不存「发生了什么」，存「现在是什么」。LangGraph 在每个 super-step 结束时把所有 channel 的值打包成一个 checkpoint，外加一份 pending_writes 记录同一步里已经成功的 node 写了什么。we0-agent-x 用 SQL 表做 message/part 的 upsert，同一条记录会被覆盖，它的设计文档明确写了「不引入 Outbox、Event Sourcing」。

只有消息。 Claude Code 的 JSONL transcript。opencode 介于中间：message 和 part 是可变表，旁边另有一张 append-only 的 event 表，但恢复时读的是 part 的状态。

这个三分法比「日志派 vs 快照派」多一类，多出来的这一类正好是最常见的。大多数自己拼 SDK 的团队做出来的都是第三种。

第五步：那一步到底做没做，四种回答

现在回到第二步留下的问题。日志里有 tool_dispatched 没有 tool_result，新进程怎么办。八个框架给了四种答案，每种都有源码。

重跑答案一：再跑一次。 Tardigrade。reconciler 的逻辑只有一条：派生出来的 transition 如果在日志里找不到同 key 的结果，就 fire（reconciler.ts#L204-L218）。工具的 key 绑在返回事件上（tool.ts#L33-L48）：

effect({
  key: `tr:${call.callId}`,
  act: (input, signal) =>
    Effect.gen(function* () {
      const result = yield* tool.run(input.arguments, { … })
      return [toolReturned({ callId: input.callId, result, … })]
    })
})

注意这里和第三步的差别：模型调用有前置的 ModelCalled，工具调用没有。tr:<callId> 只在工具返回时才写。所以对工具来说，Tardigrade 连「这一步可能做过」都不知道，它只知道「没有结果」，然后重跑。文档自己写明这是 at-least-once（why.md#L67）：

Every external effect runs at least once and its keyed result is recorded once. The transition key also functions as an idempotency key for providers that accept one.

作者在 2026-09-04 开的 PR #360 里说得更坦白：

External calls remain at least once across the gap between the side effect and its recorded outcome. The guide calls out idempotency keys and repeat-safe operations because event keys cannot make an external service transactional with the log.

这条设计在下游都接受幂等键的场景里成立，比如它默认的沙箱 JS 工具和支持 idempotency key 的 provider。接一个原生 bash 工具进去，重跑 git push --force 就是重跑。

补结果答案二：补一条「结局未知」，让模型自己判断。 DeepSeek Harness。它在工具执行前先 append('tool/call')，崩溃恢复时对每个没有结果的 call 合成一条错误结果（repair.ts#L91-L134）：

for (const [callId, { step, callSeq }] of pendingCalls) {
  const started = callSeq !== undefined
  const message: ToolResultMessage = deepFreeze({
    text: started
      ? 'The tool call was interrupted after it was recorded, but no result was durably recorded. Its outcome is unknown. Decide whether to retry from the tool semantics: retry only if the operation is read-only or idempotent; if it may have side effects, first verify external state or ask the user. Do not retry blindly.'
      : 'The tool call was interrupted before the Harness recorded it as started. Retry it if it is still needed.',
  })
  closers.push({ type: 'tool/result', /* error: TOOL_OUTCOME_UNKNOWN | TOOL_NOT_STARTED */ })
}
closers.push({ type: 'turn/end', /* reason: { kind: 'interrupted' } */ })

注意它区分了两种情况：tool/call 已落盘（可能做了）和还没落盘（肯定没做）。前者标 TOOL_OUTCOME_UNKNOWN，后者标 TOOL_NOT_STARTED。然后把 turn 闭合，把「要不要重试」这个决定写成一段英文交给模型。checkpoint policy 的 README 把边界说得很清楚：

Durable execution intent, not exactly-once effects — the policy records that a call was dispatched, not that its external effect completed.

停住答案三：停下来等人。 JAI。recoverOperation 是个纯函数，输入两本 journal，输出四种判定之一（recovery.ts#L113-L126）：

const incompleteDispatches = dispatches.filter((d) => !evidence.sessionEntryIds.has(d.resultEntryId));
if (incompleteDispatches.length > 0) {
  if (terminal) {
    return corrupted(`Operation "${operationId}" is terminal while a dispatched tool has no durable outcome`);
  }
  return Result.ok({ status: "indeterminate_tool", operationId, dispatches: … });
}

Runtime Host 拿到 indeterminate_tool 之后什么都不做（host.ts#L642-L662）：

/** Starts exactly one recovered provider-safe operation; indeterminate tools are deliberately parked. */
resume(verdicts) {
  if (verdict.status === "indeterminate_tool") {
    this.#indeterminate = new RuntimeHostIndeterminateTool({
      message: `Operation "${verdict.operationId}" requires tool reconciliation before it can resume`, …
    });
    return Result.ok(undefined);
  }

session 被 park 住，resume、navigate、cancel 都被挡。这是三种里最保守的，代价也在源码里能看到：错误文案写着 requires tool reconciliation，但仓库里没有任何 UI、RPC 或 CLI 能做这个 reconciliation。rg reconcil 只命中这条错误消息。

重跑节点答案四：从节点开头重来，副作用你自己管。 LangGraph。它没有 tool 级的意图记录，恢复的粒度是 node。官方文档写：

When execution resumes (after you provide the requested input), the runtime restarts the entire node from the beginning—it does not resume from the exact line where interrupt was called. This means any code that ran before the interrupt will execute again.

Side effects called before interrupt must be idempotent

这是把问题交还给应用层。opencode 和 we0-agent-x 大致也在这一档：opencode 把崩溃时还是 pending/running 的 part 投影成 interrupted，不重跑；we0-agent-x 按工具元数据 has_side_effects 分支，有副作用就 interrupted，没有就重跑。

四种答案排成一行：重跑 / 补结果交给模型 / 停住交给人 / 重跑节点交给开发者。没有哪个是免费的。Tardigrade 换来的是不用人介入；DeepSeek Harness 换来的是流程能自动闭合；JAI 换来的是不会多做一次；LangGraph 换来的是框架最简单。

第六步：把一次崩溃走完

抽象的说法看多了容易飘。JAI 的 crash-gate.test.ts 用 11 个崩溃点把一次 run 切开，每个点断言恢复判定、provider 调用次数、工具调用次数（crash-gate.test.ts#L194-L206）。挑其中四个点：

const checkpoints = [
  { expected: { type: "model_intent" },                       recovery: "ready",                providerCalls: 0, toolCalls: 0 },
  { expected: { type: "model_request", assistantEntryId: … }, recovery: "provider_interrupted", … },
  // …
  { expected: { type: "tool_execute", toolCallId: "call-1" }, recovery: "indeterminate_tool",   providerCalls: 1, toolCalls: 0 },
  { expected: { type: "session_entry", entryId: "tool-result-1" }, recovery: "indeterminate_tool", providerCalls: 1, toolCalls: 1 },
];

读法是这样的。

崩在 model_intent 之前：什么都没落盘，判 ready，重头跑，provider 0 次。

崩在 model_request 发出之后、回复落盘之前：model_attempted 在，assistantEntryId 不在，判 provider_interrupted。这一档允许重调模型，因为模型调用的重复代价只是钱，不改外部世界。

崩在 tool_execute 之前：assistant 的 tool_use 落了，tool_dispatched 没落。这时可以精确重跑那个工具，不用重新问模型。

崩在 tool_execute 门上：tool_dispatched 已落，工具还没真的跑（toolCalls: 0）。判 indeterminate_tool，park。

崩在 session_entry 门上：工具已经跑完（toolCalls: 1），结果那条 entry 还没写进 session journal。判定同样是 indeterminate_tool。

最后两行值得对着看。一个工具没跑，一个跑完了，从 journal 里看它们一模一样：都是有 tool_dispatched 没有 resultEntryId。恢复逻辑只能看 journal，所以它们必须得到同一个判定。这就是第二步说的「不知道做没做」的精确含义。

这张表说明了「意图先行」的收益是什么：每一种崩法都有一个确定的、可测试的判定，不需要人读日志猜。它也说明了写了意图不等于问题解决，最后两个点上你还是得停下来。

第七步：循环之外还有三件事会分出框架的高下

前面六步都在讲 durable 事实和恢复。这是差异最大、最难改的一条，但不是唯一一条。再看三个。

扩展能触到多深。 Claude Code 的 hook 是 shell 命令，30 多个具名事件，脚本返回退出码 2 就能挡住这一步，返回 JSON 能改 permissionDecision 和 updatedInput。它能拦一步，改不了循环。opencode 有 21 个进程内 hook，pi v1 有 33 个 extension 事件，JAI 有 6 + 9 个，这一档能改消息数组和工具列表。Tardigrade 没有 hook 这个概念，它的 permissions、budget、compaction 都是 component，和内核用同一个 initial / step / output 接口（component.ts#L14-L24）。LangGraph 也没有 hook，你要插一步就加一个 node。

待批准的请求崩了还在不在。 这个问题在单人交互式场景里不存在，人就在终端前。在后台跑、要等人审批时它就是主要问题。opencode 的实现是一张内存 Map（permission/index.ts#L18-L106）：

interface State {
  pending: Map<PermissionV1.ID, PendingEntry>   // PendingEntry = { info, deferred }
  approved: PermissionV1.Rule[]
}
…
pending.set(id, { info, deferred })
yield* events.publish(Event.Asked, info)
return yield* Effect.ensuring(Deferred.await(deferred), Effect.sync(() => { pending.delete(id) }))

进程一退，finalizer 对所有 pending 发 RejectedError。JAI 的审批也是进程内 Map，AGENTS.md 明写「审批是可丢弃的内存状态」。Tardigrade 把权限请求做成 keyed actor call，请求和决定都是日志里的事件；LangGraph 的 interrupt() 存进 checkpoint。这两家崩了重启，那个「等你点同意」的状态还在。

UI 拿到的事件能不能重放。 前端断线重连，是重新拉全量，还是从某个位置续。Tardigrade 的 SSE 直接用日志 seq 当 id，Last-Event-ID 就是续传点。JAI 的 Desktop 事件带 seq 信封，发现断层就拉一次 snapshot。opencode 的 /event 有 id 但 handler 不做 catch-up。Claude Code 的 stream-json 没有序号。这条决定了多窗口、后台任务、回放调试能不能做。

第八步：多 agent 并行，便宜模型解决不了的那些

「并行跑几个 agent，用便宜的模型打满并发就行」这个想法把并行当成了网络 I/O 问题。实际卡住的地方都在状态上。这一节只列源码里能看到的。

子 agent 的身份。 并行起五个子 agent，崩了重放，怎么保证不变成十个？Tardigrade 的做法是让子 agent 的身份等于那次调用的 call id（agents.ts#L43-L54）：

// Every call is its own agent: the child's identity is the call's id, so a Promise.all of five
// runs is five agents by construction, and no name exists to collide on.
// …
// The call id is the child's identity AND the message id, so a replayed dispatch reaches the
// same child and is absorbed as a duplicate.

opencode 的 task 工具建一个带 parentID 的子 session，默认深度 1。JAI 的 SpawnAgent 在同进程起独立 Agent，上限 4 个。Claude Code 每个 sub-agent 是独立的 subagents/agent-<id>.jsonl。

预算不能双扣。 父 agent 给整个 run 定了预算，子 agent 并发跑，重试时怎么不多扣？Tardigrade 在 spawn 之前先从父预算里划一份，划扣本身也按 call id 去重（agents.ts#L484-L489）：

// Draw from the run's single budget before the child spawns, …
// The draw is keyed on this call's id, so a re-driven code body reuses its grant and never draws twice.
const budget = yield* Effect.promise(() => reserve(ctx.callId, want))
if (budget <= 0) return { error: "the run's budget is exhausted; no budget to spawn this agent" }

子 agent 自己预算用完时，caller() 把预算权威解析成调用它的那个 thread，往上要（budget.ts#L47-L51）。其他七家里我没有找到等价的机制。

同一份上下文不能被多个分支写。 pi 的 v2 设计用 lane 给每个并行分支独立的树位置、operation log 和队列，SQLite 层用带 fence 的 writer_leases 拒绝第二个写者。这一条要标清楚：它在 harness-v2/j4 分支的设计文档和 substrate 里，主产品路径还没走上去。JAI 用树形 branch，LangGraph 用 subgraph 隔离 state。

这三条加上第七步的「待批准请求在不在」，就是并行 agent 会撞上的墙。它们跟模型便宜不便宜没有关系。

怎么用这些信息

如果你的 agent 只在终端里陪人干活，人随时能看、能按 Ctrl-C，Claude Code 那种「会话记录 + hook」的形态够用，不需要事件日志。

如果它要在后台跑，工具有副作用，你要先回答第二步那个问题：工具开始前写不写一行。写了之后再决定第五步的策略。我的判断是：能接受人介入就选 park 或补结果，不能接受人介入又不能保证下游幂等，就不要接不幂等的工具。

如果你的流程能画成图、每个节点的副作用能自己做到幂等，LangGraph 的 checkpoint 够用，并且它是八家里最不用你操心持久层的。

如果你想看事件日志派做到极致是什么样，读 Tardigrade 的 reconciler.ts 和 DeepSeek Harness 的 repair.ts，两个文件加起来不到 500 行。但别急着搬 Tardigrade 的 component / actor 抽象，它 22 天发了 22 个 release，核心契约在 8 月 25 日和 9 月 4 日各改过一次。

最后回到开头那句话。「LLM 加工具加循环」定义了 agent 做什么。Tardigrade 作者在 PR #360 里那句「event keys cannot make an external service transactional with the log」定义了 harness 要解决什么。这两句话之间的距离，就是这篇文章。
