为什么 Desktop Agent 会重复搜索而不收敛

这次问题主要发生在 Agent runtime：工具结果会让模型继续下一轮，但系统没有记录“已经搜过什么、这次有没有新信息”。

核验日期：2026-09-12（UTC+8） · commit 78ce62007ec54166c63622ef09e88da8a438b384

证据笔记：Markdown 研究笔记。本页 Tailwind 依赖 CDN，打开时需要联网。

结论

一次普通工具调用不是结束信号；如果没有明确的停止状态，模型会把结果当作下一次搜索的输入。

1. 这不是 ACP、Bash 或 Desktop transcript 在内部重试，而是一次 run 中 8 次模型尝试、14 个 tool call 和 14 个 tool result 逐轮重新规划。

类比：像店员每拿到一次货架清单就重新决定下一排要看；清单没有复制，缺的是“哪些排已经看过”的记录。这个类比不适用于副作用工具，因为写入操作不能仅凭清单去重。

对本项目：控制点在 Agent loop/工具执行边界，不在 transcript 卡片。

s-loop

2. 模型没有直接看到 cwd 和可搜索的 sibling roots，于是先在错误的局部 workspace 内试探。

类比：给人一张房间地图，却不告诉他整栋楼的入口；他会反复检查房间，最后才去找楼梯。类比不代表应该扩大所有访问权限。

对本项目：应把 cwd、项目身份和授权的额外 roots 作为运行事实注入模型 context。

s-cwd

3. 工具返回了文本，却没有 operation 级的搜索覆盖、结果 fingerprint 或 no-progress 状态。

类比：每次查档案都拿到一张纸，但没有总目录；你知道这张纸写了什么，却不知道同一柜子是否已经查完。

对本项目：需要统一的结果 envelope 和跨 turn search ledger。

s-contract

4. “最新”以及 `we0` 指什么没有固定；工具本身很快，最后一次跨 workspace 权限请求被拒绝后，run 才以 aborted 结束。

类比：盘点时没有先约定“最新”看生产日期还是入库日期，盘点员一直追加检查，最后被告知不能进仓库。

对本项目：权限拒绝后的 partial summary 需要成为明确的 Runtime 产品语义。

s-abort

5. 成熟方案把预算、精确重复检测、post-turn stop 和工具契约分开做，但没有一个公开方案自动解决所有语义等价搜索。

类比：既要限制盘点次数，也要防止重复扫同一箱，还要在需要时强制收工；三件事不能用一个“请注意”代替。

对本项目：先借鉴硬边界，再为 `ls → find → rg` 建立本地 coverage 语义。

这次 `we0` run 实际发生了什么

这次真实运行先在 `app/desktop` 内搜索，拿到候选后又扩大到用户代码目录，最后因为权限拒绝中止。

类比：先在当前房间翻抽屉，再翻整栋楼，找到几只箱子后继续逐箱开封；中途被门禁拦住，所以没有把已经找到的东西整理成清单。

具体 trace

  1. 一次 `send` 进入 `session/prompt`，Runtime 创建一个 operation。
  2. 首轮调用 `pwd && ls -la` 和 FFF `find("we0")`，确认 cwd 是 `jai-mono/app/desktop`。
  3. 模型在 `jai-mono` 内重复枚举并传入绝对搜索 path，FFF 返回 workspace boundary 错误。
  4. 第五个 turn 才扩大到 `/Users/jayden/code`，得到多个 `we0` 候选。
  5. 模型继续检查子目录和 git 状态，跨 workspace Bash 触发权限请求并被拒绝。
  6. provider 返回 `stopReason: "aborted"`，没有自动 partial summary。

工具结果为什么会进入下一轮

工具结果默认只是下一次模型判断的输入，只有显式停止状态才会让 loop 结束。

类比：每交一次查档结果，主管都会再问“下一步呢”；除非有人明确盖章结束，否则流程会继续。这个类比不意味着应该把所有工具都改成自动结束。

工具契约缺少哪些收敛信息

工具知道一些执行细节，但模型没有统一收到搜索范围、覆盖完整性和下一步动作。

类比：仓库管理员手里有完整盘点表，访客只拿到几张打印纸；访客不能据此判断整个货架是否已经盘完。

为什么最后没有给出总结

权限拒绝被当成 aborted 终态处理，当前 Runtime 没有把已找到的候选自动整理成部分结果。

类比：盘点员被门禁拦住后，系统只记“任务中止”，没有自动把已扫过的箱子列出来。

成熟方案说明了什么

成熟实现把“限制次数”“识别重复”和“正常收工”分开处理。

类比：盘点制度同时规定最多查几轮、同一箱不要重复扫、主管可以在一轮结束后叫停；任何一个规则都不能替代其它规则。
机制能解决不能解决
cwd / authorized roots减少猜工作范围不定义“最新”的业务排序
max turns / max steps防止 run 无限增长不知道结果是否足够
exact fingerprint拦截完全相同调用拦不住语义等价变体
post-turn stop当前批次完成后安全退出不能撤销已执行工具
result envelope提供 count、truncated、cursor、scope仍需要 coverage/no-progress 判断
证据与原文
“Repeated Tool Calls: If we detect 5 consecutive instances of an identical tool call ...” —— Gemini CLI 的 exact detector，不能覆盖 `ls → find → rg` 的语义等价调用。
“Tools can also return `terminate: true` to hint that the automatic follow-up LLM call should be skipped.” —— Pi 的工具停止接口。

建议落地顺序

最小的后续路线是先补运行事实和结果状态，再补重复保护与终止原因。

类比：先把地图和盘点表交给盘点员，再加重复扫描报警，最后规定被门禁拦住时怎样交接结果。
  1. 把 cwd、project metadata 和授权的额外 roots 注入模型可见的运行事实。
  2. 统一搜索结果 envelope：root、normalized query、count、complete/truncated、cursor、错误 code 和 next action。
  3. 在统一执行边界增加 exact fingerprint，再按 operation 判断跨工具 no-progress。
  4. 补 `completed`、`max_steps`、`loop_blocked`、`needs_authorization`、`tool_error`、`aborted` 等终止原因。

不要单独依赖：system prompt、maxIterations、compaction 或 transcript 折叠；它们都不能提供搜索 coverage。

待验证

  • provider 为什么没有续 FFF cursor，以及为什么在已有候选后继续扩大搜索。
  • 完整 provider request payload 是否包含 cwd、project 或其它未落 durable journal 的上下文。
  • “最新”应按 mtime、git commit time、最近打开时间还是 Desktop metadata 定义。
  • exact/no-progress guard 的阈值和误报处理，需要真实运行样本 benchmark。

对本项目的影响

修复边界在 Agent runtime 和工具执行契约，不在 Desktop transcript projection。

类比：应修改盘点规则和工作单，而不是把重复的盘点记录折叠起来。

结论：先补模型可见的工作范围和搜索状态，再补 operation 级重复/无进展保护；UI 只需如实展示终止原因。

术语表

Agent loop
模型提出动作、工具执行、结果回传，再决定下一步的循环。
tool result envelope
除了文本，还告诉模型范围、数量、是否完整和下一步怎么继续的结果包装。
search ledger
一次运行中记录哪些目录和查询已经覆盖、是否产生新候选的状态表。
no-progress
这次动作没有扩大范围或增加有用结果，可以停止继续试探的判断。
partial summary
任务中止时，把已经确认的事实和尚未完成的部分分别列出来。
