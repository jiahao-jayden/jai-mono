# `app/desktop` 多语言框架选型：FormatJS / i18next / Lingui

核验日期：**2026-09-01**。项目证据固定在 `jai-mono` 提交 [`de3d1f0a36d658fd087c671c5658b12669c1b117`](https://github.com/jiahao-jayden/jai-mono/tree/de3d1f0a36d658fd087c671c5658b12669c1b117)；候选包固定为 `react-intl@10.1.25`（FormatJS tag [`548d6469`](https://github.com/formatjs/formatjs/tree/548d6469a2336bc8f08716bd3d810adb2cee9c0f)）、`@formatjs/cli@6.16.22`（tag [`14be9c38`](https://github.com/formatjs/formatjs/tree/14be9c387b5ea78bca7264e3f94af2edc2efd9d3)）、`i18next@26.4.1`（tag [`c057ee04`](https://github.com/i18next/i18next/tree/c057ee048c55a61c095acc017365e997e4f723f8)）、`react-i18next@17.0.13`（tag [`addf646a`](https://github.com/i18next/react-i18next/tree/addf646a37f5980af08814b5a2568def28e7e428)）、`@lingui/react` / `@lingui/vite-plugin` / `@lingui/cli@6.6.0`（tag [`665a1981`](https://github.com/lingui/js-lingui/tree/665a19815378dedd89346bb7707bdb0e28df79e7)）。官方文档为当日访问快照。固定 package 与 commit 的目的，是避免将未来文档或依赖范围变化误读为本次结论。

## 结论

1. **推荐 `FormatJS/react-intl`：安装 `react-intl@10.1.25`，用 `@formatjs/cli@6.16.22` 做提取。** 该版本声明 React `>=18` peer，因此覆盖本项目锁定的 React 19；`IntlProvider` 的 `locale` 与 `messages` 正好接收 Desktop 主进程持久化并经 IPC 投影出的 UI locale 与目录；其 `FormattedMessage` 使用 ICU Message Syntax，并且有日期、数字、相对时间组件及原生 TypeScript 声明。[包元数据](https://github.com/formatjs/formatjs/blob/548d6469a2336bc8f08716bd3d810adb2cee9c0f/packages/react-intl/package.json)；[Provider 与组件 API](https://formatjs.github.io/docs/react-intl/components/)；[消息与 ICU API](https://formatjs.github.io/docs/react-intl/api/)；[提取工具](https://formatjs.github.io/docs/react-intl/#message-extraction)。
2. **这不是“功能最多”的选择，而是对“仅 `zh-CN` / `en`、不需要浏览器探测或远端加载、locale 由 Electron 自己保存”的最小完整方案。** `react-intl` 的文档路径只要求 provider、消息描述符和独立 CLI 提取；相比之下，i18next 若统一采用 ICU 还要接入 `i18next-icu`，而 Lingui 在本项目的 `@vitejs/plugin-react` 路径要求在 Vite 配置中同时加入 Lingui 插件和 Babel macro 转换。这里的“更小”是基于这些官方安装步骤作出的工程推断，不是未经核实的包体积结论。[FormatJS 提取](https://formatjs.github.io/docs/react-intl/#message-extraction)；[react-i18next 的 ICU 配置](https://react.i18next.com/misc/using-with-icu-format)；[Lingui 的 Vite + React/Babel 安装](https://lingui.dev/installation#vite)。
3. **不推荐把“无框架”作为正式 UI 国际化的默认实现。** 原生 ECMA-402 确实已有 `Intl.DateTimeFormat`、`Intl.NumberFormat`、`Intl.RelativeTimeFormat` 和 `Intl.PluralRules`，所以它可作为极小、冻结页面的基线；但它不提供消息目录、ICU 消息编译或源码提取。对于当前 `app/desktop/src` 的 85 个 TS/TSX 文件及持续演进的 Shell，手工保持两份文本、插值和复数分支同步的维护成本是更高的合理推断，而非标准本身的承诺。[ECMA-402 `Intl` 对象](https://tc39.es/ecma402/#intl-object)；[项目源码树与锁定版本](https://github.com/jiahao-jayden/jai-mono/tree/de3d1f0a36d658fd087c671c5658b12669c1b117/app/desktop)。
4. **先纠正前提：此 checkout 实际锁定 Electron `42.7.0`，不是 43；React `19.2.4`、Vite `7.3.6`，并使用 `@vitejs/plugin-react@5.2.0`。** 选型对 Electron 主版本没有专属依赖，但实施前的 build/typecheck 应以这些实际版本为准。[Desktop manifest](https://github.com/jiahao-jayden/jai-mono/blob/de3d1f0a36d658fd087c671c5658b12669c1b117/app/desktop/package.json)；[Bun lock](https://github.com/jiahao-jayden/jai-mono/blob/de3d1f0a36d658fd087c671c5658b12669c1b117/bun.lock)。

## 当前 Desktop 与“Electron 保存 UI locale”的边界

当前分支还没有 UI i18n 依赖或 `locale` 持久化实现；`index.html` 固定为 `lang="zh-CN"`，而 renderer Vite 配置只有既有 React、Tailwind 与检查器插件。[HTML](https://github.com/jiahao-jayden/jai-mono/blob/de3d1f0a36d658fd087c671c5658b12669c1b117/app/desktop/index.html)；[renderer Vite 配置](https://github.com/jiahao-jayden/jai-mono/blob/de3d1f0a36d658fd087c671c5658b12669c1b117/app/desktop/vite.renderer.config.mts)；[manifest](https://github.com/jiahao-jayden/jai-mono/blob/de3d1f0a36d658fd087c671c5658b12669c1b117/app/desktop/package.json)。

仓库已经有适合 Desktop 自有偏好的持久化形态：`electron/theme.ts` 用 `electron-store` 保存 `theme`，并通过一个窄的 `DesktopThemeService` 暴露读写；这只是主题的现状，不表示 UI locale 已被保存。[主题服务源码](https://github.com/jiahao-jayden/jai-mono/blob/de3d1f0a36d658fd087c671c5658b12669c1b117/app/desktop/electron/theme.ts)。

设置页中的 `Response language` 是 agent 的响应语言：`DesktopConfigService` 将 `language` 读取和写回 Runtime Host，页面标题也明确是 `Agent Defaults`。它不能复用为 Desktop UI locale，也不应让 renderer 把 UI 偏好写入 agent 配置。[配置适配器](https://github.com/jiahao-jayden/jai-mono/blob/de3d1f0a36d658fd087c671c5658b12669c1b117/app/desktop/electron/config/index.ts)；[设置组件](https://github.com/jiahao-jayden/jai-mono/blob/de3d1f0a36d658fd087c671c5658b12669c1b117/app/desktop/src/components/shell/settings/general-settings.tsx)。

因此本题的约束应落实为：**Desktop 主进程拥有 `"zh-CN" | "en"` 这一 UI 偏好事实，安全 RPC DTO 将它投影给 renderer；renderer 只据此选择 catalog 并配置 `IntlProvider`。** 后半句是把既有主题 owner 模式和 React Intl 的 provider API 结合后的架构判断，不是任一框架的强制要求。[主题 owner](https://github.com/jiahao-jayden/jai-mono/blob/de3d1f0a36d658fd087c671c5658b12669c1b117/app/desktop/electron/theme.ts)；[React Intl Provider](https://formatjs.github.io/docs/react-intl/components/#intlprovider)。

## 推荐落地边界与待验证项

推荐的运行时边界是：主进程保存 `DesktopUiLocale`，RPC 返回经过白名单投影的 locale；renderer 在首次 snapshot 到达后，以 `IntlProvider(locale, messages, defaultLocale)` 包住 app，再让业务组件只消费 FormatJS message/format API。`IntlProvider` 本来就是为根树提供 locale 与 messages，未要求 locale 来自浏览器，因此不需要接浏览器语言探测。[React Intl Provider](https://formatjs.github.io/docs/react-intl/components/#intlprovider)。

建议将英文作为 `defaultMessage` / `defaultLocale`，将 `zh-CN` 放入显式 catalog；这与 React Intl 的 fallback 语义一致。是否应把中文而非英文定为 source locale 是产品/翻译流程选择，不是技术可由资料替代的结论，**待产品决定**。[Provider 的 `defaultLocale` / fallback 说明](https://formatjs.github.io/docs/react-intl/components/#locale-formats-and-messages)。

以下验证是实施 gate，而不是本次已经完成的代码改动：

1. 在固定版本上安装推荐依赖后运行 `bun --cwd app/desktop typecheck` 和 Electron Forge production build，专门核验 FormatJS ESM 依赖与当前 Vite 7 管线；FormatJS 明确提醒其 ESM artifacts 需要构建链处理。[FormatJS ESM 说明](https://formatjs.github.io/docs/react-intl/)。
2. 添加含 `{count, plural, ...}`、插值、`FormattedDate`、`FormattedNumber`、`FormattedRelativeTime` 的 `zh-CN` / `en` 测试页或组件测试；这些是推荐方案的官方 API，测试应证明现有 Electron runtime 中的输出，而不是只检查 TypeScript。[组件 API](https://formatjs.github.io/docs/react-intl/components/)；[消息 API](https://formatjs.github.io/docs/react-intl/api/)。
3. 将 `formatjs extract` 作为受 review 的脚本，并在 CI 校验生成 catalog 没有未处理消息；具体 catalog 格式、翻译来源和是否采用 FormatJS eslint 插件尚未由需求给定，**待实现 spec 决定**。[提取与 eslint 插件](https://formatjs.github.io/docs/react-intl/#message-extraction)。

## 对本项目的影响

- 应选 **FormatJS/react-intl**，而非从零实现 `t()`、也无需为只有 `zh-CN` / `en` 先引入 i18next 的 detector/backend 或 Lingui 的 Vite macro 工具链。该决定的事实基础是三方官方 API 与本项目当前 React/Vite 配置；“最小”是已明确标注的范围推断。[FormatJS](https://formatjs.github.io/docs/react-intl/)；[i18next](https://react.i18next.com/getting-started)；[Lingui Vite](https://lingui.dev/ref/vite-plugin)。
- 新增的 durable fact 必须是 Desktop 的 UI locale，不可复用 `Response language`；后者属于 Runtime Host 的 agent 配置。主进程已有 `electron-store` 保存主题的先例，因而可在同一 Desktop 配置领域为 UI locale 建立独立、窄的 owner 与 RPC DTO。[主题服务](https://github.com/jiahao-jayden/jai-mono/blob/de3d1f0a36d658fd087c671c5658b12669c1b117/app/desktop/electron/theme.ts)；[Runtime Host 配置投影](https://github.com/jiahao-jayden/jai-mono/blob/de3d1f0a36d658fd087c671c5658b12669c1b117/app/desktop/electron/config/index.ts)。
- 初次实现应同时建立 provider、两份 catalog、提取脚本与最小格式化测试；不必实现 SSR、Next.js、HTTP translation backend、浏览器 language detector 或远端 locale 下载。前半是 FormatJS 的正常组件/CLI 闭环，后半来自本题的 Electron 本地持久化范围。[Provider](https://formatjs.github.io/docs/react-intl/components/#intlprovider)；[提取](https://formatjs.github.io/docs/react-intl/#message-extraction)。
- 在合并前以当前真实依赖（React 19.2.4 / Vite 7.3.6 / Electron 42.7.0）做 typecheck 与 packaged build；若 Electron 将来升到 43，需重新做同一验证，不能把本笔记的 Electron 42 结果外推为 43 的实测结论。[当前 lock](https://github.com/jiahao-jayden/jai-mono/blob/de3d1f0a36d658fd087c671c5658b12669c1b117/bun.lock)。
