# 03: 本地 sink adapter（文件与 stderr）

要先完成:02 · 状态:⬜

## 交付什么

开发者在本机能真正看到一次运行发生了什么，不需要联网、不需要部署任何服务、不需要装厂商 SDK。做完之后：

- 启用本地 sink 后，运行过程以结构化记录写到本地文件或 stderr，带能串起同一次运行的关联 ID。
- **未配置任何外部平台时，本地文件就是事后可见性的来源**：昨天那次运行的因果链仍可翻看，且不需要数据库、不需要查询接口、不重建 trajectory。
- CLI 与协议模式下，诊断输出**不会污染 stdout**——协议数据与诊断数据分开。
- 诊断记录**不含 stack、不含 cause、不含用户内容**。
- 默认不开启；开启方式明确，产生的文件路径、保留期与体积上限是显式的，不是隐含行为。

## 范围

做:

- 实现本地文件 sink 与 stderr sink，二者都是 01 定义的 sink 接口的 adapter，不是另一套并行机制。它们接收 01 已完成内容投影的安全记录，**自己不再做投影**。
- 确定落盘的序列化形式（行式 JSON），使记录可被普通工具翻看与过滤，同时保持与其他 sink 相同的记录语义。
- 按实际运行时依赖单独导出这两个 adapter，不进入 01 的零依赖契约包。
- 严格区分输出通道：协议 stdout 与用户 CLI 输出归各自的宿主，诊断固定走 stderr 或文件。业务模块不直接打印，只通过注入的诊断端口。
- 确定并记录本地文件的路径、轮转策略、保留期与体积上限。这些必须是显式的，不能留为隐含行为。
- 明确本地文件的定位：**可删除的诊断产物**，不是事实来源、不参与恢复、不被任何代码当权威数据读。
- 在宿主组合根装配：默认不开启；开启后不改变任何业务行为。可与其他 sink 同时启用。
- 测试：记录不含 stack 与 cause、协议模式下 stdout 不被污染、sink 失败不影响调用方与其他 sink、关联 ID 能串起一次运行、写出的文件可被重新读回并还原因果结构。

不做:

- 不发送任何数据到进程外的网络目标（05 做）。
- 不产生新的 span 或事件词汇；本项只消费 02 已产生的观测记录。
- 不在 sink 内做内容投影或脱敏。那在 01 的扇出前统一完成；此处重做一遍等于制造第二个可能漏的地方。
- 不实现 SQLite sink。
- 不做 metrics。
- 不新增长期保存的数据。本地文件是可删除的诊断产物，不是 durable fact，不参与恢复。
- 不为本地文件建查询接口、协议方法或 UI。要翻看就用普通文件工具——一旦给它做读取面，就是上一版 trajectory 的开头。
- 不改变既有的用户可见输出或 CLI 行为。
- 不引入 `console.*` 到业务模块。

## 需要遵守的整体选择

- 所有去向都是同一 sink 接口的 adapter，可同时启用多个，失败逐个隔离。见 plan.md「方案」第 2 条。
- 内容治理在扇出前做一次，sink 不重做。见 plan.md「方案」第 3 条。
- 本地输出与协议输出严格分开。见 plan.md「方案」第 10 条。
- 诊断记录不含 stack、不含 cause；跨边界只用白名单投影。见 plan.md「必须遵守的项目规则」中的错误处理条目。
- 带运行时依赖的 adapter 单独导出，不静态带入零依赖契约包。见 plan.md「方案」第 1、11 条。
- 本地文件是可删除的诊断产物，不是事实来源。见 plan.md「方案」第 4 条与「风险」。
- 轮转文件是可丢弃的诊断产物，不是长期保存的事实。

## 长期保存的数据与维护方

无。本项不产生、不读取、不修改任何长期保存的数据。本地轮转文件是可删除的诊断产物，由宿主管理其路径、保留期与体积上限，不参与恢复，也不是任何领域事实的来源。

## 风险

- 协议 stdout 被污染会直接破坏 CLI 与协议模式的通信。这是本项最容易出问题的地方，必须有测试覆盖。
- 诊断产物的路径、保留期与体积若留为隐含行为，磁盘占用与敏感信息驻留都不可控。
- 本地文件一旦被当成事实来源，就等于凭空多了一个 durable owner。它没有保留保证、可被清理、可被关闭。
- 诊断记录一旦允许携带 stack 或 cause，就会成为绕过内容治理的后门。
- 生产代码当前 `console.*` 为 0，这个基线要保持；引入 sink 不应给业务模块开直接打印的口子。
