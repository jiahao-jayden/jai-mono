# RFC 格式 PRD 与图示

结构来源：[InnerSource Commons 中文 RFC 模板](https://patterns.innersourcecommons.org/zh/fu-lu/e-wai/rfc)，核对日期：2026-09-14。以下保留原章节顺序，填写说明为 JN 的适配；范围、验收、图示和确认记录是 JN 的补充要求。

## 正文模板

填写后删除提示，不删 RFC 章节。不适用时说明原因，不能用空白冒充已检查。`意图（AI 当前理解）`必须保留，它是给后续执行者看的短交接，不替代概述、动机或验收。负责人必须来自用户指定或已有明确项目约定；个人需求默认由用户确认。

```markdown
# <功能名称>

功能名称：<稳定、唯一的名称>
开始日期：<YYYY-MM-DD>
被提名的负责人：<实际负责确认的人，不替他人签字>

## 意图（AI 当前理解）
<用几句话说明 AI 认为用户要解决什么问题、准备交付什么结果，以及本轮做与不做的边界。这里写当前理解，不写宣传语；需求变化时先更新本节。>

- 要解决：<当前问题或触发原因。>
- 准备交付：<用户最终能得到的行为、产物或变化。>
- 本轮不做：<明确排除的范围。>
- 已确定：<已经由用户或项目事实确定的关键取舍。>
- 还不确定：<会影响方案或实施的待确认问题；没有则写无。>

## 概述
<问题、拟议改动和预期结果，读完能知道这个需求做什么。>

## 回顾
<什么时候、在哪里、由谁回顾，结果记在哪里。>
- [ ] 复盘完成
<实施前写安排，实施后写实际发现，不以验收通过代替复盘。>

## 动机
<受影响的人、现有问题、使用场景和预期结果，带现状依据。>

## 指南级的介绍
<从使用者或贡献者角度解释新行为，定义项目特有概念，给出具体示例。>

### 本次范围
<本次交付什么、明确不做什么。>

### 使用流程与示例
<主流程图放这里，接着解释输入、结果和重要失败分支。>
<静态需求用关系图或前后对照替代，并说明原因。>

### 验收标准
- AC1：<可观察、可检查的条件。>
- AC2：<必要的异常、兼容或边界条件；数量按实际需要。>

## 参考实现级别的介绍
<回到使用示例，解释模块交互、数据与维护方、接口或协议、失败处理。>
<写清适用的权限、并发、兼容/迁移、运行依赖、项目规则和验证方式。>
<规则只摘相关条目并标出处；外部约定给来源、遵循程度及允许偏离。>
<关系图、时序图或状态图放在所解释的设计旁边。>

## 缺点
<明确成本、可能的回归、限制和承担的风险。>

## 理由和替代方案
<选当前方案的依据、认真考虑的其他路径，以及不做的后果。>

## 现有技术
<现有实现或相关方案的经验，引用研究结论与一手来源。>
<未查证的主张不能当成事实；无相关材料时如实说明。>

## 未解决的问题
<分别列出接受前必须解决、实施中验证、范围外的问题。>
<接受前必须解决的问题未解决时，不能标记需求已接受。>

## 未来的可能性
<后续可能演变的方向，不自动计入当前范围或子任务；没有则说明。>

## JN 确认记录
<初始写待确认。得到实际确认后记录确认人、日期、覆盖的 PRD 与任务范围、
确认依据（评论链接或明确的会话决定）及是否稍后开始。范围改变时追加记录。>
```

多位负责人时，在所有被提名负责人实际确认前不能标记接受。记录授权依据不等于代签。发布未确认草稿可以独立于接受和实施，是否发布遵循用户授权。

## 图示怎么选

PRD 默认用 Markdown 内的 Mermaid，不创建 HTML 副本。至少有一张主流程图；静态需求以关系图或前后对照代替。检查需求实际涉及哪些关系，再补充图示，不只为凑数量重复画主流程。

| 需要解释的内容 | 图示 | 放置位置 |
|---|---|---|
| 用户或系统如何完成目标、失败后去哪 | 流程图 | 指南级介绍的使用示例旁 |
| 多个模块的职责和数据流向 | 关系图或数据流图 | 技术部分的模块说明旁 |
| 调用顺序、响应、超时或重试 | 时序图 | 技术部分的交互说明旁 |
| 创建、运行、暂停、失败等生命周期 | 状态图 | 技术部分的状态定义旁 |
| 迁移或流程调整 | 前后对照图 | 迁移或改动说明旁 |

每张图只回答一个问题，附一句说明。概览装不下就拆出细节图。流程中的分支标条件，时序中的参与者与正文一致，状态转换标触发条件。区分现状、拟议方案和未决部分，不把假设画成已确认事实。

使用可读的节点文字，避免仅写函数名；保留必要的技术术语。颜色不能承担唯一含义，正文必须能说明图中的关键行为。不把图中出现的未来能力当成本次范围。

## 交付前检查

1. 使用当前环境已有的 Mermaid 解析/渲染工具，或在有授权的文档预览环境中验证；不为预览擅自发布 Issue 或上传私有 PRD。
2. 检查实际渲染，确认标签可读、连线方向正确、重要分支和状态没有遗漏。无渲染工具时如实标记“图示未验证”，保留草稿状态。
3. 应用 `renhua` 项目文档模式，编辑正文及图中文字，不改节点 ID 和语法结构来追求文风。
4. 修改图中文字后重新验证渲染。逐条核对 AC、边界、约束和证据，确认编辑没有改变含义。
5. 交回图示验证结果及 renhua 编辑完成情况；不要把这份编辑检查当成用户已接受 RFC。
