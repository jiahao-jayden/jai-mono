把一个还没想清楚的想法,问成一份别人接手也不会跑偏的意图。

**只产内容。** 调用方决定它存到哪、叫什么。

## 要问出什么

- **问题** — 现在做不到什么,谁被影响。这是根,其他都挂在它下面
- **期望结果** — 做完之后什么变了
- **影响范围** — 碰哪些模块;碰哪些 durable fact,按项目约定它们归谁
- **边界** — 明确不做什么。这条决定了后面拆 spec 不跑偏,也是最容易被跳过的一条
- **规模** — 大(要拆成多个可独立验证的单元)还是小(1-2 个单元)

## 怎么问

调用 Skill 工具,传 `jn-grilling`。

**能查到的不要问。** 项目约定文件(`AGENTS.md` / `CLAUDE.md`)、领域词汇(`CONTEXT.md`)、已有 ADR、代码现状、`git log`,自己去读。事实归属和模块角色的规则通常都写在约定文件里。查到的列成「📌 已查明」告诉用户,不占提问额度。

只有真正需要用户拍板的才提问。他能一眼答上来的问题,说明你没查。

## 辨清术语

意图之所以会被误解,多半不是逻辑没讲清,而是同一个概念有三种叫法。

拷问过程中出现下面任一情况,当场把这个词记下来,连同一到两句定义和该避免的同义词:

- 用户用的词和已有词汇表里的定义对不上 → 当场指出:「词汇表里 X 是指 A,你说的像是 B,是哪个?」
- 一个词身兼数职(「配置」既指用户设置又指运行时参数)→ 提出一个更精确的叫法
- 出现了词汇表里没有、但这次会反复提到的概念

调用方会把这些词落到词汇表里。已经在词汇表里的不要重复产出。

只记**是什么**,不记怎么实现——这是词汇表,不是规格书。

## 产出

```markdown
# Intent: <标题>

日期:<YYYY-MM-DD>

## 问题
<现在做不到什么,谁被影响。用用户自己的话,别翻译成技术术语——翻译会丢掉他真正在意的东西。>

## 期望结果
<做完之后什么变了。>

## 影响范围
模块:<涉及的包/模块>
Durable fact 与 owner:<本次碰的持久事实,按项目约定归谁>

## 边界
<明确不做的事。>

## 规模
<大 | 小>。<一句理由。>

## 既定前提
<自查到的事实,带出处(文件路径或约定文件的条目)。>
```

## 完成标准

一个没参与这场对话的人,只读这份意图,能说出「要做什么」「不做什么」「碰了谁的地盘」——三样都答得上来才算完。

答不上来的那一样,就是下一轮该问的。

## 交回

把内容给调用方,并说明:规模判断是大还是小、还有什么没想清楚。

**这份东西要用户确认过才算数。** 意图错了,后面拆出来的每一个 spec 都是错的,而那时返工的代价已经翻了几倍。
