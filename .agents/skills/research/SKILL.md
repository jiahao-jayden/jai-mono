回答一个问题，证据追到一手来源，产出一份别人不用重查就能复核的笔记。用户要求可视化报告，或问题确实存在复杂关系、流程、时间演变、多方案比较或 GitHub issue 讨论时，同时输出 HTML 报告。

**结论必须可复核，而且在笔记里就能复核。** 读者应当不离开这份笔记就能看到支撑每条结论的原文，再顺着链接走到源头确认。只给链接不给原文的调研，读者要么全信，要么全部重查，两种都等于没做。

## 0. 在哪跑

**任何 research 调用都必须在独立 subagent 上下文里执行，包括用户直接点名这个 skill 的情况。** 主 agent 负责拆分、派活、汇总和交付，不得自己代替 subagent 做调研。

调研要读大量文档和源码。这些原文留在调用方的上下文里，会挤掉它正在做的事——一场访谈、一次拆分。隔离出去，调用方拿到的是浓缩后的答案，原文留在笔记里，需要时再翻。用户直接调用也遵循这条规则：他看到的是主 agent 汇总后的结论和笔记，而不是把检索过程塞进主上下文。

## 1. 先定规模

先把问题写成一句话再动手。写不出一句话，说明还不知道要查什么，先问用户。

然后判断问题类型。类型决定派几个 subagent、每个查什么、笔记要达到哪些深度要求（见「完成标准」）：

| 问题类型 | 并行 subagent | 每个的工具调用下限 | 固定要有的 subagent |
|---|---|---|---|
| 单点查证（某个 API 行为、某个字段含义） | 1 个 | 5 | — |
| 机制类（某个系统怎么运行、为什么这样设计） | 3 个以上，按子系统切分 | 15 | 1 个查来源面 |
| 对比几个方案 | 一个方案一个，再加 1 个 | 15 | 1 个查来源面 |
| 可行性（能不能接入、能不能跑起来） | 2 个以上 | 15 | 1 个真跑 |
| 摸清一整套协议或架构 | 4 个以上，按主题切分 | 20 | 1 个查来源面 |

数字是下限，不是预算。subagent 什么时候停，看它负责的那部分是否达到「完成标准」，而不是看调用次数。达到了就停，没达到就继续，中途发现问题比预想的大就回来加派。

**来源面 subagent** 只做一件事：跳出目标项目本身，找同类方案、作者或维护者本人的说法、issue 和社区实践、历史演变。它的产出直接填「来源覆盖」表。机制类、对比类和架构类问题都必须派它，因为只读目标仓库得出的结论，看不到这个设计在别处被证伪或被换掉的历史。

单点查证保持轻量：一个 subagent，找到原文、摘录、钉版本、回来。不要为了形式加派。

## 2. 派活要具体

每个 subagent 的任务描述必须包含五样，缺一样就会出现重复劳动、盲区或没法用的产出：

- **目标** — 要回答的那个具体问题，不是主题
- **输出格式** — 写到哪个文件；每条发现必须是「主张 + 带 SHA 的链接 + 原文摘录」三件套，缺摘录的发现单独列成「待验证」
- **来源指引** — 去哪查，优先哪类来源
- **边界** — 明确不查什么，避免和别的 subagent 撞车
- **完成标准** — 从「完成标准」一节里挑出它负责的那几条，原样写进去

反例：让三个 subagent 各自"调研 X 的权限模型"。它们会查同一批文件，得到三份高度重叠的报告。
正例：一个查协议定义，一个查参考实现的代码路径，一个查我们现在怎么做的，一个查别的项目怎么解决同一个问题。

subagent 把详细笔记连同摘录写到文件，只回传结论和文件路径。主 agent 汇总时把各份笔记的摘录**原样搬进**最终笔记，不得把摘录压缩成转述——转述会失真，而且读者又得回去点链接。

## 3. 先宽后窄

默认倾向是一上来就用又长又具体的查询，而这种查询往往什么都搜不到。

先用短而宽的查询探地形，看回来了什么，再逐步收窄。像人做研究一样：先知道有哪些东西，再钻进去。

## 4. 一手来源

**追到拥有这个事实的地方为止。** 官方文档、规范、源码、first-party API 响应，而不是别人对它们的转述。

第三方博客和教程可以用来**发现**线索，不能用来**支撑**结论。看到有用的说法，顺着它找到原始出处，引原始出处。作者或维护者本人的博客、演讲、issue 回复算一手来源，因为它们记录的是设计意图，这在源码里读不出来。

来源排序偏好要主动纠偏：权威但排名靠后的东西（规范原文、源码、学术 PDF、当事人的个人博客）通常比排在前面的内容农场更值得读。搜索排名不等于可信度。

查不到就说查不到。给一个来源不明的答案，比说"没查到"更糟，因为它会被当成事实用下去。

## 5. 把版本钉死

调研的是活的东西：代码会改，文档会更新，API 会变。不钉版本，结论过几周就无法复核，而且没人知道它是什么时候开始失效的。

- 源码：记下 commit SHA，引用用带 SHA 的 permalink 和行号范围
- 文档、规范：记下版本号或访问日期
- 包：记下版本号

笔记开头写明核验日期和钉住的版本，并说清为什么钉：避免后续变动混进结论。

## 5.5 GitHub issue 和 PR

当用户给出 GitHub issue/PR 链接，或问题涉及第三方库的真实故障、已知限制、维护者态度、修复进度时，读 [`references/github-issues.md`](references/github-issues.md)。

不要把 issue 当成另一个搜索引擎。先用文档、规范、源码或 release 确认公开行为；只有这些来源没有回答实际使用中的问题、需要追踪回归，或需要了解维护者已经确认的限制时，才查 issue 和 PR。

GitHub 讨论能提供三种不同东西，写报告时必须分开：

- 维护者确认的当前行为、设计取舍或修复计划
- 有版本、环境和复现步骤的实际案例
- 用户反馈、重复提问和表情反应反映出的关注程度

第一类可以支撑"维护者已确认"的结论；第二类只能说明"有人在这些条件下遇到过"；第三类不能推导出使用量、发生率或普遍性。issue 已关闭也不等于问题已经修复，必须看关闭原因、关联 PR、release 和受影响版本。

## 6. 产出

**只产内容。** 调用方决定笔记存到哪、叫什么。没有调用方（用户直接点名你）时，看仓库里已有的调研笔记放在哪、长什么样，跟随已有约定；没有约定就放一个合理的位置并说明放在哪了。

### 按主题归档

目标仓库已有 `.jnative/research/` 时，新笔记必须放在 `.jnative/research/<area>/<topic>.md`，不要继续堆在 `research/` 根目录，也不要按当前特性 slug 建目录。`<topic>` 是短横线小写、能表明调研题目的名字；同一份协议、平台或实现调研应能被多个特性直接引用。

先查看已有目录和笔记，复用已有 `<area>`，并先确认没有一份已有笔记已经覆盖当前问题。根据研究问题的主语义、读者最可能查找它的位置和后续复用方式自主分类；不要依赖一张预设主题表，也不要仅按当前需求名称分类。

问题跨主题时，按需要被复用的主结论选一个目录，不要复制同一份笔记；从需求工件链接到它即可。没有匹配的主题时，创建一个简短、稳定、能概括一组相关研究的主题目录。生成 HTML 报告时，与 Markdown 保持同目录同名，例如 `.jnative/research/<area>/<topic>.md` 和 `.jnative/research/<area>/<topic>.html`。

Markdown 是事实和引证的唯一依据。HTML 是它的完整可读版加上图，不能在里面新增 Markdown 没有的结论。

### 引证的形状

一处引证 = 链接 + 摘录。链接负责定位，摘录负责证明。

源码用带行号的代码块，5 到 15 行，多了截断并标 `…`；文档和规范用引用块引原句；命令输出用代码块贴原样输出。摘录紧跟被它支撑的那句话，不攒到文末。

````markdown
reconciler 只处理日志里还没有同 key 结果的 transition。[`reconciler.ts#L204-L231`](https://github.com/org/repo/blob/<sha>/packages/core/src/runtime/reconciler.ts#L204-L231)

```ts
// packages/core/src/runtime/reconciler.ts:204-231 @ <sha>
for (const transition of pending) {
  if (log.hasResult(transition.key)) continue;
  …
}
```
````

结论区里每条结论只放链接，保持结论短；但结论里出现的每个链接，中段必须至少有一处带摘录地再次出现。读者从结论跳到中段就能看到原文。

**没有摘录的主张不能进「结论」。** 它只能进「待验证」，并写明缺什么证据。做不到摘录通常有两种原因：来源是二手转述，或者是自己的推断。前者去找原始出处，后者老实标成推断。

### 固定的框

三件事是固定的：

- **结论在最前。** 读者要的是答案。编号列出，每条自足，不看后面也能读懂。不要铺垫
- **来源覆盖在影响之前。** 一张固定五行的表，逐行交代查了哪类来源、查到了什么或为什么没查到。读者一眼看到盲区
- **影响在最后。** 这些结论对本项目意味着什么：要改什么、不用改什么、什么被证伪了。不确定的地方在这里讲明，不要藏进结论

开头写核验日期和钉住的版本。

「来源覆盖」的五行固定，不许删行也不许留空：

| 来源类别 | 查到了什么 |
|---|---|
| 官方文档 / 源码 | <查了哪些文件和文档，钉在哪个版本> |
| 作者或维护者本人的说法 | <博客、演讲、RFC、issue 回复；没找到就写「未找到」并说明搜了什么> |
| 同类方案 | <点名 2 个以上，它们怎么解决同一个问题；单点查证可写「不适用」> |
| issue / PR / 社区实践 | <查了哪些，得到了什么；没查就写「未查」并说明为什么不需要> |
| 历史演变 | <changelog、设计文档、被替换的旧方案；没查就写「未查」并说明为什么不需要> |

写「未查」不丢人，写不出这一行才有问题：说明没想过这类来源可能推翻结论。

### 中间按题目自己长

中段不预设章节。**用题目自己的词命名**：「与本项目的映射」「逐项差距」「权限模型」「速查表」都比一个通用的「证据」更有信息量。

一份摸清整套协议的笔记会有十来个小节，一份单点核验可能只有一节。按需要来，不要凑数，也不要为了套模板把八个小节压成三个。

**每处主张紧跟它的来源和摘录。** 读者是在读到某一句时才想验证它的。

### 表格是主力，不是点缀

多方案对比、逐维差距、能力矩阵、时点与约束，这些用表格远比散文清楚。**维度做行，方案做列**，单元格里直接嵌带 SHA 的证据链接，读者当场就能跳过去核。

散文适合讲因果和取舍，表格适合让人扫。同一批事实要被逐项比较时，就用表。

### 图什么时候画

关系是图状的才画：调用链、状态迁移、跨进程的消息时序。这类东西用文字描述，读者得在脑子里重建一遍。

层级、清单、对比不要画图，表格更快、更好扫。

### 骨架

```markdown
# <问题的标题>

核验日期：<YYYY-MM-DD>。<钉住的版本/SHA，以及为什么钉。>

## 结论

1. <直接回答问题。自足。链接指向中段有摘录的位置。>
2. <...>

<按题目命名的中间章节，数量随主题而定，主张紧跟链接和摘录>

## 来源覆盖

| 来源类别 | 查到了什么 |
|---|---|
| 官方文档 / 源码 | ... |
| 作者或维护者本人的说法 | ... |
| 同类方案 | ... |
| issue / PR / 社区实践 | ... |
| 历史演变 | ... |

## 对本项目的影响

<要改什么、不用改什么、什么被证伪了。不确定的也写在这里。>
```

## 完成标准

通用四条，每份笔记都要过：

1. 每条结论都能指到中段某一处带摘录的引证。指不到的，要么去补，要么降级成「待验证」并写明缺什么
2. 「来源覆盖」五行都填了，同类方案至少点名 2 个（单点查证除外）
3. 每条结论紧跟它成立的条件或限制；没有限制的结论通常是没查到限制
4. 能量化的就量化：版本号、日期、行数、次数、延迟、基准数据。「很大」「较慢」「常见」这类词要么换成数字，要么删掉

再按问题类型加：

| 问题类型 | 额外要求 |
|---|---|
| 机制类 | 至少一段**具体走一遍**的 trace：给定一个输入，逐步写出触发了哪些事件、状态怎么变、每一步指到哪几行代码。再加一节失败模式或边界情况：崩溃、并发、超时、空输入时会怎样，各自有摘录 |
| 对比类 | 所有方案按同一组维度比；每个方案至少写出一个它**不成立的条件**（反方证据），不能只列优点 |
| 可行性类 | 真跑：clone、安装、执行、复现，把命令和输出原样贴进笔记。读代码推断出来的可行性只能标「未实测」 |
| 协议 / 架构类 | 机制类要求 + 对比类要求；另外每个核心概念给一张速查表 |

一个没参与调研的人，只读这份笔记就能判断结论是否成立，不需要重新查一遍。

交付前跑：

```bash
python3 <skill-dir>/scripts/check_note.py <note>.md
```

它检查上面第 1、2 条和骨架结构。检查失败就修，不要靠「这次情况特殊」跳过。

## 7. 可视化 HTML 报告

### 什么时候生成

用户明确要 HTML、可视化报告、汇报页或可以直接打开的报告时，生成。即使用户没说，只要调研的重点是以下任一项，也同时生成并在交付时说明：

- 组件、系统或参与方之间的关系
- 有顺序的流程、调用链或状态变化
- 版本、事件或决策随时间的变化
- 三个以上方案需要按相同维度比较

单点查证、两三条独立结论，或一张表就能说清的对比，不生成 HTML。

### HTML 是什么

HTML 的读者和 Markdown 不同。Markdown 给要复核证据的工程师看；HTML 给**所有人**看，包括不写代码的产品、设计、管理者和第一次接触这个领域的人。他们要的不是原文摘录，是"这东西到底是什么、跟我有什么关系"。

所以 HTML 分两层：

- **解释层**在上。每个章节按同一个顺序写：一句话说清是什么 → 一个来自日常生活的类比 → 再展开细节 → 这对读者意味着什么。术语第一次出现时用 `<dfn>` 标出，并在页尾术语表里给一句人话定义。先讲目的，再讲机制；读者不知道一个东西为什么存在之前，不关心它怎么运作
- **证据层**在下。Markdown 的全部内容——每个章节、每张表、每处摘录、每个链接——原样放进对应章节的折叠区里。想核的人展开看，不想核的人跳过

解释层不许新增 Markdown 没有的结论，只许换一种说法讲同一件事。类比是帮助理解的工具，它一定有不准确的地方，在类比旁边写清楚它在哪里失效。

一致性契约（`check_report.py --note` 会检查）：

- Markdown 的每个 `##` / `###` 章节，HTML 里有对应的一节，标题一致，顺序一致
- Markdown 的每张表、每处摘录、每个链接，HTML 里都有
- 每张结论卡片和每个中段章节都有一段 `data-plain` 的人话解释
- 有术语表；正文里每个 `<dfn>` 术语在术语表里都有定义
- 图放进它解释的那个章节，一张图回答一个问题；图上的标签用人话，不用代码里的标识符

写法细节、示例和判断标准见 [`references/visual-report.md`](references/visual-report.md)。

### 怎么生成

生成报告前先读 [`references/visual-report.md`](references/visual-report.md) 和 [`assets/report-template.html`](assets/report-template.html)。将它保存为与笔记同名的 `.html` 文件。

如果使用 GitHub issue 或 PR，还要读 [`references/github-issues.md`](references/github-issues.md)。

- 使用模板里的 Tailwind CDN：`https://cdn.tailwindcss.com`。报告打开时需要联网，交付时明确说明这点。
- Tailwind 负责页面排版；关系、流程和时间线用内嵌 SVG；多方案比较用 HTML 表格。
- 单张图超过 9 个节点或 12 条关系时，拆成概览和细节两张。
- 图表必须来自已经核验过的事实。每个结论标记 `data-claim-id`，并用 `data-source-ids` 连到报告中的来源；来源列表包含 Markdown 的全部引证，不挑选。
- 让图表有标题和说明。SVG 带 `role="img"`、`<title>` 和 `<desc>`；不要用颜色作为唯一的信息来源。
- 写完解释层后，找一段自己不熟悉领域的话读一遍：碰到一个不认识的词就停下来。用这个标准检查自己的报告，每个会让外行停下来的词都要么换成人话，要么 `<dfn>` 加术语表。

生成后运行：

```bash
python3 <skill-dir>/scripts/check_report.py <report>.html --note <note>.md
```

检查失败就修复；检查只验证报告结构、来源关联和与 Markdown 的一致性，不替代对事实的核验。
