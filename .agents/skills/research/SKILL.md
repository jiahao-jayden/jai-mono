回答一个问题,证据追到一手来源,产出一份别人能复核的笔记。

**结论必须可复核。** 读者应当能顺着引证走到源头,自己判断你的结论对不对。做不到这一点的调研,只是一份读起来可信的猜测。

## 0. 在哪跑

**任何 research 调用都必须在独立 subagent 上下文里执行,包括用户直接点名这个 skill 的情况。** 主 agent 负责拆分、派活、汇总和交付,不得自己代替 subagent 做调研。

调研要读大量文档和源码。这些原文留在调用方的上下文里,会挤掉它正在做的事——一场访谈、一次拆分。隔离出去,调用方拿到的是浓缩后的答案,原文留在笔记里,需要时再翻。用户直接调用也遵循这条规则:他看到的是主 agent 汇总后的结论和笔记,而不是把检索过程塞进主上下文。

## 1. 先定规模

投入要匹配问题。凭感觉估会系统性地过度投入,所以按这张表来:

| 问题类型 | 并行 subagent | 每个的工具调用 |
|---|---|---|
| 单点查证(某个 API 行为、某个字段含义) | 1 个 | 3-10 |
| 对比几个方案 | 2-4 个,一个方案一个 | 各 10-15 |
| 摸清一整套协议或架构 | 4 个以上,按主题切分 | 各 15-25 |

单点问题也必须派 1 个 subagent,但不要为了形式再多派;给单点问题派一堆 subagent,是这类任务最常见的浪费。

先把问题写成一句话再动手。写不出一句话,说明还不知道要查什么,先问用户。

## 2. 派活要具体

每个 subagent 的任务描述必须包含四样,缺一样就会出现重复劳动或盲区:

- **目标** — 要回答的那个具体问题,不是主题
- **输出格式** — 回什么、多长、要不要带引证
- **来源指引** — 去哪查,优先哪类来源
- **边界** — 明确不查什么,避免和别的 subagent 撞车

反例:让三个 subagent 各自"调研 X 的权限模型"。它们会查同一批文件,得到三份高度重叠的报告。
正例:一个查协议定义,一个查参考实现的代码路径,一个查我们现在怎么做的。

subagent 把详细笔记写到文件,只回传结论和文件路径。把大段原文回传给主 agent,既烧 token 又会在转述中失真。

## 3. 先宽后窄

默认倾向是一上来就用又长又具体的查询,而这种查询往往什么都搜不到。

先用短而宽的查询探地形,看回来了什么,再逐步收窄。像人做研究一样:先知道有哪些东西,再钻进去。

## 4. 一手来源

**追到拥有这个事实的地方为止。** 官方文档、规范、源码、first-party API 响应,而不是别人对它们的转述。

第三方博客和教程可以用来**发现**线索,不能用来**支撑**结论。看到有用的说法,顺着它找到原始出处,引原始出处。

来源排序偏好要主动纠偏:权威但排名靠后的东西(规范原文、源码、学术 PDF、当事人的个人博客)通常比排在前面的内容农场更值得读。搜索排名不等于可信度。

查不到就说查不到。给一个来源不明的答案,比说"没查到"更糟,因为它会被当成事实用下去。

## 5. 把版本钉死

调研的是活的东西:代码会改,文档会更新,API 会变。不钉版本,结论过几周就无法复核,而且没人知道它是什么时候开始失效的。

- 源码:记下 commit SHA,引用用带 SHA 的 permalink 和行号范围
- 文档、规范:记下版本号或访问日期
- 包:记下版本号

笔记开头写明核验日期和钉住的版本,并说清为什么钉:避免后续变动混进结论。

## 6. 产出

**只产内容。** 调用方决定笔记存到哪、叫什么。没有调用方(用户直接点名你)时,看仓库里已有的调研笔记放在哪、长什么样,跟随已有约定;没有约定就放一个合理的位置并说明放在哪了。

### 固定的框

只有两件事是固定的:

- **结论在最前。** 读者要的是答案。编号列出,每条自足,不看后面也能读懂。不要铺垫
- **影响在最后。** 这些结论对本项目意味着什么:要改什么、不用改什么、什么被证伪了。不确定的地方在这里讲明,不要藏进结论

开头写核验日期和钉住的版本。

### 中间按题目自己长

中段不预设章节。**用题目自己的词命名**:「与本项目的映射」「逐项差距」「权限模型」「速查表」都比一个通用的「证据」更有信息量。

一份摸清整套协议的笔记会有十来个小节,一份单点核验可能只有一节。按需要来,不要凑数,也不要为了套模板把八个小节压成三个。

**每处主张紧跟它的来源。** 引证贴在被支撑的那段旁边,而不是攒到文末列一串。读者是在读到某一句时才想验证它的。

### 表格是主力,不是点缀

多方案对比、逐维差距、能力矩阵、时点与约束,这些用表格远比散文清楚。**维度做行,方案做列**,单元格里直接嵌带 SHA 的证据链接,读者当场就能跳过去核。

散文适合讲因果和取舍,表格适合让人扫。同一批事实要被逐项比较时,就用表。

### 图什么时候画

关系是图状的才画:调用链、状态迁移、跨进程的消息时序。这类东西用文字描述,读者得在脑子里重建一遍。

层级、清单、对比不要画图,表格更快、更好扫。

### 骨架

```markdown
# <问题的标题>

核验日期:<YYYY-MM-DD>。<钉住的版本/SHA,以及为什么钉。>

## 结论

1. <直接回答问题。自足。>
2. <...>

<按题目命名的中间章节,数量随主题而定,主张紧跟来源>

## 对本项目的影响

<要改什么、不用改什么、什么被证伪了。不确定的也写在这里。>
```

## 完成标准

每一条结论都能指到笔记里某一处具体引证。指不到的,要么去补证据,要么把它从结论降级成「待验证」并写明。

一个没参与调研的人,只读这份笔记就能判断结论是否成立,不需要重新查一遍。
