# 用 GitHub issue 和 PR 做调研

GitHub issue 适合补充“实际发生过什么”和“维护者怎么回应”。它不能替代文档、规范、源码或 release，也不能把几条评论变成用户统计。

## 什么时候查

只在以下情况查：

- 用户直接给出 issue 或 PR 链接
- 官方文档没有回答真实故障、边界或回归问题
- 要确认维护者是否承认某个行为、是否计划修复、修复是否已经发布
- 比较方案时，需要了解具体版本中曾经出现过的限制

不要为了“看看社区怎么说”而无边界地搜索。先写出要回答的一句话，例如“v3.2 的流式响应在代理下断开，维护者是否确认、修复是否已发布？”

## 怎么查

1. 用户给了链接时，先读 issue/PR 本体、完整评论和关联 PR；不要只看标题或首条评论。
2. 没有链接时，先限定仓库，再用库名、错误文本、行为词和受影响版本搜索。一次搜索没有结果时，缩短查询，不要把同义词全部塞进去。
3. 对每条准备引用的讨论，记录：仓库和编号、打开/关闭日期、当前状态、涉及版本、说话的人、关联 PR/release，以及链接。
4. 关闭的 issue 要查清关闭原因：重复、无法复现、不会修、已有修复或已发布，含义完全不同。
5. 如果结论依赖维护者说法，确认这条回复来自能代表项目的人；无法确认身份时，只写“账号 X 回复”，不要擅自称为维护者。

GitHub 连接器可用时：先搜索 issue，再读取选中的 issue 和完整评论；需要确认修复时，再读取关联 PR、合并提交和 release。没有连接器时，可用 GitHub 网页或 API，但仍按同样的证据标准记录。

## 证据强度

| 类型 | 可以怎么写 | 不能怎么写 |
|---|---|---|
| 已合并的修复 PR + release | “该问题在 v2.4.1 的修复中处理。” | “现在所有版本都不会再出现。” |
| 维护者明确回复 | “维护者在 #123 说明当前不支持该用法。” | “GitHub 社区认为不支持。” |
| 有环境和复现步骤的 issue | “有人在 Node 22、v3.2.0 下复现了这个错误。” | “v3.2.0 一定有这个错误。” |
| 普通用户评论或表情反应 | “该讨论收到 34 个 👍，说明它值得关注。” | “34 个 👍 代表 34 个受影响用户。” |
| 已关闭但没有修复证据的 issue | “#123 已关闭，原因是重复/无法复现/不处理。” | “#123 已修复。” |

表情反应、重复 issue 和评论数量只反映公开讨论的活跃度，不能表示发生率、市场份额或用户满意度。

## Markdown 写法

在结论附近直接说清 GitHub 讨论承担的角色：

```markdown
维护者在 [owner/repo#123](https://github.com/owner/repo/issues/123) 回复，当前版本不支持在 worker runtime 中使用该接口（2026-08-12）。这说明的是维护者立场；实际支持范围仍以当前文档和 release 为准。

有人在 Node 22 + v3.2.0 下复现连接中断，并附上最小复现（[owner/repo#456](https://github.com/owner/repo/issues/456)）。这是一个具体案例，尚不足以判断发生率。
```

问题包含多条 issue 时，用表格，按“讨论说明了什么”组织，不按 issue 编号堆列表：

| 讨论 | 说明了什么 | 状态和版本 | 证据强度 |
|---|---|---|---|
| [#123](https://github.com/owner/repo/issues/123) | 维护者确认限制 | closed · 2026-08-12 | 维护者确认 |
| [#456](https://github.com/owner/repo/issues/456) | 一个可复现案例 | open · v3.2.0 | 可复现案例 |
```

## HTML 写法

在报告的来源区把 issue/PR 标成结构化来源：

```html
<li id="source-gh-123" data-source-kind="github-issue"
    data-github-repo="owner/repo" data-github-number="123"
    data-github-state="closed">
  <p class="font-medium">[GH-123] 维护者确认的限制</p>
  <a href="https://github.com/owner/repo/issues/123">owner/repo#123</a>
  <p>closed · 2026-08-12 · 影响版本：v3.2.0</p>
</li>
```

结论卡片继续用 `data-source-ids="gh-123"` 指向它。运行 `check_report.py`；它会检查仓库名、编号、状态和链接是否一致。
