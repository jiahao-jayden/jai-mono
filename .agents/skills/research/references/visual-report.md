# 可视化调研报告

HTML 报告帮助读者更快看懂复杂关系，不负责替代证据笔记。先完成 Markdown，再从已经核验的内容中挑出值得可视化的部分。

## 选什么形式

| 调研重点 | 首选形式 | 不要这样做 |
|---|---|---|
| 服务、模块、参与方之间如何连接 | 内嵌 SVG 关系图 | 给每个实现细节各画一个框 |
| 请求、事件或状态按顺序怎么走 | 内嵌 SVG 流程图或时间线 | 用一条带很多折线的箭头塞完所有分支 |
| 版本、发布或决策如何变化 | HTML 时间线 | 只有两件事也强行画时间线 |
| 多个方案按同一组条件比较 | HTML 表格 | 把定性信息伪装成精确的雷达图 |
| GitHub issue 的处理过程或多条 issue 的结论 | 时间线或证据表 | 把表情反应画成“用户满意度” |
| 哪条结论由哪些来源支撑 | 结论旁的来源编号和来源列表 | 把来源堆在页尾，不让人知道它支撑什么 |

如果一张三列表格就能说清，不画图。图表现的是关系、顺序或层级；表表现的是逐项比较；段落解释因果和取舍。

## 内容和层级

报告默认顺序：

1. 标题、问题、核验日期和范围
2. 直接结论，通常 2–5 条
3. 一张主图或一张对比表
4. 这张图说明什么，以及它没有覆盖什么
5. 对本项目的影响和仍未确认的事
6. 来源

每条结论用 `data-claim-id` 标识，并用 `data-source-ids` 列出支撑它的来源 ID。来源条目使用 `id="source-<id>"`。这样读者不需要猜一条链接支撑了哪句话。

GitHub issue 或 PR 做来源时，在来源条目上补 `data-source-kind="github-issue"` 或 `data-source-kind="github-pr"`，以及 `data-github-repo="owner/repo"`、`data-github-number="123"` 和 `data-github-state="open|closed|merged"`。运行检查脚本会检查这些字段和链接是否对得上。

## 图的规则

- 只保留读者需要区分的节点和关系。两个节点总是一起出现时合并。
- 默认一张主图不超过 9 个节点、12 条关系。超过时拆成概览和细节，或改表格。
- 用中性颜色表达普通元素，用一个强调色指出读者首先该看的节点或路径。不要给每个节点上色。
- 箭头应当表达方向或因果；没有信息的线删掉。标签不能压在线上。
- SVG 的每个图都有 `<title>` 和 `<desc>`。颜色、虚线和形状需要有文字说明。
- 不用 Mermaid。报告是交付物，布局和标签需要由内容决定。

## Tailwind CDN

模板通过 `https://cdn.tailwindcss.com` 加载 Tailwind。这是为了快速获得一致的排版、响应式网格和可读的表格，不需要构建步骤。

这也意味着报告打开时需要联网。交付时要说明这一点；如果用户需要离线报告，改用内嵌 CSS，而不是假装 CDN 报告可以离线打开。

## 图表的来源

图里的每个节点、关系、日期、数值和结论，都必须能回到 Markdown 中已经核验的内容。来源链接优先指向一手资料，并在报告中同时放一个回到同名 Markdown 笔记的链接。

不要把还没查实的推断画成事实。尚未确认的内容单独列出，使用“待确认”而不是模糊的颜色暗示。

## GitHub issue 在报告里怎么写

只有实际用了 GitHub issue 或 PR 时，才加“GitHub 讨论”一节。它通常是表格，不需要硬画图：

| 讨论 | 能确认什么 | 当前状态和版本 | 证据强度 |
|---|---|---|---|
| `owner/repo#123` | <维护者已确认的说法，或具体案例> | <open/closed、日期、受影响版本> | <维护者确认 / 可复现案例 / 用户反馈> |

如果一个问题经历了报告、确认、修复、发布四个以上关键节点，可以画时间线。每个节点写 issue 或 PR 编号和日期；不要把“关闭”画成“修复完成”，除非有合并的修复和相应 release 作为证据。
