# 可视化调研报告

HTML 报告给所有人看，包括不写代码的人。它分两层：上层用人话解释，下层把 Markdown 的全部证据原样折叠进去。先完成 Markdown 并通过 `check_note.py`，再写 HTML。

顺序不能反：先有经过核验的 Markdown，再有解释层。解释层只是换一种说法讲同一件事，不能带进 Markdown 里没有的结论。

## 读者是谁

想象三个人同时打开这份报告：

- 一个后端工程师，想知道机制，会展开证据层核对
- 一个产品经理，想知道这东西解决什么问题、对我们的计划有什么影响，不会展开证据
- 一个刚入行的人，连标题里的词都不一定认识

解释层写给第三个人，证据层写给第一个人，「对本项目的影响」写给第二个人。三个人都能从头读到尾不卡住，这份报告才算合格。

## 解释层怎么写

每个章节（结论卡片、中段的每一节、影响）都按同一个顺序：

1. **一句话说清是什么。** 用 `data-plain` 标记这段。不带任何术语，或者带的术语在这句话里就解释掉
2. **一个日常生活的类比。** 记账本、餐厅点单、快递签收、装修施工单，这类所有人都经历过的事。类比旁边写清它在哪里失效，因为类比一定有不准的地方
3. **再展开。** 这时可以引入术语，第一次出现用 `<dfn>` 标出并链到术语表。先说这个东西为什么存在，再说它怎么运作
4. **这对读者意味着什么。** 具体到本项目：要改什么、不用改什么、要小心什么

一段技术主张改成解释层的例子：

Markdown 里的原句：

> reconciler 只处理日志里还没有同 key 结果的 transition；进程重启就重读日志，状态和待办都能重建。

解释层写法：

> **一句话：** 程序把每件发生过的事记在一个只能往后加、不能改的本子上，重启后靠重读本子恢复到崩溃前的状态。
>
> **类比：** 像餐厅的点单本。服务员每接一单就写一行，厨房只做本子上还没打勾的单。就算换了一个厨师，他翻一遍本子就知道哪些菜还没做。这个类比在一处不准：餐厅的厨师做完会打勾，而这里"打勾"本身也是往本子上加一行，永远不擦掉旧的。
>
> **展开：** 这个本子叫<dfn>事件日志</dfn>，本子上"还没打勾的单"叫<dfn>待办转换</dfn>（transition）。负责翻本子、找出没做完的事去做的模块叫<dfn>调和器</dfn>（reconciler）……
>
> **对我们：** JAI 已经有同样的本子（journal）。要学的不是本子，是"每件能自动继续的事都要能从本子上推出来"这条纪律。

判断标准：找一个不做这行的人，让他读解释层，问他"这东西是什么、有什么用"。他能用自己的话复述，就合格。

## 术语表

页尾固定一节术语表（`data-report-section="glossary"`，用 `<dl>`）。正文里每个 `<dfn>` 的词都在这里有一条，一句人话定义，可以再跟一句它在本报告里为什么重要。

`check_report.py` 会核对每个 `<dfn>` 都能在术语表的 `<dt>` 里找到。反过来不要求：术语表里可以多几个读者可能会碰到的词。

术语表的定义写法和解释层一样：不能用另一个术语解释这个术语。「幂等：多次执行和执行一次效果相同」不合格，因为读者不知道"效果相同"指什么；「幂等：同一张快递单扫两次，包裹还是只签收一次，这种性质叫幂等」合格。

## 证据层怎么放

从 Markdown 到 HTML 是**逐节搬运**，不是挑选。每个章节的解释层下面放一个 `<details>`，`<summary>` 写「证据与原文」，里面是该章节在 Markdown 里的全部内容：

| Markdown 里的东西 | HTML 里变成 | 不要这样做 |
|---|---|---|
| 开头的核验日期和钉住的版本 | `<header>` 里的元信息行 | 省略 SHA |
| `## 结论` 的编号列表 | 一条一张卡片，每张带 `data-claim-id`、`data-source-ids`、一段 `data-plain`，卡片上显示来源徽标 | 挑 3 到 5 条"最重要的"，其余丢掉 |
| 中段的每个 `##` / `###` | 一个 `<section>`，`<h2>` / `<h3>` 文字与 Markdown 一致；解释层在上，`<details>` 证据在下 | 把几个章节合并成一段综述 |
| 段落里的链接 | `<a>` 保留原 href | 把链接去掉只留文字 |
| 代码摘录 | `<pre><code>` 块，第一行保留 `path:L起-止 @ sha` 注释 | 把代码改写成一句话 |
| 引用摘录 | `<blockquote>` | 同上 |
| 表格 | `<table>`，单元格里的链接保留，列数一致；表格前用一句人话说明这张表回答什么问题 | 把 6 行压成 3 行，或把单元格里的链接去掉 |
| `## 来源覆盖` | 单独一节，表格原样搬，前面一句话解释"这张表告诉你我们查了哪些地方、没查哪些地方" | 省略 |
| `## 对本项目的影响` | `data-report-section="impact"`，保留子标题和列表，每个子标题下先一句人话 | 压成一段话 |
| 「待验证」「不应照搬」这类清单 | `data-report-section="unknowns"` 或对应的 callout，保留清单形式 | 压成一段话 |
| 所有出现过的链接 | 页尾 `data-report-section="sources"` 列表，每个来源一个 `id="source-<id>"` | 只列 5 到 6 个 |

搬完之后 `check_report.py --note` 会对照 Markdown 检查章节标题、表格数、链接集合、摘录数和结论数，少了就 FAIL。

## 图放在哪、画什么

图放进它解释的那个章节里，紧跟解释层的段落，用 `<figure>` 包住，带 `<figcaption>` 用人话说明它回答什么问题、覆盖什么、没覆盖什么。

图上的标签是给所有人看的。节点上写「点单本」「厨房」「还没做的单」，不写 `EventLog`、`reconciler`、`pending transition`。代码标识符可以放在 figcaption 或证据层里。

| 章节在讲什么 | 首选形式 | 不要这样做 |
|---|---|---|
| 服务、模块、参与方之间如何连接 | 内嵌 SVG 关系图 | 给每个实现细节各画一个框 |
| 请求、事件或状态按顺序怎么走 | 内嵌 SVG 流程图或泳道时序图 | 用一条带很多折线的箭头塞完所有分支 |
| 具体走一遍的 trace | 编号的步骤列表，每步一句人话 + 可折叠的代码位置；步骤超过 5 个再配一张泳道图 | 只画抽象循环，不落到具体步骤 |
| 版本、发布或决策如何变化 | HTML 时间线 | 只有两件事也强行画时间线 |
| 多个方案按同一组条件比较 | HTML 表格，前面一句话说这张表回答什么 | 把定性信息伪装成精确的雷达图 |
| GitHub issue 的处理过程或多条 issue 的结论 | 时间线或证据表 | 把表情反应画成"用户满意度" |

一张图回答一个问题。一份机制类报告通常会有两到三张：一张整体关系，一张走一遍的步骤，可能再一张出问题时的分支。它们分别属于不同章节，不要合并成一张大图。

如果一张三列表格就能说清，不画图。

## 图的规则

- 只保留读者需要区分的节点和关系。两个节点总是一起出现时合并。
- 一张图不超过 9 个节点、12 条关系。超过时拆成概览和细节。
- 用中性颜色表达普通元素，用一个强调色指出读者首先该看的节点或路径，用一个警示色标出未知或危险的边界。不要给每个节点上色。
- 箭头应当表达方向或因果；没有信息的线删掉。标签不能压在线上。
- SVG 的每个图都有 `<title>` 和 `<desc>`。颜色、虚线和形状需要有文字说明。
- 不用 Mermaid。报告是交付物，布局和标签需要由内容决定。

## 页面结构

模板已经定好了骨架，按它填：

1. `<header>`：标题、**一句人话的总回答**（`data-plain`）、核验日期、钉住的版本、范围、回 Markdown 的链接
2. 左侧粘性目录（`<nav>`），列出所有 `<h2>`，大屏显示，小屏折叠到顶部
3. 结论卡片区：每张卡片 = 人话一句 + 展开一段 + 成立条件 + 来源徽标
4. 中段各节，按 Markdown 顺序：解释层四步 → 图（如有）→ `<details>` 证据
5. 来源覆盖表，前面一句话解释它是什么
6. 影响：子标题保留，每个子标题下先一句人话
7. 待验证 / 不应照搬：清单
8. 术语表
9. 来源列表

每条结论用 `data-claim-id` 标识，并用 `data-source-ids` 列出支撑它的来源 ID。来源条目使用 `id="source-<id>"`。卡片上把来源 ID 显示成徽标并链接到对应条目。

GitHub issue 或 PR 做来源时，在来源条目上补 `data-source-kind="github-issue"` 或 `data-source-kind="github-pr"`，以及 `data-github-repo="owner/repo"`、`data-github-number="123"` 和 `data-github-state="open|closed|merged"`。检查脚本会核对这些字段和链接是否对得上。

## Tailwind CDN

模板通过 `https://cdn.tailwindcss.com` 加载 Tailwind。这是为了快速获得一致的排版、响应式网格和可读的表格，不需要构建步骤。模板另有一小段内嵌 CSS 管代码块、引用块、`<details>` 和打印样式，因为 Tailwind 的 preflight 会把它们抹平。

这也意味着报告打开时需要联网。交付时要说明这一点；如果用户需要离线报告，改用内嵌 CSS，而不是假装 CDN 报告可以离线打开。

## 图表的来源

图里的每个节点、关系、日期、数值和结论，都必须能回到 Markdown 中已经核验的内容。来源链接优先指向一手资料，并在报告中同时放一个回到同名 Markdown 笔记的链接。

不要把还没查实的推断画成事实。尚未确认的内容单独列出，使用"待确认"而不是模糊的颜色暗示。

## GitHub issue 在报告里怎么写

只有实际用了 GitHub issue 或 PR 时，才加"GitHub 讨论"一节。它通常是表格，不需要硬画图：

| 讨论 | 能确认什么 | 当前状态和版本 | 证据强度 |
|---|---|---|---|
| `owner/repo#123` | <维护者已确认的说法，或具体案例> | <open/closed、日期、受影响版本> | <维护者确认 / 可复现案例 / 用户反馈> |

如果一个问题经历了报告、确认、修复、发布四个以上关键节点，可以画时间线。每个节点写 issue 或 PR 编号和日期；不要把"关闭"画成"修复完成"，除非有合并的修复和相应 release 作为证据。
