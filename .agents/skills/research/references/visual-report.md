# 把调研写成读者能用的 HTML

仅在用户明确要求 HTML 或网页报告时使用本指南。Markdown 保存完整核验过程，HTML 回答用户的问题。两者不要求相同标题、顺序、章节数量或篇幅。先完成笔记核验，再组织 HTML。

## 先决定这页要回答什么

从用户的问题和背景确定读者，不默认所有人都懂代码，也不默认所有人都需要入门课。用户没有说明时，面向了解业务目标、但不熟悉被调研技术的项目协作者。

写页面前先列出：

- 用户要解决的问题，以及读完后应能做出的判断。
- 最重要的答案及成立条件；哪些反证会改变这个答案。
- 一个来自笔记的实际场景，能让读者跟着看懂过程。

按这些内容安排阅读顺序。没有具体材料时明确说明，不编造案例、数字、引述或测试结果。推演示例须标明是说明机制的例子，不冒充实测。

## 内容怎样取舍

开头用一段话直接回答问题，不用大段背景、术语定义或结论卡片墙。主要结论可以合并，保留它们的条件、限制与相反证据；省略的只应是不会改变判断的细节。

接着解释答案为什么成立：机制问题走一遍实际输入到结果的过程；对比问题按用户关心的条件比较；可行性问题分清实际跑通、代码推断和未验证部分。每节标题说清这一节回答的问题，不照搬笔记目录。

结尾给出对当前项目的具体建议和代价，分清现在该做、无需改动和仍需验证。没有足够证据就写暂时无法判断，不为了网页完整而强行推荐。

完整源码、全部引用、来源覆盖表和检索记录留在 Markdown。HTML 只引用支撑所选结论的来源；短摘录确实能解释关键差异时才放入局部 details。禁止把整份 Markdown 隐藏进折叠区充当可读性改造。

## 用实际例子解释

例如，笔记证明“日志恢复可重建待办，但外部副作用不一定能自动去重”。HTML 应解释：

> 一个任务先保存进度，再发送通知。程序在通知已发出、发送结果尚未保存时崩溃。重启后虽然知道任务进行到哪一步，却可能再次发送通知。因此，有恢复日志不等于通知只发一次；还需要接收方识别重复请求，或人工核实发送结果。

随后链接到笔记中的依据。如果笔记未核实这条机制，不能直接采用这个例子作为结论。

不把数据库、队列、执行器全部改叫“本子”“厨房”“服务员”。图和正文都用真实对象，第一次出现时就地解释；否则读者要在类比和系统之间再翻译一次。类比是可选工具，不能每节强加。术语表仅在确有多个需要反复查阅的词时添加；使用 `<dfn>` 标记的词须在术语表定义。

## 图表怎么帮忙

先写明图要回答的问题，再决定是否画。步骤列表或表格已经清楚时不加装饰图。

| 问题 | 表达方式 |
|---|---|
| 一个请求经过谁，数据放在哪 | 关系图或时序图，标真实角色和数据方向 |
| 重启、失败、重试会发生什么 | 带关键分支的流程或状态图 |
| 哪个方案适合当前约束 | 对比表，列出证据、限制和选择理由 |
| 版本和修复状态如何变化 | 有日期及来源的时间线 |

图必须与正文解释同一个场景；读者能跟随起点、动作、分支和结果。复杂关系拆成概览与局部细节，避免字体缩小、箭头交叉或只有模块名而没有动作。每图附标题和说明，SVG 带 `role="img"`、`aria-labelledby`、`title` 和 `desc`，不能只靠颜色传递状态。

## 页面与来源约定

使用模板的内嵌 CSS，可以按内容改布局；无需 Tailwind CDN、构建系统或外部字体。优先单列阅读，长内容提供目录。表格允许局部横向滚动，正文不能因长链接撑破窄屏。

- header 包含标题、直接回答（`data-plain`）、核验日期、范围和完整笔记链接（`data-note-link`）。
- 保留 `conclusions`、`impact`、`unknowns`、`sources` 四个 `data-report-section`，标题可按问题命名。没有未知项时如实说明，不制造风险凑数。
- 主要结论元素标 `data-claim-id`，用 `data-source-ids` 指向实际来源；段落带 `data-plain` 表示它负责解释，但属性本身不证明通俗。
- 来源条目用 `id="source-<id>"`，保留笔记里该来源的原链接、版本或访问日期。不是所有笔记链接都要复制。
- GitHub 来源仍遵循 [`github-issues.md`](github-issues.md) 的状态和证据强度约定。

`check_report.py --note` 检查报告引用的来源是否来自笔记，不校验“来源是否证明结论”，也不能检查是否遗漏了关键反证。这两点必须人工核对。

## 交付前检查

先不看源码、来源列表和折叠区，只读主文，检查能否回答：

1. 用户问的问题，答案是什么，什么条件下不成立？
2. 实际例子里谁先做什么，失败后发生什么，最后得到什么？
3. 对当前项目建议什么，为什么，代价是什么？

答不出来就重写对应段落。尤其检查是否只是给原文加标题、卡片或“对我们意味着”一行套话。

再对照 Markdown 检查数字、术语、条件、反证及未验证状态；用 renhua 可改善中文表述，但不能替代这一步事实检查。

运行结构检查，然后在桌面与窄屏实际打开页面，检查目录锚点、图中文字、表格滚动和阅读顺序。模板提示必须全部替换或删除。没做预览时报告这个限制，不声称视觉验收通过。
