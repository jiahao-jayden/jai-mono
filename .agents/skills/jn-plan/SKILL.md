把一份意图,变成一份计划和一组能一个个做完的 spec。

**只产内容。** 调用方决定这些文档存到哪。

调用方应当给你:意图内容、项目约定文件的内容、词汇表。缺哪样就问它要,别自己猜。

验证命令**现查现填**:读受影响子包的 `package.json` scripts,或用项目约定文件里记录的命令。某个包没有 test 脚本就只列类型检查并注明——编一条跑不通的命令,下游的验证门禁就静默失效了。

## 1. 摸现状

按意图的影响范围读代码:已有实现在哪、接口什么样、测试怎么写的。

## 2. 摘硬约束

从项目约定文件里摘出**本次真正触及**的条目。

这是整件事的重点。规则写在约定文件里但 agent 照犯,不是因为规则不存在,而是因为动手那一刻它不在上下文里。摘进计划和 spec,它才会跟着走到实现现场。

- **只摘本次会碰的。** 改 UI 就摘组件规则;动持久化就摘事实归属和投影方向。全文复制等于没摘——什么都重要就等于什么都不重要
- **原文摘录,不要转述。** 转述会软化约束
- **标出处**,方便回查

## 3. 拆 spec

一个 spec = 一个可独立验证的**纵向**单元:

- 端到端跑通一件事,不是某一层的横切
- 单独可验证(能跑类型检查和测试,或能演示)
- 装得进一个干净的上下文窗口
- prefactor 排最前

依赖写成 `阻塞于`。

**小需求**(拆下来 1-2 个单元):不出 spec 文档,把内容压进 todo 的行里。小改动走全套仪式,用户下次就会跳过整个流程。

## 4. 先确认再产出

**把拆分方案给用户看**,编号列表,每条含:标题 / 阻塞于 / 交付什么。问三件事:

- 粒度对吗(太粗还是太细)
- 阻塞关系对吗,每个 spec 是否只依赖真正卡住它的
- 有没有该合并或该再拆的

同时**自己回答另外三个问题**,答案进 plan 的「风险」和「没选的路」:

- 这个改动可能弄坏什么?
- 哪一步最危险?
- 有哪些方案我认真考虑过但没选,为什么?

第三个问题最容易跳过,也最值得写。没记下来的否决理由,过两周会被原样重新提一遍。

改到用户认可再产出正式文档。拆错了,要么每个 spec 都跑不完,要么改一处牵动一片。

## 5. 产出

### 计划

```markdown
# Plan: <标题>

来源:intent · 日期:<YYYY-MM-DD>

## 背景
<为什么现在做。现状什么样。>

## 方案
<整体怎么做。关键技术选择及理由。>

## 没选的路
<认真考虑过但否掉的方案,每条一句为什么否。没有非显然的备选就写「无」。>

## 风险
<会改变实现方式的约束和未知数:限流、并发、数据量、外部依赖的不确定行为。>
<每条写清它逼着实现做什么。例:claims-core API 限流 50 rps,面板必须做缓存。>

## 硬约束
<从项目约定文件原文摘录,带出处。>

## 验收计划
| workspace | 命令 |
|---|---|
| <包名> | <现查到的类型检查 + 测试命令;无 test 则注明> |

## Spec 拆分理由
<为什么这么拆。哪些是纵向切片,哪些是 prefactor。>
```

### todo 索引

```markdown
# Todo: <标题>

进度:0/N

| # | 状态 | Spec | 阻塞于 | gist |
|---|---|---|---|---|
| 01 | ⬜ | <标题> | - | <一句:交付什么> |
| 02 | ⬜ | <标题> | 01 | <一句> |

⬜ 未开始 · 🔄 进行中 · ✅ 完成 · ⏸ 挂起

## 未决问题
<跨 spec 的。单个 spec 内部的写在那份 spec 里。>
```

每行只留一句 gist。详情在 spec 里——索引一旦开始存内容,读它的成本就和读全部 spec 一样高。

### 每个 spec

「动手前」和「验收」两段是门禁,**必须原样带上**。它们写在 spec 里而不是某个 skill 里,是因为 spec 一定会被读,skill 只在被想起时才加载:

```markdown
# <NN>: <标题>

阻塞于:<编号|无> · 状态:⬜

## 交付什么
<从用户角度,做完什么能用了。别写成分层实现清单。>

## 动手前(门禁)
先在对话里列出下面三项,列不出来说明 spec 没读够或本身没写清,回去读或补 spec,不要边猜边写:
- 本次触及的 durable fact 及其 owner
- 本次适用的硬约束(见下)
- 不碰什么(上一个 spec 的「停在哪」+ 本 spec 边界外的)

## 触及的 durable fact
<持久事实及 owner。没碰就写「无」。>

## 硬约束
<从计划里挑出本 spec 相关的那几条,原文。>

## 风险
<从计划的「风险」里挑出落在本 spec 头上的那几条。没有就写「无」。>

## 验收(门禁)
未跑完并贴出真实输出,不得标 ✅:
- [ ] <可检查的条件>
- [ ] <类型检查命令>
- [ ] <测试命令,无则写「无 test 脚本」>
- [ ] <本次触及的领域若有专项自查规则,列在这里>

## 决策记录
<!-- 随做随写 -->

## 遗留问题
<!-- 发现但本次不做的 -->

## 停在哪
<!-- 完成或挂起时填:停在哪、下一刀不许碰什么。写给下一个 session 看,要具体 -->
```

不写具体文件路径和代码片段,过期太快。例外:原型产出的、比散文更精确编码了某个决策的片段(状态机、reducer、schema、类型形状),只摘决策相关的部分。

## 完成标准

每个 spec 都能让一个没参与规划的人单独领走做完,不用回来问"这条算不算我的范围"。做不到的那个,是拆得不对。
