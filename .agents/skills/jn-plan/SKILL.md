把一份意图,变成一份计划和一组能一个个做完的 spec。

**只产内容。** 调用方决定这些文档存到哪。

调用方应当给你:意图内容、项目约定文件的内容、词汇表。缺哪样就问它要,别自己猜。

验证命令**现查现填**:读受影响子包的 `package.json` scripts,或用项目约定文件里记录的命令。某个包没有 test 脚本就只列类型检查并注明。编一条跑不通的命令,下游的验证门禁就静默失效了。

## 工件边界

一条信息只在一个层级拥有真相,否则 plan 和 spec 会互相复述、又可能悄悄矛盾。

| 工件 | 拥有什么 | 不写什么 |
|---|---|---|
| intent.md | 问题、目标、影响范围、边界 | 技术路线和逐项实施方式 |
| plan.md | 跨 spec 的整体方案、已确认技术决策、完整硬约束/风险、验证基线、拆分和依赖理由，以及整套计划的评审状态 | 某一个 spec 的具体改动清单、逐项验收条件、局部代码组织 |
| spec | 一个纵向交付的范围、行为契约、适用的约束/风险、验收与本刀决策 | 重做整项技术选型，或重复整个特性的背景和方案 |
| todo.md | spec 状态、依赖和一句 gist | 计划评审状态、设计细节、决策理由和验收记录 |

plan 里的「硬约束」「风险」是特性范围内的完整集合;spec 只摘本刀实际适用的项，目的是让实现时不必来回翻 plan。它们是**受控副本，不是第二个真相源**：改计划中的任一条时，同一次改动必须同步更新受影响的 spec。

## 1. 摸现状

按意图的影响范围读代码:已有实现在哪、接口什么样、测试怎么写的。

## 2. 摘硬约束

从项目约定文件里摘出**本次真正触及**的条目。

这是整件事的重点。规则写在约定文件里但 agent 照犯,不是因为规则不存在,而是因为动手那一刻它不在上下文里。摘进计划和 spec,它才会跟着走到实现现场。

- **只摘本次会碰的。** 改 UI 就摘组件规则;动持久化就摘事实归属和投影方向。全文复制等于没摘,什么都重要就等于什么都不重要
- **原文摘录,不要转述。** 转述会软化约束
- **标出处**,方便回查

## 3. 拷问关键技术决策

先读完现状、硬约束和意图,再判断哪些技术选择还需要用户拍板。**计划不是替用户把高代价方案静默定掉的地方。**

把技术问题分成三类:

- **既定事实** — 已有契约、项目规则、已部署的依赖或用户在意图里明确给出的约束。写入「既定前提」或「硬约束」,不重复问用户。
- **关键决策** — 会改变产品行为、数据兼容性、对外契约、成本、风险或后续扩展空间,且存在合理替代方案的选择。必须调用 Skill 工具传 `jn-grilling`,让用户确认后才能写入方案。
- **局部实现细节** — 文件如何拆、函数/类型如何命名、已有模式中的局部组织。这些不逐项拷问;由实现者决定,有非显然取舍时记入 spec 的「决策记录」。

通常属于关键决策的包括:

- durable fact 的模型、owner、迁移和向后兼容策略
- 对外 API、事件或用户交互契约
- 权限、安全、幂等、并发、一致性、失败与重试语义
- 会引入或替换基础设施/第三方依赖的选择
- 明显影响延迟、吞吐、配额或持续成本的方案

不要把清单当成问卷。只有同时满足「用户尚未决定」「至少有两条合理路径」「选错返工代价高」才提问。没有这类决策时,明确写「无须用户确认的关键技术决策」,然后继续拆 spec。

把 `jn-grilling` 的决策清单原样作为计划输入。计划中的「方案」和「已确认的技术决策」必须与它一致;后续发现新关键决策时,暂停实现,回到拷问而不是自行假设。

## 4. 拆 spec

一个 spec = 一个可独立验证的**纵向**单元:

- 端到端跑通一件事,不是某一层的横切
- 单独可验证(能跑类型检查和测试,或能演示)
- 装得进一个干净的上下文窗口
- prefactor 排最前

依赖写成 `阻塞于`。

**小需求**(拆下来 1-2 个单元):不出 spec 文档,把内容压进 todo 的行里。小改动走全套仪式,用户下次就会跳过整个流程。

## 5. 完成后评审计划包

**先完成计划包，再请用户 review；不要只展示拆分提纲就停下。** 小需求的计划包是 `plan.md + todo.md`;大需求还包括全部 specs。用户需要 review 的是将来实际执行的工件，不是对工件的口头预告。

关键技术决策已经在上一步单独确认;这里不要借评审拆分之名重新问一遍。若完成计划包时发现它依赖一个未决的关键技术选择,先回到上一步。

同时**自己回答另外三个问题**,答案进 plan 的「风险」和「没选的路」:

- 这个改动可能弄坏什么?
- 哪一步最危险?
- 有哪些方案我认真考虑过但没选,为什么?

第三个问题最容易跳过,也最值得写。没记下来的否决理由,过两周会被原样重新提一遍。

完成计划包后，给用户一份很短的 review 导览：spec 标题 / 阻塞于 / 交付什么，并请他从**已落盘的完整工件**判断三件事:

- 粒度对吗(太粗还是太细)
- 阻塞关系对吗,每个 spec 是否只依赖真正卡住它的
- 有没有该合并、删掉或再拆的

整套计划只有一个评审状态，**唯一写在 `plan.md`**：初始为 `⏳ 待用户评审`。这不是逐个确认 spec：所有 specs 准备好后，用户只需 review 整包并确认一次。

评审未通过前，只能修改计划包本身，不能创建或修改生产代码、不能把 spec 标为 🔄。用户提出调整时，修订受影响的 plan / todo / specs，保持 `⏳ 待用户评审`，再请他 review 整包。

用户明确确认“计划和拆分”后，调用方只将 `plan.md` 的状态改为 `✅ 已确认 · 可执行`，并在同一处记录确认日期。**确认计划只解除执行门禁，不等于立刻开始实现。** 调用方汇报可执行的第一个 spec 后停下，等用户另行说开始/继续；用户若要同一轮开始，必须明确说“确认并开始 <spec>”。

## 6. 产出

### 计划

```markdown
# Plan: <标题>

来源:intent · 日期:<YYYY-MM-DD> · 状态:⏳ 待用户评审

评审对象:<小需求:plan.md + todo.md | 大需求:plan.md + todo.md + 全部 specs>
执行门禁:状态改为 `✅ 已确认 · 可执行` 前，不得开始实现或修改生产代码。

## 背景
<为什么现在做。现状什么样。>

## 方案
<只写跨 spec 的整体路线、组件/数据/调用之间的关系，以及已经确认的关键技术选择及理由。不要在这里列每个 spec 的文件改动或局部步骤。>

## 已确认的技术决策
<来自 jn-grilling 的决策清单。没有需要用户确认的选择时,写「无」。>

## 没选的路
<认真考虑过但否掉的方案,每条一句为什么否。没有非显然的备选就写「无」。>

## 风险
<会改变实现方式的约束和未知数:限流、并发、数据量、外部依赖的不确定行为。>
<每条写清它逼着实现做什么。例:claims-core API 限流 50 rps,面板必须做缓存。>

## 硬约束
<从项目约定文件原文摘录,带出处。>

## 验证基线
| workspace | 命令 |
|---|---|
| <包名> | <现查到的类型检查 + 测试命令;无 test 则注明> |

<这是特性会用到的命令清单;每个 spec 的「验收」只列本刀要实际跑的命令和可观察结果。>

## Spec 拆分理由
<为什么这么拆。哪些是纵向切片,哪些是 prefactor。>
```

### todo 索引

```markdown
# Todo: <标题>

进度:0/N

| # | 状态 | Spec | 阻塞于 | gist |
|---|---|---|---|---|
| 01 | ⬜ | <标题> | - | <一句:交付什么> |
| 02 | ⬜ | <标题> | 01 | <一句> |

⬜ 未开始(计划待评审时不可执行) · 🔄 进行中 · ✅ 完成 · ⏸ 挂起

## 未决问题
<跨 spec 的。单个 spec 内部的写在那份 spec 里。>
```

每行只留一句 gist。详情在 spec 里。索引一旦开始存内容,读它的成本就和读全部 spec 一样高。

### 每个 spec

「动手前」和「验收」两段是门禁,**必须原样带上**。它们写在 spec 里而不是某个 skill 里,是因为 spec 一定会被读,skill 只在被想起时才加载:

```markdown
# <NN>: <标题>

阻塞于:<编号|无> · 状态:⬜

## 交付什么
<从用户角度,做完什么能用了。别写成分层实现清单。>

## 范围
做:
- <本 spec 负责的可观察行为和必要改动。>

不做:
- <明确留给其他 spec 或计划外的内容。>

## 已继承的计划决策
<只列本 spec 必须遵守的 plan.md 决策，并链接到对应小节。这里不重新比较方案;需要推翻时回到计划确认。>

## 动手前(门禁)
先在对话里列出下面三项,列不出来说明 spec 没读够或本身没写清,回去读或补 spec,不要边猜边写:
- 本次触及的 durable fact 及其 owner
- 本次适用的硬约束(见下)
- 不碰什么(上一个 spec 的「停在哪」+ 本 spec 边界外的)

## 触及的 durable fact
<持久事实及 owner。没碰就写「无」。>

## 硬约束
<从计划里挑出本 spec 相关的那几条,原文。>

## 风险
<从计划的「风险」里挑出落在本 spec 头上的那几条。没有就写「无」。>

## 验收(门禁)
未跑完并贴出真实输出,不得标 ✅:
- [ ] <可检查的条件>
- [ ] <类型检查命令>
- [ ] <测试命令,无则写「无 test 脚本」>
- [ ] <本次触及的领域若有专项自查规则,列在这里>

## 决策记录
<!-- 只记录本刀实施中出现的局部、非显然选择;改变跨 spec 方案时回到 plan.md。-->

## 遗留问题
<!-- 发现但本次不做的 -->

## 停在哪
<!-- 完成或挂起时填:停在哪、下一刀不许碰什么。写给下一个 session 看,要具体 -->
```

不写具体文件路径和代码片段,过期太快。例外:原型产出的、比散文更精确编码了某个决策的片段(状态机、reducer、schema、类型形状),只摘决策相关的部分。

## 完成标准

每个 spec 都能让一个没参与规划的人单独领走做完,不用回来问"这条算不算我的范围"。做不到的那个,是拆得不对。
