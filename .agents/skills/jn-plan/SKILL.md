description: "把范围已经说清的需求拆成计划和一组可独立检查的工作项（spec），并从项目约定中找出这次必须遵守的规则。Use when an intent is settled enough to plan, or when asked to plan, split, or re-split specs for a feature."
---

把需求说明拆成整体计划和可以分别完成、分别检查的工作项（spec）。调用方负责保存文件。写给用户看的导览、问题和状态，优先用自然语言；文件名和 `spec` 只是方便定位的名字。

输入：需求说明、项目约定、词汇表。缺少其中任何一项时让调用方补充，不要猜。验证命令现查受影响包的 scripts；没有测试脚本就列类型检查并注明。编出一条不能运行的命令，后面的完成检查会变成摆设。

## 工件边界

每条信息只放在一个地方，避免计划和工作项各写一份，后来悄悄不一致。

| 文件 | 写什么 | 不写什么 |
|---|---|---|
| intent.md | 问题、目标、影响范围、边界 | 技术路线和逐项实施方式 |
| plan.md | 整体做法、已确认的关键选择、完整的项目规则和风险、验证命令、为什么这样拆分，以及整套计划是否已确认 | 某一项工作的具体改动清单、逐项检查条件、局部代码组织 |
| spec | 一项能从头到尾交付的工作、用户和外部调用方能看到的行为、适用的规则/风险、完成前检查和本项决定 | 重新做整项技术选型，或重复整个需求的背景和方案 |
| todo.md | 每项工作的状态、先后关系和一句摘要 | 计划是否确认、设计细节、决定理由和检查记录 |

`plan.md` 的「必须遵守的项目规则」「风险」写完整；每份 spec 只摘与它有关的部分，实施时就不用来回翻整份计划。计划修改后，同步更新受影响的 spec。

## 1. 摸现状

按意图的影响范围读代码:已有实现在哪、接口什么样、测试怎么写的。

## 2. 找出必须遵守的项目规则

从项目约定文件里找出**这次真的会碰到**的条目。

- 只摘本次会碰的条目。整份复制进来等于没有重点。
- 原文摘录并标出处，避免转述时把要求说轻了。

## 3. 先把需要想清的事查一遍，再问用户要选的事

读完现状、项目规则和需求后，检查下面六类。每一类都写结论和依据，让用户能看出哪些已经确定、哪些还要选择。

| 维度 | 扫什么 |
|---|---|
| 长期保存的数据与兼容 | 数据由哪个模块维护、是否需要迁移、旧数据/配置还能不能用、旧路径什么时候删除 |
| 外部产品或规范的约定 | 协议、产品或库的一手来源；是完全遵循、参考行为还是只借鉴思路；哪些地方允许不同 |
| 用户和调用方看到的行为 | API、事件、用户交互、命名和默认值 |
| 权限与安全 | 信任边界、权限、敏感数据与失败语义 |
| 运行环境和依赖 | 基础设施、第三方依赖、打包、平台、成本与性能 |
| 同时操作和失败重试 | 并发操作会不会互相影响、重复请求能否安全处理、重试顺序和日志是否足够排查问题 |

外部参考先查一手资料。跟随程度不清楚、且会影响行为或成本时，列为需要用户决定的事。把检查结果写进「需要先想清的事」，来源和允许不同的地方写进「外部产品或规范的约定」。

分类:

- **已经确定的事**: 现有接口约定、项目规则、已部署的依赖和用户明确要求。写进现状或项目规则。
- **需要用户选择的事**: 会改变行为、兼容性、对外约定、成本、风险或以后扩展方式，而且确实有合理替代方案。交给 `jn-grilling`。
- **实现细节**: 文件、函数、类型和局部组织。不是显而易见的取舍，写进对应 spec 的「决策记录」。

只在用户还没决定、确实有至少两条路、而且选错后返工代价高时提问。没有要问的事，就在检查表里写“无需用户决定”和依据。把 `jn-grilling` 的决定清单原样写进计划；实施时发现会影响整套方案的新选择，回到这里。

## 4. 拆成工作项

一份 spec 是一项能从头到尾检查、一个人拿到后能独立完成的工作：应该能跑检查或演示结果，也不能大到需要反复补上下文。需要先做的准备工作放在前面；在工作清单里写清“要先完成哪一项”。只有 1–2 项工作的小需求直接写进 `todo.md`。

## 5. 请用户查看并确认整套计划

先把整套计划写完，再请用户查看。小需求给出 `intent.md + plan.md + todo.md`；大需求再加全部 specs。这一次确认同时覆盖范围、和外部产品或规范的约定、工作拆分和后续实施。还有需要用户选择的事，就回到上一步。

在「风险」和「没选的路」里回答：

- 这个改动可能弄坏什么?
- 哪一步最危险?
- 有哪些方案我认真考虑过但没选,为什么?

给用户一份简短导览：每项工作的标题、必须等待的前置工作和交付内容。请用户检查：

- 粒度对吗(太粗还是太细)
- 前后顺序对吗，每项工作是否只等待真正需要先完成的工作
- 有没有该合并、删掉或再拆的

是否确认只写在 `plan.md`，初始为 `⏳ 等待确认`。用户确认前只改计划文件。用户提出调整时，更新受影响的 plan/todo/specs 后，再请用户查看。

计划展示后，“确认”“开始”“继续”等都表示用户确认整套计划并启动。将状态改为 `✅ 已确认 · 可执行`，记录日期，然后连续完成能开始的工作。用户明确说稍后开始时，只更新状态。

## 6. 产出

### 计划

```markdown
# 计划: <标题>

来源:需求说明 · 日期:<YYYY-MM-DD> · 状态:⏳ 等待确认

请确认这些文件:<小需求:intent.md + plan.md + todo.md | 大需求:intent.md + plan.md + todo.md + 全部 specs>
开始条件:状态改为 `✅ 已确认 · 可执行` 前，只完善计划文件，不开始实现或修改正式代码。

## 背景
<为什么现在做。现状什么样。>

## 方案
<跨多项工作的整体做法和已确认的关键选择。>

## 外部产品或规范的约定
<一手来源、要跟得多像、哪些地方可以不同。无则写「无」。>

## 需要先想清的事
| 维度 | 结论 | 依据 |
|---|---|---|
| 长期保存的数据与兼容 | <已经确定 / 无需用户决定 / 已确认选择> | <来源或为什么没有合理替代> |

| 用户和调用方看到的行为 | <同上> | <同上> |

| 运行环境和依赖 | <同上> | <同上> |
| 同时操作和失败重试 | <同上> | <同上> |

## 已确认的关键选择

## 没选的路

## 风险
<会改变实现方式的约束和未知数。>

<从项目约定文件原文摘录,带出处。>

## 要运行的检查
| workspace | 命令 |
|---|---|
| <包名> | <现查到的类型检查 + 测试命令;无 test 则注明> |

## 为什么这样拆分
<为什么这样安排每项工作及其先后顺序。>
```

### todo 索引

```markdown
# 工作清单: <标题>

进度:0/N

| # | 状态 | 工作项 | 要先完成 | 一句摘要 |
|---|---|---|---|---|
| 01 | ⬜ | <标题> | - | <一句:交付什么> |
| 02 | ⬜ | <标题> | 01 | <一句> |

⬜ 未开始（等待计划确认时不能开始） · 🔄 进行中 · ✅ 完成 · ⏸ 暂停

## 未决问题
<跨多项工作的。只属于某一项的问题写在对应 spec 里。>
```

每行只留一句摘要，详情写在 spec 里。工作清单如果塞进太多内容，读起来就和把所有 spec 都读一遍一样慢。

### 每个工作项（spec）

「开始前确认」和「完成前检查」两段**必须原样带上**。它们写在 spec 里，是因为做这项工作时一定会读 spec；skill 只有被想起时才会加载。

```markdown
# <NN>: <标题>

要先完成:<编号|无> · 状态:⬜

## 交付什么
<从用户角度,做完什么能用了。别写成分层实现清单。>

## 范围
做:
- <本项负责的、用户或调用方能看到的行为和必要改动。>

不做:
- <明确留给其他工作项或计划外的内容。>

## 需要遵守的整体选择
<只列本项必须遵守的 plan.md 选择，并链接到对应小节。这里不重新比较方案；要推翻时回到计划确认。>

## 开始前确认
先在对话里说清下面三项。说不清说明 spec 没读够，或 spec 本身没写清；回去读或补 spec，不要边猜边写：
- 本次会改到哪些长期保存的数据，以及哪个模块维护它们
- 本次必须遵守哪些项目规则（见下）
- 这次不碰什么（上一个 spec 的「交接说明」和本项范围外的内容）

## 长期保存的数据与维护方
<会长期保存、之后仍会被读取的数据，以及哪个模块维护它们。没碰就写「无」。>

## 必须遵守的项目规则
<从计划里挑出本项相关的那几条，保留原文。>

## 风险
<从计划的「风险」里挑出会影响本项的那几条。没有就写「无」。>

## 完成前检查
下面的检查没有跑完、也没有贴出真实输出前，不能标 ✅：
- [ ] <可检查的条件>
- [ ] <类型检查命令>
- [ ] <测试命令,无则写「无 test 脚本」>
- [ ] <本次触及的领域若有专项自查规则,列在这里>

## 决策记录
<!-- 只记录这项工作实施时出现的局部、非显然选择；改变整套方案时回到 plan.md。-->

## 遗留问题
<!-- 发现但本次不做的 -->

## 交接说明
<!-- 完成或暂停时填：做到哪里、下一项不要碰什么。写给下次继续工作的人看，要具体。 -->
```

不写具体文件路径和代码片段,过期太快。例外:原型产出的、比散文更精确编码了某个决策的片段(状态机、reducer、schema、类型形状),只摘决策相关的部分。

## 完成标准

每个 spec 都应该让一个没参与规划的人拿到后独立做完，不用回来问“这项算不算我的范围”。做不到，说明拆分还不对。
