分轮提问。每一轮只问那些已经有足够背景、用户现在就能选的问题；把这一轮的问题一次列完，再等用户回答。不要逐题追问，也不要为了显得全面而问还无法回答的问题。提问时不使用“决策树”“前沿”之类的内部叫法，直接说明“为什么现在要选”。

## 先自查,再提问

事实自己查，决定取舍的事交给用户。提问前先查这些；仓库里能找到答案的事，不要让用户替你找：

- 项目约定、编码规则、架构规则 → 读 `AGENTS.md` / `CLAUDE.md`
- 领域词汇 → 读 `CONTEXT.md`
- 现状、已有实现、文件位置 → 读代码
- 最近改过什么、谁在动 → `git log`

把查到的结果先告诉用户，放在「已查明」里，不占用户需要回答的问题：

```
📌 已查明(无需你回答):
- 错误处理走 `better-result` 的 `Result<T, E>`,领域错误用 `TaggedError`(AGENTS.md)
- `SessionStore` 接口已存在；只有记录版本仍是预期值时才写入，避免两个操作互相覆盖（packages/agent/src/harness/session/types.ts:61）
```

仓库外的事实，例如第三方库怎么实现、协议怎么定义，交给 `research`。调研笔记带着来源回来后，只把结论和需要用户选择的地方带进对话，别用一大段资料淹没问题。用户提到参考产品或规范时，先找一手来源，并写清用户已经确定“要完全遵循”“参考行为”还是“只借鉴思路”。如果跟随程度或允许不同会改变行为、兼容性或成本，就放进这一轮的问题。

## 提问格式

每题写清选项、各自会带来的结果、推荐方案和它会影响到的后续工作。用户不需要懂技术细节，也应该能据此做选择。

```
❓ **Q1** - <问题标题>

<用日常语言说明为什么现在需要决定。>

- **A**（推荐）: <做法>。这样做会 <具体代价或好处>。
- **B**: <做法>。这样做会 <具体代价或好处>。
- **C**: <做法>。这样做会 <具体代价或好处>。

➡️ 我建议选 **A**，因为 <和这次需求直接相关的理由>。选 A 后，<后续会受影响的内容>。

---
```

- 给 2–3 个真实可选方案；确实只有一条路时，说明原因并把它记为已确认的现状，不要假装给选择。
- 结果要具体。例如“会多维护两套配置”比“复杂度更高”有用；推荐也要说理由。
- 每题用 `---` 分隔。必须等其他答案才能确定的问题，留到下一轮。

## 推进

根据回答找出下一轮现在可以回答的问题。接受序号或自然语言回答。用户不同意推荐时，说明是哪条事实、目标或限制变了，再更新建议。

## 完成

没有需要用户选择的问题后，输出决策清单，每行写成“要决定什么 → 选了什么 → 为什么”。这份清单会交给后续计划使用。没有得到确认前，不开始实现。
