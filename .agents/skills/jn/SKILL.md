JN 用父记录保存 RFC 格式的 PRD，用子任务记录管理任务和依赖。流程是 **Grill → PRD → 子任务 → Implement → Review**，一项任务也走同一条路。tracker 可配置为 GitHub 或本地文件，GitHub 不可用时回退本地。

`research` 可以独立调用，也可以在任一阶段按需调用。调研后返回调用阶段；单独调研不自动进入 JN。

## 职责和依赖

- `jn-grilling` 澄清场景、边界和取舍。
- `jn-intent` 生成带图的 RFC 格式 PRD，必须使用 `renhua` 的项目文档模式。
- `jn-plan` 从 PRD 生成任务正文和依赖。
- JN 负责定位、在授权范围内发布、记录确认、调度实施及 Review。

调用前读取对应 skill；有 skill 调用工具就使用，没有则读取其 `SKILL.md` 并按规则执行。不要假设某个工具一定存在。必需 skill 不可用时说明缺少什么，保留草稿，不声称完成该阶段。只有需要外部查证时才要求 `research` 可用。

不创建 PR、stack、worktree、项目看板或分支管理机制，不自动 commit、push、切分支。不维护 tracker 之外的 intent/plan/todo/spec 或第二套进度；`.jnative/task/index.md` 和 `history.md` 只保存导航元数据，不是另一套状态。

## Tracker 配置

`.jnative/issue-tracker.md` 是可选配置，由用户显式运行 `jn-setup` 创建或修改；普通 JN 不调用 setup、不创建配置。配置存在时按配置执行；不存在时使用内置默认值：GitHub remote 明确且可访问则用 GitHub，否则用本地，fallback 固定为本地。配置为 GitHub 时从 remote 确定仓库，多个合理目标时询问；配置为本地时使用 `.jnative/task/`。具体格式、回退和迁移规则见 [Tracker 操作约定](references/issues.md)。

同一需求只使用一个正式 tracker。已有父记录决定该需求继续写 GitHub 还是本地，不能因暂时失败同时维护两份；切换已有需求必须由用户明确要求迁移。

## 定位和读取

接受 GitHub 父/子 Issue 的链接、编号，或 `.jnative/task/` 下的父需求、任务路径。GitHub 编号必须绑定明确的仓库。不得把当前 skills 仓库当成所有需求的目标。

未指定任务时先读 `.jnative/task/index.md`，缺失、用户要求刷新或条目与 tracker 冲突时再从配置的 tracker 列父需求元数据并刷新视图。只有一个合理候选就用它，多个候选列标题、进度和最近活动供用户选择；不要把所有打开记录都当成 JN 任务。只有用户查询历史或旧需求匹配时才读 `history.md`；新需求进入澄清。

GitHub 以 `jn:prd`、`jn:task` 查找，本地以 frontmatter 的 `jn_type` 查找；历史无标签记录仍按正文和父子关系定位，不因缺标签创建重复需求。读父 PRD、确认记录、全部子任务、依赖和执行记录。用户指定子任务时回读它的父 PRD。tracker 状态优先于聊天里的旧进度，但本会话明确的新决定也要回写，不能因记录滞后重复索要授权。

| 当前情况 | 下一步 |
|---|---|
| 新想法或目标不清 | 调用 `jn-grilling`，事实自己查，重要取舍问用户 |
| 目标已清楚、PRD 未完成 | 调用 `jn-intent`，补全 RFC、图示和 renhua 编辑 |
| PRD 完成、任务未拆齐 | 调用 `jn-plan` |
| PRD 和任务已展示、尚未确认 | 处理反馈或已有确认，不实施代码 |
| 已确认、有可执行任务 | 读取 [执行与 Review](references/execution.md)，连续推进 |
| 子任务都已处理、父需求未验收 | 按执行规则做整体 Review |
| 父需求已验收关闭 | 汇报结果；新要求先判断是修复还是范围变化 |

只读查看关闭的记录不会重开它。用户要继续修复或调整时，再在相应授权范围内重开或补任务。

## 内容、发布与确认

项目规则从 `AGENTS.md` / `CLAUDE.md` 等实际约定读取，术语表存在才读；文件不存在不阻止推进。只摘与需求相关的规则。已有词汇表不复制，只有项目特有词确有歧义时更新定义。

PRD 和子任务草稿先写完整。图示或 renhua 编辑未完成时可继续准备不依赖这些检查的任务草稿，但不能进入整体接受或实施；已有用户授权不等于这些检查已通过。父记录使用 `jn-intent` 的 RFC 模板，子任务使用 `jn-plan` 的任务模板。独立调用这些阶段 skill 时默认只交付内容；通过 JN 入口推进且已有对应授权时，JN 负责发布或更新 tracker。

发布、更新或关闭 tracker 记录前确认现有用户授权涵盖该动作。用户明确要求开始、继续、跟进或管理一项需求时，视为授权 JN 创建或更新对应的父需求和子任务；已授权就继续，不每次询问。仅要求调研、草稿或发布文档不等于授权实施代码。GitHub 在任何对象创建前确认不可用时按操作约定回退本地；远端结果有歧义时先恢复，不创建第二份本地记录。

发布和重试时读取 [Tracker 操作约定](references/issues.md)。它定义 GitHub 标签、本地 frontmatter、父子关系、依赖、状态、轻量视图、按日期归档、部分失败恢复和迁移。

完整 PRD 和任务拆分展示后，用户的“确认”“开始”“继续”可以覆盖整套实施；语境仅表示继续讨论时不能当作实施授权。JN 生成完整父 PRD 后，默认创建或更新父记录；任务拆分完成后，默认创建或更新子任务、补齐父子关系和依赖。用户仅要求草稿时不发布。确认写在父 PRD 的「JN 确认记录」中。默认用户为负责人；明确列有多位 RFC 负责人时收齐他们的确认，不替任何人签字。

确认跨会话有效。只有目标、范围、外部行为或重大风险改变时，更新相关 PRD、图示和任务，重新应用 `renhua`，再确认变化。普通实现细节写任务记录，不重走审批。用户已明确授权本次变化时记录该授权即可。

## Research 与本地资料

独立调用 `research` 不需要仓库 Issue、PRD 或 JN 确认。JN 的澄清、PRD、拆分、实施和 Review 均可调用它，完成后只带回结论、证据和笔记位置。

JN 调研使用 `.jnative/research/<area>/<topic>.md`，复用语义相同的主题目录；复用旧笔记前检查版本和适用性，不为每个 feature 复制研究。HTML 是否生成遵循 `research` 自身规则，不为 PRD 额外维护 HTML。

GitHub Issue 里优先引用可访问的仓库文档和一手来源。完整笔记仍在本地时，摘出支撑选择的结论和证据，注明完整笔记位置；不能只贴本机路径，也不能未经授权推送文件或公开敏感资料。本地 tracker 可直接使用相对路径引用笔记。

保留 `.jnative/CONTEXT.md` 和已有调研。旧需求文件不删除、不自动上传；仅在用户要求迁移时按 Tracker 操作约定处理。

## 汇报

先说明结果、原因和下一步，再给 GitHub 链接或本地路径。汇报完成、取消、执行中、阻塞各多少项；关闭但未计划完成的任务不能算作完成。详细输出留在任务执行记录，父需求的进度由子任务读取，不手工复制一张状态表。

只在用户要求停下、需要重要决定、没有可做任务或全部验收完成时结束连续执行。检查失败先修复，再决定是否阻塞该项。
