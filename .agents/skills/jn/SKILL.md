这是 `.jnative/` 的入口。它负责找到当前工作、保存文档、查验证命令，并把意图、计划和实施串起来；各阶段 skill 只负责生成自己的内容。

## 和用户怎么说

JN 的文件可以保留 `spec`、`todo.md` 这些名称，对话里先说清楚含义。第一次提到 Spec 时写成“第 N 项工作（Spec N）”，之后可简称“第 N 项”。

先说事实、原因和下一步，再给文件名或状态。不要把内部词直接当结论丢给用户：

| 不要只说 | 改成这样说 |
|---|---|
| “门禁没过” | “开始前还缺一项确认”或“完成前的检查还没有通过” |
| “Spec 被阻塞” | “第 2 项要等第 1 项完成后才能开始” |
| “计划待评审” | “计划已经写好，等你查看并确认后我就开始做” |
| “外部契约” | “和外部产品、协议或调用方约好的行为和数据格式” |
| “durable fact / owner” | “会长期保存的数据，以及由哪个模块负责维护” |
| “硬约束” | “这次必须遵守的项目规则” |
| “gist” | “一句摘要” |

状态汇报要能让不熟悉 JN 的人直接看懂。例如：

```text
第 1 项已经完成。第 2 项现在可以开始。
第 2 项暂时不能开始，因为第 1 项的测试还失败；我会先修复或说明这个失败。
计划已经写好。你回复“确认”“开始”或“继续”，我就按整套计划连续做下去。
```

## 目录约定

```
<repo>/.jnative/
├── CONTEXT.md                # 项目术语表,共识对齐用
├── research/                 # 调研笔记,跨特性共用
│   └── <topic>.md
├── archive/                  # 已归档的特性,定位时跳过
│   └── <slug>/
└── <slug>/                   # 一个特性,slug 短横线小写、取自意图、不带日期
    ├── intent.md
    ├── plan.md               # 整体方案、拆分理由和整套计划的确认状态
    ├── todo.md               # 工作清单，也是唯一的进度记录
    └── specs/NN-<slug>.md    # 每一项可独立完成的工作；小需求直接写在 todo.md
```

## CONTEXT.md

`.jnative/CONTEXT.md` 放项目特有术语，目的是让用户、当前会话和下次继续工作时都在说同一个东西。项目别处已经有词汇表时，只读，不复制也不回写；同一个词维护两份，很快会说法不一致。

### 什么词才配进来

只记项目特有、或在这里有特殊含义的词。超时、重试、缓存、工具函数等通用词不记。写之前问一句：不记下来，下次继续工作的人会不会理解错？不会就别加。

### 什么时候写

只在这些情况更新:

- 用户用的词和词汇表里的定义对不上
- 一个词身兼数职(「配置」既指用户设置又指运行时参数)
- 说法和代码矛盾

当场辨清并写入；其他时候不动。不要遇到新概念就加词，词汇表不是实现笔记。

### 格式

```markdown
# 术语

**<术语>**:
<一到两句定义。说清它「是什么」,不是「做什么」。>
_Avoid_: <该避免的同义词>
```

词多时按主题分组。不写实现细节。

## 验证命令

先从受影响包的 `package.json` scripts 或项目约定中查验证命令。monorepo 只跑本项工作触及的 workspace；没有测试脚本时，至少跑类型检查，并把这个事实写进“完成前检查”。不要凭空写一条命令，跑不起来的检查等于没有检查。

## 调研

仓库外的事实，例如第三方库怎么实现、协议怎么定义，交给 `research`。笔记放 `.jnative/research/<topic>.md`，`<topic>` 不带特性 slug，因为同一份调研可能被多个需求复用。已有笔记覆盖当前问题时直接引用，不要重复查一遍。

在需求说明的「已确认的现状」或计划的「方案」链接笔记。这样下次看到结论时，能知道它来自哪里，而不是重新猜一次：

```markdown
- Connector 的 Action 按 provider 定义的行为和数据格式生成([调研](../research/open-connector-actions.md))
```

## 归档

把 `<slug>/` 移到 `.jnative/archive/<slug>/`。归档只是把完成的需求移出当前视野，不是删除；必须同时满足：

1. `todo.md` 里**每一行都是 ✅**
2. **用户主动说要归档**

### 条件不满足时

有未完成项就列出状态和原因，不归档。别只说“不能归档”，用户需要知道是哪一项还没做完：

```
还不能归档，以下工作还没有完成：
- 第 03 项《<标题>》正在进行
- 第 05 项《<标题>》已暂停（原因：<原因>）
```

用户要放弃未完成项时，先把这个决定和状态写入 `todo.md`，再归档。

### 执行

1. 建 `.jnative/archive/`(不存在的话)
2. 把整个 `<slug>/` 目录移过去
3. 将 intent/plan 的调研链接从 `../research/` 改为 `../../research/`
4. 汇报归档到哪、动了几个文件

不移动 `CONTEXT.md` 或 `research/`，因为术语和调研会被其他需求继续使用。

## 定位

扫 `.jnative/*/`，跳过 `research/` 和 `archive/`。用户点名就用它；只有一个就用它；多个则按最近活动列进度并询问，不自己挑一个。归档需求要先问用户是只查看，还是恢复后继续做。

先读 `intent.md`、`plan.md` 的状态，再看其他文件。状态写着 `⏳ 等待确认`（旧文件可能写作 `⏳ 待用户评审`）时，不能只凭以前的聊天记录开始改正式代码。

| 现状 | 做 |
|---|---|
| 无 `.jnative/`,或用户描述了新需求 | **A. 意图** |
| 有 `intent.md`,无 `plan.md` | **B. 写计划** |
| plan.md 是 `⏳ 等待确认` 或旧的 `⏳ 待用户评审` | **B. 查看并确认计划**。只接受反馈、修改建议或确认 |
| plan.md 为 `✅ 已确认 · 可执行`,且有未完成行 | **C. 执行** |
| 全部 ✅ | 说完成 |

用户明确指定动作时照做。

## A. 意图

调用 Skill 工具,传 `jn-intent`。给它:项目约定文件(`AGENTS.md` / `CLAUDE.md`)和词汇表(`.jnative/CONTEXT.md`;项目别处另有词汇表就一并给,供它读)的内容。

它产出意图内容和这轮辨清的术语。你落盘:意图写 `.jnative/<slug>/intent.md`,新术语并入 `.jnative/CONTEXT.md`。

`.jnative/` 里已有同名 slug 时先问清楚:是补写那个特性,还是开新的。同名会覆盖掉已有工件。

意图不单独审批。除非用户说“这轮只定意图”，否则直接进入 B；`jn-grilling` 等待回答时停下。

## B. 计划

调用 Skill 工具,传 `jn-plan`。给它:

- intent.md 的内容
- 项目约定文件的内容（它要从里面找出这次必须遵守的规则）
- 词汇表（让每项工作的说法和项目现有用词一致）

它产出一套等待用户确认的计划，你立刻保存:

- `plan.md`
- `todo.md`
- `specs/NN-<slug>.md`,按依赖顺序编号,`01` 起
- 小需求(1-2 个单元)不建 `specs/`,内容直接进 todo.md 的行
- 这轮新辨清的术语并入 `.jnative/CONTEXT.md`

落盘后，`plan.md` 状态为 `⏳ 等待确认`。小需求请用户看 `intent.md + plan.md + todo.md`；大需求再加上全部 specs。用户确认前，不改正式代码。

计划展示后，“确认”“开始”“继续”“确认开始”“确认并开始”都表示整体确认并启动：将状态改为 `✅ 已确认 · 可执行 · 确认日期:<YYYY-MM-DD>`，然后进入 C。这一次确认覆盖整套计划，不在每项工作开始前或完成后重复确认。用户明确说“稍后开始”才只更新状态。

## C. 执行

### 汇报

检查 `plan.md`。计划已展示且用户这轮说了确认或开始执行时，按 B 更新状态；否则说“计划还没有确认”，并停下。没有展示过完整计划时，用户说“开始写”不算确认。

确认后先读 `todo.md`，需要细节再打开对应的 spec。

```
## <特性> — 已完成 <N/M> 项
接下来:第 <编号> 项《<标题>》<；需要等待哪一项时，把原因说完整>
正在做 / 暂停: <若有，说明原因>
还需要决定的事: <若有>
上一次留下的说明: <最近完成或暂停的 spec 的「交接说明」>
```

进度计数和状态列不一致时直接指出。

### 做

从第一个前置工作都已完成、且还没有开始的 spec 做起；用户指定某项时按用户指定。每项都读：该 spec 全文、`plan.md` 的「方案」「已确认的关键选择」「必须遵守的项目规则」，以及词汇表。验证命令按该项触及的 workspace 现查。

上一个 spec 的「交接说明」有内容时先读。开始前完成 spec 的「开始前确认」；完成前跑完「完成前检查」。

局部取舍写「决策记录」，本次不做的写「遗留问题」。会改变整套方案、已确认选择、工作顺序或范围时，先回 B 修改计划并让用户重新确认；不要悄悄改掉用户已经确认的内容。

### 回写

spec 写本项的决定、暂不处理的事、交接说明、检查输出和状态。`todo.md` 只写状态、一句摘要、进度和跨项的未决问题。

验证失败时，spec 保持 🔄，写下真实输出和原因。已有失败没有解决前，不能跳到后续依赖它的工作。

### 连续推进与停止

当前项通过完成前检查并标成 ✅ 后，马上继续下一项前置工作已完成的 spec。只在检查失败、没有可做的工作、计划需要修改、用户暂停或全部完成时停下。

## 各阶段单独可用

用户可以直接点名 `jn-intent` / `jn-plan` / `jn-grilling` 拿内容,那时产出留在对话里,不落盘。要落盘就走 `/jn`。
