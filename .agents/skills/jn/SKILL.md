JN 用父 Issue 保存 RFC 格式的 PRD，用子 Issues 管任务和依赖。流程是 **Grill → PRD → 子 Issues → Implement → Review**，一项任务也走同一条路。

`research` 可以独立调用，也可以在任一阶段按需调用。调研后返回调用阶段；单独调研不自动进入 JN。

## 职责和依赖

- `jn-grilling` 澄清场景、边界和取舍。
- `jn-intent` 生成带图的 RFC 格式 PRD，必须使用 `renhua` 的项目文档模式。
- `jn-plan` 从 PRD 生成任务正文和依赖。
- JN 负责定位、在授权范围内发布、记录确认、调度实施及 Review。

调用前读取对应 skill；有 skill 调用工具就使用，没有则读取其 `SKILL.md` 并按规则执行。不要假设某个工具一定存在。必需 skill 不可用时说明缺少什么，保留草稿，不声称完成该阶段。只有需要外部查证时才要求 `research` 可用。

不创建 PR、stack、worktree、项目看板或分支管理机制，不自动 commit、push、切分支。不维护本地 intent/plan/todo/spec 或第二套进度。

## 定位和读取

接受父或子 Issue 的链接、编号。编号必须绑定明确的仓库：先读当前仓库 remote，必要时查已连接仓库；存在多个合理目标时询问。不得把当前 skills 仓库当成所有需求的目标。

未指定任务时列当前仓库相关父 Issues。只有一个合理候选就用它，多个候选列标题、进度和最近活动供用户选择；不要把整个仓库所有 open Issues 当成 JN 任务。新需求进入澄清。

以 `jn:prd`、`jn:task` 查找需求与任务；历史无标签记录仍按正文和父子关系定位，不因缺标签创建重复需求。读父 PRD、确认记录、子 Issues、依赖和相关评论，分页读取完整任务集合。用户指定子 Issue 时回读它的父 PRD。读取状态优先于聊天里的旧进度，但本会话明确的新决定也要回写，不能因记录滞后重复索要授权。

| 当前情况 | 下一步 |
|---|---|
| 新想法或目标不清 | 调用 `jn-grilling`，事实自己查，重要取舍问用户 |
| 目标已清楚、PRD 未完成 | 调用 `jn-intent`，补全 RFC、图示和 renhua 编辑 |
| PRD 完成、任务未拆齐 | 调用 `jn-plan` |
| PRD 和任务已展示、尚未确认 | 处理反馈或已有确认，不实施代码 |
| 已确认、有可执行任务 | 读取 [执行与 Review](references/execution.md)，连续推进 |
| 子任务都已处理、父 Issue 未验收 | 按执行规则做整体 Review |
| 父 Issue 已验收关闭 | 汇报结果；新要求先判断是修复还是范围变化 |

只读查看关闭的 Issue 不会重开它。用户要继续修复或调整时，再在相应授权范围内重开或补任务。

## 内容、发布与确认

项目规则从 `AGENTS.md` / `CLAUDE.md` 等实际约定读取，术语表存在才读；文件不存在不阻止推进。只摘与需求相关的规则。已有词汇表不复制，只有项目特有词确有歧义时更新定义。

PRD 和子任务草稿先写完整。图示或 renhua 编辑未完成时可继续准备不依赖这些检查的任务草稿，但不能进入整体接受或实施；已有用户授权不等于这些检查已通过。父 Issue 使用 `jn-intent` 的 RFC 模板，子 Issue 使用 `jn-plan` 的任务模板。各阶段单独调用默认交付内容，不自动发布或实施。

发布、更新或关闭 GitHub Issues 前确认现有用户授权涵盖该动作。已经授权就继续，不每次询问。仅要求调研、草稿或发布文档不等于授权实施代码。没有 GitHub 访问能力时保留草稿，说明缺少连接或权限，不改用本地文件充当已同步的进度。

发布和重试时读取 [Issue 操作约定](references/issues.md)。它定义 JN 标签、父子关系、依赖、状态、部分失败恢复和迁移。打开的 Issue 恰好一个阶段 label，正文不重复存阶段；确认依据仍在父 PRD。

完整 PRD 和任务拆分展示后，用户的“确认”“开始”“继续”可以覆盖整套实施；语境仅表示继续讨论时不能当作实施授权。记录在父 Issue 的「JN 确认记录」：确认人、日期、覆盖的 PRD 与任务范围、确认依据，以及是否稍后开始。默认用户为负责人；明确列有多位 RFC 负责人时收齐他们的确认，不替任何人签字。

确认跨会话有效。只有目标、范围、外部行为或重大风险改变时，更新相关 PRD、图示和任务，重新应用 `renhua`，再确认变化。普通实现细节写任务记录，不重走审批。用户已明确授权本次变化时记录该授权即可。

## Research 与本地资料

独立调用 `research` 不需要仓库 Issue、PRD 或 JN 确认。JN 的澄清、PRD、拆分、实施和 Review 均可调用它，完成后只带回结论、证据和笔记位置。

JN 调研使用 `.jnative/research/<area>/<topic>.md`，复用语义相同的主题目录；复用旧笔记前检查版本和适用性，不为每个 feature 复制研究。HTML 是否生成遵循 `research` 自身规则，不为 PRD 额外维护 HTML。

Issue 里优先引用可访问的仓库文档和一手来源。完整笔记仍在本地时，摘出支撑选择的结论和证据，注明完整笔记位置；不能只贴本机路径，也不能未经授权推送文件或公开敏感资料。

保留 `.jnative/CONTEXT.md` 和已有调研。旧需求文件不删除、不自动上传；仅在用户要求迁移时按 Issue 操作约定处理。

## 汇报

先说明结果、原因和下一步，再给 Issue 链接。汇报完成、取消、执行中、阻塞各多少项；关闭但未计划完成的任务不能算作完成。详细输出留在任务评论，父 Issue 的进度由子任务读取，不手工复制一张状态表。

只在用户要求停下、需要重要决定、没有可做任务或全部验收完成时结束连续执行。检查失败先修复，再决定是否阻塞该项。
