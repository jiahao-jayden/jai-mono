`.jnative/` 流程的入口。**这里是唯一知道环境的地方**:目录约定、验证命令、哪个特性、产出落到哪,全在这份文件里。

被调用的阶段 skill 只产内容,不知道文件去哪。它们把内容给你,由你落盘。

## 目录约定

```
<repo>/.jnative/
├── CONTEXT.md                # 项目术语表,共识对齐用
├── research/                 # 调研笔记,跨特性共用
│   └── <topic>.md
├── archive/                  # 已归档的特性,定位时跳过
│   └── <slug>/
└── <slug>/                   # 一个特性,slug 短横线小写、取自意图、不带日期
    ├── intent.md
    ├── plan.md
    ├── todo.md               # 索引,唯一进度真相源
    └── specs/NN-<slug>.md    # 小需求不建此目录,直接在 todo.md 列行
```

## CONTEXT.md

各阶段共用的词汇表,`.jnative/CONTEXT.md` 是它唯一的位置。目的是让你、用户和下一个 session 说同一套话。同一个概念三种叫法,是重开 session 后误解的主要来源。

项目别处已有词汇表时,**读它,但不要往里写,也不要把它的词复制过来**。同一个术语只活在一个地方,复制出来的第二份一定会和第一份漂移。

### 什么词才配进来

一个词要进词汇表,先问:**它是这个项目特有的概念,还是通用编程概念?** 只有前者算数。

超时、重试、错误类型、缓存、工具函数这类词,项目里用得再多也不进。它们在任何项目里都是一个意思,不需要对齐。真正要记的是**只有这个项目才这么叫、或者这个项目赋予了特殊含义**的词。

写之前再问一遍:不记这条,下个 session 会不会因此误解?答案是否,就别记。这份文件更新得太勤,通常不是时机问题,是这道闸没关。

### 什么时候写

不是"遇到新概念就记",而是**词出问题的时候才记**:

- 用户用的词和词汇表里的定义对不上
- 一个词身兼数职(「配置」既指用户设置又指运行时参数)
- 说法和代码矛盾

这三种情况当场辨清、当场记下,不要攒到最后。攒到最后就只剩结论,丢掉了当时为什么要区分它。

除此之外不动这个文件。

### 格式

```markdown
# 术语

**<术语>**:
<一到两句定义。说清它「是什么」,不是「做什么」。>
_Avoid_: <该避免的同义词>
```

词多了按主题分二级标题;都属于一个领域时平铺即可。

不放实现细节。这是词汇表,不是规格书,也不是草稿本。

## 验证命令

不缓存。需要时现查:读子包 `package.json` 的 `scripts`,或用项目约定文件里记录的命令。

环境本身就是真相源,复述它只会过期。monorepo 的根目录常常没有聚合脚本,那就按 spec 触及的 workspace 逐个跑。某个包没有 test 脚本就只跑类型检查,并在验收里注明。**不要编一条跑不通的命令**,那会让验证门禁静默失效。

## 调研

事实落在仓库之外时(第三方库怎么实现、协议怎么定义、别的项目怎么解决同一问题),**派一个 subagent 去做,让它调用 Skill 工具传 `research`**,回来只要结论和笔记内容。把笔记落到 `.jnative/research/<topic>.md`。

隔离出去是因为调研要读大量文档和源码,那些原文留在流程的上下文里会挤掉正在做的事。

`<topic>` 按题目命名,不带特性 slug——调研跨特性复用,一份 ACP 协议的笔记不该绑死在某个特性下面。

**落盘后一定要从工件链回去。** 在 intent 的「既定前提」或 plan 的「方案」里,写明这条结论来自哪份笔记:

```markdown
- Connector 的 Action 契约按 provider 定义生成([调研](../research/open-connector-actions.md))
```

不链回去,这份调研就只在当时那次对话里起过作用。下一个 session 读 intent 时看到一条结论,不知道它是查证过的还是拍脑袋的,于是要么重查一遍,要么当成假设继续用。

已有笔记覆盖了当前问题就直接引用,不要重查。重查的成本不只是时间,还会得到一份和旧笔记结论不一致的新笔记。

## 归档

把一个特性目录整个移到 `.jnative/archive/<slug>/`,从定位视野里移出去。

**两个条件必须同时成立,缺一个都不动:**

1. `todo.md` 里**每一行都是 ✅**
2. **用户主动说要归档**

不要自己提议归档,也不要在特性做完时顺手归档。归档是把东西移出视野,该由用户决定什么时候不想再看见它。

### 条件不满足时

**还有未完成的行**:说清楚卡在哪,别归档。

```
还不能归档,以下 spec 未完成:
- 03 <标题> 🔄
- 05 <标题> ⏸(挂起原因:<原因>)
```

用户明确说"这些不做了、直接归档",那是他在改变 spec 的状态,不是在跳过条件。让他先决定这些 spec 是完成、放弃还是留着,状态落到 `todo.md` 上,再归档。

### 执行

1. 建 `.jnative/archive/`(不存在的话)
2. 把整个 `<slug>/` 目录移过去
3. **修相对链接的层级。** intent 和 plan 里指向调研的链接原本是 `../research/<topic>.md`,移深一层后要改成 `../../research/<topic>.md`,否则链接全断
4. 汇报归档到哪、动了几个文件

`CONTEXT.md` 和 `research/` 不动。术语和调研是跨特性的资产,不随某个特性退场。

归档后的目录保持原样可读,不压缩、不合并。归档是移出视野,不是销毁。

## 定位

先定特性:扫 `.jnative/*/`,**跳过 `research/` 和 `archive/`**,它们不是特性。用户点名了就用那个;只有一个就用它;多个则列出各自进度(`<特性> — N/M`,按最近活动排序)问推进哪个,别自己挑。

用户提到的特性在 `archive/` 里,说明它已归档,问他是要看归档内容还是移回来继续做。

再定阶段:

| 现状 | 做 |
|---|---|
| 无 `.jnative/`,或用户描述了新需求 | **A. 意图** |
| 有 `intent.md`,无 `plan.md` | **B. 计划** |
| 有 `todo.md` 且有未完成行 | **C. 执行** |
| 全部 ✅ | 说完成。不要提议归档,那是用户主动发起的动作 |

用户明确说了要干什么(「重新拆一下 spec」「先看看进度」「归档 X」),照他说的做,别机械走表。

## A. 意图

调用 Skill 工具,传 `jn-intent`。给它:项目约定文件(`AGENTS.md` / `CLAUDE.md`)和词汇表(`.jnative/CONTEXT.md`;项目别处另有词汇表就一并给,供它读)的内容。

它产出意图内容和这轮辨清的术语。你落盘:意图写 `.jnative/<slug>/intent.md`,新术语并入 `.jnative/CONTEXT.md`。

`.jnative/` 里已有同名 slug 时先问清楚:是补写那个特性,还是开新的。同名会覆盖掉已有工件。

**停下**,汇报路径、规模判断、还有什么没想清楚,等用户确认。确认后接着走 B,不用他再输命令。

## B. 计划

调用 Skill 工具,传 `jn-plan`。给它:

- intent.md 的内容
- 项目约定文件的内容(它要从里面摘硬约束)
- 词汇表(让 spec 的措辞和项目说同一套话)

它产出计划、todo 索引、spec 文档。你落盘:

- `plan.md`
- `todo.md`
- `specs/NN-<slug>.md`,按依赖顺序编号,`01` 起
- 小需求(1-2 个单元)不建 `specs/`,内容直接进 todo.md 的行
- 这轮新辨清的术语并入 `.jnative/CONTEXT.md`

它会先拷问并确认尚未决定的关键技术选择,再把拆分方案给用户确认,最后才产出正式内容。确认后接着走 C。

## C. 执行

### 汇报

读 `todo.md` 就够,**需要细节时才打开对应 spec**。todo.md 存在的意义就是省下把所有 spec 读一遍的开销。

```
## <特性> — <N/M>
下一个:<编号 标题>(阻塞已清)
进行中 / 挂起:<若有,附原因>
未决问题:<若有>
上一刀停在哪:<最近完成或挂起 spec 的「停在哪」>
```

进度计数和状态列对不上时如实指出,别静默修正。

### 做

取第一个**阻塞已全部完成**的未开始 spec(用户指定则用指定的)。读:该 spec 全文、`plan.md` 的硬约束段、词汇表。验证命令按 spec 触及的 workspace 现查。

**上一个 spec 的「停在哪」有内容就先读**,那里写着这一刀的禁区。接不上上一刀的状态,是重开 session 后最容易翻车的地方。

spec 文件里有「动手前」和「验收」两段门禁,照着做。门禁写在 spec 里而不是这份 skill 里,是因为 spec 一定会被读,skill 只在被想起时才加载。

实现期间:决策**随做随写**进 spec 的决策记录段(攒到最后就只剩结论、没有当时的权衡,而那正是日后回顾时想看的);发现但不解决的进遗留问题段;偏离了 spec 就改 spec,同一次提交里。

### 回写

spec 文件:决策记录、遗留问题、**停在哪**(停在哪、下一刀不许碰什么,写给下一个 session 看,要具体)、验收勾选、贴验证输出、状态 ✅。

`todo.md`:那行状态、gist(与实际交付不符就改)、进度计数、跨 spec 的未决问题。**只改索引**,详情留在 spec 里。索引一旦开始存内容,读它的成本就和读全部 spec 一样高。

验证没过,spec 保持 🔄,不标 ✅。标了 done 的东西没人会再回头看,这是唯一一次拦住它的机会。

### 停

汇报:完成了哪个、验证结果、下一个是哪个。然后停。

**不要连着做下一个。** 一个 session 一个 spec,上下文才干净。上一个 spec 的探索和死胡同会污染下一个的判断。
