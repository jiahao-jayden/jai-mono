`.jnative/` 流程的入口。**这里是唯一知道环境的地方**:目录约定、验证命令、哪个特性、产出落到哪,全在这份文件里。

被调用的阶段 skill 只产内容,不知道文件去哪。它们把内容给你,由你落盘。

## 目录约定

```
<repo>/.jnative/
├── CONTEXT.md                # 在做的特性引入的新术语,共识对齐用
└── <slug>/                   # 一个特性,slug 短横线小写、取自意图、不带日期
    ├── intent.md
    ├── plan.md
    ├── todo.md               # 索引,唯一进度真相源
    └── specs/NN-<slug>.md    # 小需求不建此目录,直接在 todo.md 列行
```

## CONTEXT.md

各阶段共用的词汇表。目的是让你、用户和下一个 session 说同一套话——同一个概念三种叫法,是重开 session 后误解的主要来源。

**项目已有词汇表(通常是仓库根的 `CONTEXT.md`)时,它是主。** 这里只装在做的特性**新引入**、还没进主词汇表的词。已在主词汇表里的引用即可,不要复制——复制出来的第二份一定会和第一份漂移。

术语定型后**毕业**:写进项目主词汇表,从这里删掉。这份文件应该始终很短。

格式跟随项目主词汇表。项目没有的话用这个:

```markdown
# 在做的术语

> 定型后毕业到 <项目主词汇表路径>,并从这里删除。

**<术语>**:
<一到两句定义。说清它「是什么」,不是「做什么」。>
_Avoid_: <该避免的同义词>
```

术语在什么时候写进来:拷问意图或拆 spec 的过程中,一个词被辨清了就当场记下,别攒到最后。攒到最后就只剩结论,丢掉了当时为什么要区分它。

不放实现细节。这是词汇表,不是规格书。

## 验证命令

不缓存。需要时现查:读子包 `package.json` 的 `scripts`,或用项目约定文件里记录的命令。

环境本身就是真相源,复述它只会过期。monorepo 的根目录常常没有聚合脚本,那就按 spec 触及的 workspace 逐个跑。某个包没有 test 脚本就只跑类型检查,并在验收里注明。**不要编一条跑不通的命令**,那会让验证门禁静默失效。

## 定位

先定特性:用户点名了就用那个;只有一个就用它;多个则列出各自进度(`<特性> — N/M`,按最近活动排序)问推进哪个,别自己挑。

再定阶段:

| 现状 | 做 |
|---|---|
| 无 `.jnative/`,或用户描述了新需求 | **A. 意图** |
| 有 `intent.md`,无 `plan.md` | **B. 计划** |
| 有 `todo.md` 且有未完成行 | **C. 执行** |
| 全部 ✅ | 说完成,问要不要开新的 |

用户明确说了要干什么(「重新拆一下 spec」「先看看进度」),照他说的做,别机械走表。

## A. 意图

调用 Skill 工具,传 `jn-intent`。给它:项目约定文件(`AGENTS.md` / `CLAUDE.md`)和词汇表(项目主 `CONTEXT.md` + `.jnative/CONTEXT.md`)的内容。

它产出意图内容和这轮辨清的术语。你落盘:意图写 `.jnative/<slug>/intent.md`,新术语并入 `.jnative/CONTEXT.md`。

`.jnative/` 里已有同名 slug 时先问清楚:是补写那个特性,还是开新的。同名会覆盖掉已有工件。

**停下**,汇报路径、规模判断、还有什么没想清楚,等用户确认。确认后接着走 B,不用他再输命令。

## B. 计划

调用 Skill 工具,传 `jn-plan`。给它:

- intent.md 的内容
- 项目约定文件的内容(它要从里面摘硬约束)
- 词汇表(让 spec 的措辞和项目说同一套话)

它产出计划、todo 索引、spec 文档。你落盘:

- `plan.md`
- `todo.md`
- `specs/NN-<slug>.md`,按依赖顺序编号,`01` 起
- 小需求(1-2 个单元)不建 `specs/`,内容直接进 todo.md 的行
- 这轮新辨清的术语并入 `.jnative/CONTEXT.md`

它会先把拆分方案给用户确认再产出正式内容。确认后接着走 C。

## C. 执行

### 汇报

读 `todo.md` 就够,**需要细节时才打开对应 spec**。todo.md 存在的意义就是省下把所有 spec 读一遍的开销。

```
## <特性> — <N/M>
下一个:<编号 标题>(阻塞已清)
进行中 / 挂起:<若有,附原因>
未决问题:<若有>
上一刀停在哪:<最近完成或挂起 spec 的「停在哪」>
```

进度计数和状态列对不上时如实指出,别静默修正。

### 做

取第一个**阻塞已全部完成**的未开始 spec(用户指定则用指定的)。读:该 spec 全文、`plan.md` 的硬约束段、词汇表。验证命令按 spec 触及的 workspace 现查。

**上一个 spec 的「停在哪」有内容就先读**——那里写着这一刀的禁区。接不上上一刀的状态,是重开 session 后最容易翻车的地方。

spec 文件里有「动手前」和「验收」两段门禁,照着做。门禁写在 spec 里而不是这份 skill 里,是因为 spec 一定会被读,skill 只在被想起时才加载。

实现期间:决策**随做随写**进 spec 的决策记录段(攒到最后就只剩结论、没有当时的权衡,而那正是日后回顾时想看的);发现但不解决的进遗留问题段;偏离了 spec 就改 spec,同一次提交里。

### 回写

spec 文件:决策记录、遗留问题、**停在哪**(停在哪、下一刀不许碰什么,写给下一个 session 看,要具体)、验收勾选、贴验证输出、状态 ✅。

`todo.md`:那行状态、gist(与实际交付不符就改)、进度计数、跨 spec 的未决问题。**只改索引**,详情留在 spec 里——索引一旦开始存内容,读它的成本就和读全部 spec 一样高。

验证没过,spec 保持 🔄,不标 ✅。标了 done 的东西没人会再回头看,这是唯一一次拦住它的机会。

### 停

汇报:完成了哪个、验证结果、下一个是哪个。然后停。

**不要连着做下一个。** 一个 session 一个 spec,上下文才干净——上一个 spec 的探索和死胡同会污染下一个的判断。

## 各阶段单独可用

用户可以直接点名 `jn-intent` / `jn-plan` / `jn-grilling` 拿内容,那时产出留在对话里,不落盘。要落盘就走 `/jn`。
