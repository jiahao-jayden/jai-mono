# Agent Transcript 渲染原则

日期：2026-08-06

## 背景

Coding agent 的 JSONL 是完整事件账本，不是最终 UI。当前模型经常产生：

```text
thinking -> 一句工具前说明 -> tool call
```

如果每个事件都按普通聊天消息渲染，就会出现“一行工具、一行话”的割裂节奏；如果为了视觉整洁把同一轮的工具全部提到前面，又会破坏真实执行顺序。

## 产品判断

Transcript 应分成三个信息层：

1. **对话层**：用户消息、重要决策、风险/阻塞说明和最终回答。
2. **工作轨迹层**：thinking summary、工具前叙述、工具调用、命令和结果。
3. **任务状态层**：Todo、当前任务、完成比例和 session 状态。

三层不能互相冒充：Todo 不等于 agent running，工作叙述不等于最终回答，未知事件不等于 compaction。

## 语义投影规则

Renderer DTO 必须显式表达事件语义，不能由组件根据文本猜测：

```text
assistant text + stopReason=toolUse -> WorkNarration
assistant text + stopReason=stop    -> AssistantReply
thinking / WorkNarration / ToolCall -> WorkProcess
explicit compaction event          -> CompactionNotice
unknown event kind                 -> Unsupported/debug item
```

`WorkNarration` 不是删除原始 assistant text，而是把它放入相邻工作组的次级层级。durable JSONL 始终保留完整内容。

## 顺序与分组

- 只合并相邻的 work items。
- `thinking -> narration -> tool -> tool` 可以形成一个 Work Process。
- 遇到用户消息、正式 assistant reply、权限请求、重要错误或系统 notice，立即关闭当前工作组。
- Work Process 展开后必须保持 JSONL 的原始顺序；不能为了聚合把后面的 command/edit 搬到前面。
- read/search/list 等连续低风险工具可以在组内压缩为摘要行；command、edit、失败和权限请求应保持更高可见度。

## 流式状态

每轮运行使用明确生命周期：

```text
idle -> working -> answering -> complete
```

进入 `answering` 后：

- 结束当前 Work Process；
- 停止旧 thinking 的 streaming 动画；
- 后续文本只能进入正式回答；
- 不用 `transcript_remove` 之类的补偿事件修复错误渲染。

Live projection 与 durable replay 应共享同一个 SessionProjection 状态机，保证实时显示和重载后的显示具有相同的 item 类型、顺序和分组。

## 默认视觉策略

- 最终回答使用普通聊天正文，是主视觉焦点。
- Work Process 默认紧凑/可折叠，展开后提供完整审计细节。
- 当前运行中只保留一个强活动焦点，避免多个 spinner、shimmer 同时跳动。
- command 成功时默认显示命令、exit code、短摘要；长输出折叠。
- command 失败、权限请求、阻塞状态自动提升并保持可见。
- 原始 thinking 默认弱化或折叠，只提供 summary；需要时再展开。
- 完成后将 `Working...` / `Thinking...` 收敛为过去式摘要或直接折叠，不把临时状态文案永久留在主线。

## Todo 与运行状态

- 只有收到明确 Todo snapshot/update 时才显示 Todo 面板。
- 面板标题应显示具体当前项或完成比例，不显示 `Agent is working`。
- session running 放在 session header、composer 或 stop 控件的外围状态中。
- Todo 状态更新是就地 snapshot/reducer 更新，不生成多条 transcript 消息。

## Prompt 边界

系统提示词可以要求模型不要为每个普通工具调用写例行说明，只在重要决策、风险、发现、阻塞或阶段切换时说明。但 Prompt 只负责降噪，不能承担 renderer 正确性的前提；模型继续产生短 narration 时，投影层仍必须正确归类。

## 实施顺序

1. 在 shared DTO 中增加 `DesktopNarrationItem`。
2. 让 live host 和 durable projector 使用同一套 assistant segment 分类。
3. 让 `WorkProcess` 消费 `thinking + narration + tool`，并将 narration 从顶层 ChatMessage 移除。
4. 在正式回答开始时关闭工作组 streaming 状态。
5. 增加 live/reload 等价性、顺序、失败和 Todo 状态测试。
6. 最后再调整 prompt、折叠默认值和视觉文案。

## 明确反模式

- 不通过删除 transcript item 来修 UI 顺序。
- 不把同一 user turn 内所有工具整体 hoist 到第一组。
- 不为每个工具调用额外请求模型生成 post-hoc 标题。
- 不把未知事件渲染成 `Context compacted`。
- 不把 Todo、Progress 和全局 agent 状态混成一个状态机。
