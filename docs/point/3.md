# 完成前验证：一次被否决的尝试

日期：2026-08-18（2026-08-19 更新：实现已移除）

## 结论先行

我实现了一个 `VerificationTracker`：跟踪「改过源文件但之后没跑过验证」，并在下一次 model call 前注入提醒。**它已被移除，且这个方向是错的。**

错的不是判定逻辑，是层次：**我把一条具体策略硬编码进了 runtime**。没有任何 agent 框架这样做——Claude Code 提供可阻断的 `Stop` hook 这个**机制**，但「你没验证就不许停」这条**策略**由用户自己写进 hook；OpenCode 和 pi 连机制都不给。「改完要不要验证」是用户对自己项目的判断，不是框架替所有人做的判断。

本文保留下来的价值在数据部分：它量化了「改完不验证」这个现象的规模，以及「自我报告不可信」这个更根本的问题。这些事实不会因为实现被否决而失效——将来若要解决，应该走 instructions 或用户可配置的 hook，而不是 runtime 内置状态机。

## 「有源文件修改，但没有出现成功的验证命令」是什么意思

这是一个对单次 run 的判定，口径如下：

- **源文件修改**：成功的 `Edit` / `Write` / `MultiEdit`，或写入源路径的 Bash（重定向、heredoc、`sed -i`、`patch` 等）。写入 `tmp`、`scratch` 等临时路径不算，`rm`、`git clean` 等清理命令也不算。
- **成功的验证命令**：`pytest` / `unittest` / `tox` / `tsc` / `mypy` / `npm test` 等，且**退出码为 0**。失败的测试不构成证据——它证明的恰好是相反的事。
- **判定时点**：看的是「最后一次修改之后」有没有验证，而不是「整个 run 里有没有跑过测试」。改 → 测 → 又改，最终状态仍是未验证。

判定为真，意味着这次 run 交付了一份**没有任何证据支持其正确性**的改动。

### 为什么清理命令必须排除

基线轨迹里 Agent 常在收尾时执行 `rm -f /workspace/tmp/check.py`、`git clean -f`、`git diff --stat`。如果把这些算作修改，验证证据会被平白抹掉。

本次分析的初版判定规则正是犯了这个错，导致「未验证」被统计成 74/78；修正口径后是 46/79。文档里的所有结论都基于修正后的数据。

## 数据：这个判定和得分的关系

WorkBuddy Code 80 题基线（`docs/bench/workbuddy-code-2026-08-18.md`）：

| | 题数 | 平均 Reward |
| --- | ---: | ---: |
| 最后一次修改后有成功验证 | 33 | 0.8226 |
| 无 | 46 | 0.7278 |

差值 0.095。但均值差本身不足以定因果——可能是「简单任务既容易做对，也容易被跳过验证」。因此在每个难度层内单独比较：

| 难度 | 有验证 | 无验证 | 差值 |
| --- | ---: | ---: | ---: |
| easy | 0.7500（n=4） | 0.4167（n=3） | +0.333 |
| medium | 0.8324（n=18） | 0.7094（n=12） | +0.123 |
| hard | 0.8329（n=11） | 0.7650（n=31） | +0.068 |

三层内效应方向一致，说明关联不是难度混淆的产物。样本量小（尤其 easy 层），效应量不可外推，但方向足以支撑动手。

两个佐证：

- **投入相同，结果不同。** 满分 34 题与低分 15 题的 turn 中位数（26 vs 27）、输出 token（14460 vs 13135）、耗时（340.5s vs 340.2s）、修改次数（4.5 vs 6.0）几乎一致。唯一系统性差异是验证率 50.0% vs 26.7%。**低分不是因为干得少，是干完不确认。**
- **easy 比 hard 分更低**（0.6071 vs 0.7828）。失败与难度负相关，排除了「能力上限」假说。

## 真正的问题：自我报告不可信

这是本文最值得留下的一条事实——它比「改完不验证」更根本。

| | 题数 | 平均 Reward | 其中实际 < 0.5 |
| --- | ---: | ---: | ---: |
| final response 声称测试通过 | 21 | **0.6869** | 6 |
| 未声称 | 59 | **0.7858** | 9 |

**声称通过的一组，平均得分反而更低。** 自我报告的完成度与真实完成度负相关。

典型案例 `api_contract-hard-markup_errors`，final response 写着：

```text
验证：`python -m unittest discover -s tests -v` 全部通过（12 个测试）
```

它跑的是自己新建的测试，隐藏 verifier 的 12 个断言**全灭**。这句话不假——它确实运行了，确实全绿——但它证明的是自己的假设，不是既有的公开契约。

另一个案例 `feature-medium-etag_header_for_static`：跑了 10 次成功验证、声称通过，实际 0.273。

结论：**「Agent 说它验证过了」不能作为完成信号**。判定必须由外部状态给出。15 个低分 run 中只有 4 个提到任何困难，其余以正常交付语气结束。

## 为什么不能只靠 system prompt

`packages/coding-agent/src/runtime/default-instructions.ts` 全文只有 4 段：通用角色、减少工具调用叙述、browser 任务使用 `agent-browser`、UpdateTodos 使用规则。

其中两处相关表述作用域都受限：

- 「report the capability blocker rather than claiming...」只针对 browser 场景；
- 「Mark an item completed only after its required verification succeeds... keep it in_progress or mark it cancelled instead of claiming completion」只约束 Todo 条目状态，不约束 final response，且仅在 Agent 用了 UpdateTodos 时才有意义。

这解释了数据表现：**Agent 在 Todo 语境下遵守验证纪律，在交付 final response 时不遵守。**

提示词只能表达期望，无法知道这一轮实际发生了什么——「改了没测」是关于执行历史的事实，只有观察执行流的组件能回答。

**但「需要观察执行流」不等于「该由 runtime 内置」。** 正确的分工是：runtime 提供观察能力与扩展点，策略由用户在扩展点上自己写。我当时从前半句直接跳到了实现，跳过了这一步。

## 曾经的实现（已移除）

`packages/coding-agent/src/runtime/verification-tracker.ts`，一个三状态机：

```text
mutation 成功            -> dirty = true
成功的 test/build 命令   -> dirty = false
下一次 model call && dirty && !reminded
                         -> 在请求里追加一条提醒，reminded = true
```

接在两个被 loop 同步 await 的 seam 上：`aroundToolCall` 观察工具结果推进状态，`beforeModelCall` 把提醒追加进本次请求。集成测试验证过它确实生效：改完不验证 → 下一次请求带上提醒；验证过 → 不打扰。

实现过程中有两条值得记住的技术约束，与本方案是否正确无关：

- **`beforeModelCall` 必须是纯函数。** 它在压缩与 overflow retry 时会对同一次请求重复执行（`harness/hooks.ts:26` 明确要求）。所以查询与状态推进必须拆开。
- **`onEvent` 不能用于结束前拦截。** `core/agent.ts:226` 用 `for await` 异步消费事件，而 loop 内部同步推进到 `getFollowUpMessages`——观察者永远慢一拍。这个结论在下文「附」里有完整排查记录。

## 为什么移除

**层次错了：这是策略，不该在 runtime 里。**

对比上游（详见下文调研）：

| 产品 | 提供什么 | 谁定策略 |
| --- | --- | --- |
| Claude Code | `Stop` hook 这个**机制**（可阻断 + `reason` + 防循环上限） | 用户写 hook，或用 `/goal` |
| OpenCode | 只有观察型事件 | 用户在 idle handler 里自己发起新 prompt |
| pi-agent | 只有观察型事件 + `pi.sendMessage()` 排队 | 用户 |

**没有一家把「你没验证就提醒你」这条具体规则烤进 runtime。** 框架提供观察点和干预能力，具体判断留给用户——因为「改完要不要跑测试」「跑哪些测试」「什么算验证充分」全都依赖项目本身：有的仓库没有测试，有的测试要跑二十分钟，有的项目 lint 就够了。

WorkBuddy 的数据说明「验证过的题得分更高」，这在 WorkBuddy 上成立，不代表对所有用户的所有仓库成立。我把一个 benchmark 上观察到的相关性，变成了所有人都绕不开的内置行为。

弱项切片的实测也不支持它：收到提醒组与未提醒组的最终未验证率相同（10/24 vs 6/25），**提醒注入了但没有改变模型行为**。即便退一步只看效果，它也没有兑现。

## 若要重做，该往哪走

按「机制 / 策略」分开：

1. **诊断（机制）——已保留。** `stop_reason`、`tool_calls`、`tool_errors` 已投影进 CLI run result，调用方能读到客观事实，不必扫描自然语言。这部分不含任何策略判断，是纯粹的可观测性。
2. **策略——交给 instructions 或用户 hook。** 若要表达「改完该验证」，写进 `default-instructions.ts` 是合理的（它是可被用户 instructions 覆盖的默认建议，不是强制状态机）；若要强制，则需要先设计一个通用的扩展点，让用户自己决定要不要用。
3. **扩展点（机制）——尚不存在，且不该为单个需求新增。** 见下文对 `agent_end` 时机的分析：这个点位本身语义就不清晰，要做需要独立设计。

## 附：为什么不接在结束点

初版把模块接在 `onEvent` 上，想在 Agent 收尾时注入 follow-up。集成测试显示 tracker 状态正确（`unverified=true`），但下一轮 provider 调用没有发生。

打点定位到根因：

```text
LOOP_PULL followUp n=0          <- loop 先拉取队列
HOOK_SAW message_end assistant:stop dirty=true   <- 观察者后收到事件
```

`core/agent.ts:226` 用 `for await (const event of stream)` **异步消费**事件，而 `agentLoop` 内部同步推进到 `getFollowUpMessages`。**观察者永远慢一拍**。

这意味着 `onEvent` 结构上无法用于结束前拦截——它是纯观察者，返回值被丢弃。`AgentHookMap` 的 6 类 hook 中也没有可否决结束的钩子。

`getFollowUpMessages` 的语义（「agent 本该停下时调用，有消息则继续新一轮」）恰好正确，但它被 `CoreAgentOptions` 的 `Omit` 刻意封装掉了——队列归 `CoreAgent` 管，外部只能通过 `followUp()` 入队，而那个入口赶不上时序。

## 「agent 结束前」是一个可疑的时机

初稿在这里提出新增 `beforeAgentEnd` hook。调研上游产品后判断该提案不成立，理由如下。

### 我们自己的 `agent_end` 就是多义的

`agent-loop.ts` 里 `agent_end` 有 5 个 emit 点：

| 行 | 情况 |
| ---: | --- |
| 94 | 未捕获异常（loop 外层 catch） |
| 123 | turn 上限终止 |
| 136 | 工具执行抛异常 |
| 143 | `turn.stopped` 或 signal 中止 |
| 162 | 正常结束 |

把钩子绑在 `agent_end` 上，等于同时绑住了崩溃、被截断、被用户中止。让 Agent「继续补验证」在后三种情况下没有意义。

此外 `agent-loop.ts:115` 的注释写明「一个 task：连续的 turn，直到模型不再调用工具且没有 steering 消息」，因此「结束」至少有 turn / task / run 三个层级，`beforeAgentEnd` 这个名字并未指明是哪一个。

### 上游三家：定义明确，但结论不一致

| 产品 | 时机 | 可否阻断 | 防循环 |
| --- | --- | --- | --- |
| Claude Code | `Stop` / `SubagentStop` | 可以：`decision: "block"` + 必填 `reason` | `stop_hook_active` **加连续 8 次硬上限** |
| OpenCode | `session.status(idle)`（`session.idle` 已废弃） | 不可以 | 无（社区自行加标志） |
| pi-agent | `agent_end` / `agent_settled` | 不可以 | 不适用 |

三家共同承认的难点是同一个：**「结束」不是一个点，而是一个可能被撤销的状态。** 三家的消歧方式各不相同：

- **pi 在事件层切分**：`agent_end` 表示一次 low-level run 结束，但 pi 仍可能自动重试、自动压缩后重试或继续处理排队的 follow-up；`agent_settled` 才表示确实不会再自动继续。一次用户 prompt 可能触发多次 `agent_end`，只触发一次 `agent_settled`。
- **Claude Code 在载荷层消歧**：保持单个 `Stop`，但在载荷里加 `background_tasks` 与 `session_crons`，让 hook 自行判断是「真的做完」还是「在等后台任务唤醒」。同时明确规定用户中断**不触发** `Stop`，API 错误走单独的 `StopFailure`。
- **OpenCode 在状态层收敛**：把布尔的 idle 事件换成三态 `session.status`（`idle` / `busy` / `retry`），让 `retry` 独立于 `idle`。

我们的 `agent_end` 正相当于 pi 的 `agent_end`——一个可能被撤销的状态，而非终点。

### 只有一家做了可阻断的结束门

OpenCode 的 `event` 钩子签名是 `(input: { event: Event }) => Promise<void>`，没有输出对象；其源码中该钩子以 `void hook["event"]?.({...})` 调用，显式不 await，因此插件无法延迟状态转换。它把强制拒绝集中在 `permission.ask`，即**动作发生之前**。

pi 同样没有否决结束的返回值，阻断能力放在 `tool_call` 的 `{ block: true }`，延长运行则靠 `pi.sendMessage()` 排队。

只有 Claude Code 提供了真正的结束前质量门，并为此配了两层防护。硬上限的存在说明：**仅靠一个「已提醒过」的标志位不够**——而这正是本模块 `reminded` 字段的强度。

### 本项目已排除过这条路

`docs/build-coding-agent/12-agent-plugin-hooks-v1.md:194` 将 `SessionEnd` 定义为「仅观察」，第 205 行明确把「停止 agent」列入不在 v1 的能力，并要求「将来只有 host 新增了稳定 seam 且有具体产品需求时，才可以定义新的 plugin event 版本；不得先接受配置、再把它悄悄降级为 observer 或 no-op」。

## 当初的三条路，与最终选择

| 方案 | 改动面 | 当时评价 | 最终 |
| --- | --- | --- | --- |
| A. 只保留诊断 | 零改动 | 无主动干预能力 | **实际采用** |
| B. `beforeModelCall` 注入 | 只动 coding-agent | 时点单一无歧义 | 实现后移除 |
| C. 照 Claude Code 做可阻断的 `Stop` | 四层改动 | 改公开契约 | 未做 |

我当时选了 B，理由是「时点单一、不碰结束语义、有 Todo 注入的先例」。这些技术判断都成立——**错在没问「这件事该不该由框架决定」**。A 才是正确答案：框架给事实，不替用户做判断。

C 如果将来要做，它提供的应该是**机制**（一个语义清晰的扩展点 + 防循环上限），而不是内置「验证」这条具体策略。

## 边界

- 「修改」与「验证」由工具名和命令模式识别，不是 runtime 原生字段。规则已排除临时文件写入与清理命令，但仍可能有边界误判。
- 该模块只回答「改了没测」，不回答「测得对不对」。verifier 断言全灭而自建测试全绿的情况，它只能通过文案引导，无法强制。
- 弱项切片实测（2026-08-19，49 trial）：收到提醒组最终未验证 10/24，未提醒组 6/25——**提醒被正确注入，但没有改变模型行为**。同一批数据里「验证过」与 Reward 的正相关依然成立（0.4917 vs 0.3802），即验证有价值，但这条提醒推不动模型。
- 分层样本很小（easy 层 7 题，弱项三类各 3–4 题），效应方向可信，效应量不可外推。
- 弱项三类的未验证率（33%–75%）并不高于其余类别（61%），但平均 Reward 低 0.25。**完成前验证不能解释弱项低分**——那是契约恢复的问题，两者独立。
- 上游行为取自各产品当前公开文档与源码（2026-08-18）。三家的钩子语义都在演进中——`session.idle` 已被 `session.status` 取代，Claude Code 的 `Stop` 载荷在 v2.1.145+ 才加入 `background_tasks`——因此该对比会过时，重新评估方案 C 时应重新核对。
