# Agent Runtime 该怎么搭:一个会话一个管家

日期：2026-08-23

## 一句话结论

> **一个会话只能有一个管事的;它记的账要牢到断电重启还能接着干;模型、工具、界面都是可换的零件,但只能从固定插口接进来,不能自己伸手改账本。**

这条结论要否掉两种常见做法:

- **"什么都做成插件"**:听着灵活,但"谁先谁后、谁有权改"没人统一管,复杂度只是从一坨大泥球变成一堆互相回调,更难查。
- **"一上来就拆进程"**:早期没有多端接入需求时,拆进程只是增加运维成本。

Pi 的 `dev` 分支强调断电可恢复、一个会话一个 worker、多个界面能连同一个会话;DeepSeek Harness 强调零件可换、生命周期可回收。两边都不该照搬,但指向的是同一件事。

## 真正的问题不是"状态放哪",而是"谁有权改"

把状态撒到插件、界面、微服务里并不是目标。目标是能清楚回答:**这件事谁说了算?**

```text
桌面端 / CLI / Web / 自动化脚本
            │ 递条子:命令、审批、输入
            ▼
┌──────────────────────────────────────────────────────┐
│ 会话管家(Session Runtime)                             │
│ - 所有输入排一个队,决定谁能跑                          │
│ - 存两种账:发生过什么 + 干到哪一步了                     │
│ - 管权限、审批、取消                                     │
│ - 保证顺序、不变量、崩溃后恢复                            │
└──────────────────────────────────────────────────────┘
            │                         │
            │ 接入可换零件             │ 发出快照 + 带序号的增量
            ▼                         ▼
   模型 / 工具 / MCP / 沙箱      界面:只负责显示和发命令
   / Skill
```

"一个会话一个管家"是**逻辑约束**,不是"必须一个会话一个进程"。早期在同一个进程里实现完全可以;等到需要多个界面同时连、需要故障隔离、需要跑在远端时,再把管家搬进独立 worker。**跑在哪可以改,但"谁有权改账本"这个接口不能改**——否则搬家时要重写所有调用方。

## 四种状态必须分开存

| 存什么 | 具体是什么 | 谁能写 | 要不要喂给模型 |
| --- | --- | --- | --- |
| 发生过什么 | 用户消息、工具结果、审批决定、产出文件 | 只有管家 | 挑着给 |
| 干到哪一步了 | 这次任务被接了没、模型/工具跑到哪个阶段、重试次数、有没有被取消、副作用发出去没 | 只有管家 | 不给 |
| 界面要显示的 | 聊天记录视图、Todo、状态栏、搜索索引、前端缓存 | 由前两种算出来 | 不给 |
| 这次真正喂给模型的 | 挑过的摘要、事实、工具结果 | 组装 context 的那段代码 | 给 |

分开存能澄清两个常见误解:

1. **系统能感知运行过程 ≠ 要把运行日志倒给模型。** 管控信息默认一个 token 都不占。
2. **存了聊天记录 ≠ 能恢复执行。** 聊天记录只说明"发生过什么";崩溃重启后你还得知道"那条部署命令到底发出去没有、能不能安全接着跑",这是另一份账。

## 插件放在哪

> **插件是"提供零件"和"提供显示",不是"持有真相"。**

插件可以提供:模型适配器、工具、MCP、Skill、沙箱后端、prompt 片段、领域能力、界面面板、消息渲染器、输入框动作。

插件不能:

- 直接改"干到哪一步了"这份账,或者绕过管家;
- 自己另起一个 Agent 循环偷偷跑;
- 绕过权限、审批和排队;
- 直接往会话主存储里写;
- 把 `globalThis`、界面局部 state 或者随手一个 JSON 变成业务真相。

用户装的扩展应该按权限分级,不是一律给同一套进程内权限:

| 级别 | 能干什么 | 限制 |
| --- | --- | --- |
| 随便装 | Skills、MCP、声明工具和渲染器 | 怎么解析、给什么权限、要不要沙箱,由管家决定 |
| 能存数据 | 插件自己命名空间下的持久数据 | schema、版本、访问方式由管家管 |
| 受信任的代码 | 模型/工具适配器、受控 hook、后台能力 | 要声明用到哪些能力、有生命周期、故障被隔离 |
| 核心不开放 | 排队、权限、任务状态、worker 独占、连接协议 | 第三方插件碰不到 |

界面插件同理:它读数据、发命令、在自己的错误边界里渲染。一个面板崩了可以禁用掉慢慢查,但不能把 Agent worker 或者会话状态搞坏。

## 六条不能破的规矩

1. **只能有一个人写。** 多个界面连上来,不等于多个进程可以同时读写同一份会话存储。
2. **所有输入走同一个门。** 界面、CLI、自动化、插件触发的后续任务,都排同一个队,每次都带一个稳定的任务 ID,这样重试才不会重复执行。
3. **副作用要先写"打算做",再写"结果是"。** 崩溃后如果结果未知,必须把这个不确定摆出来,不能假装没事再跑一遍。
4. **别指望"恰好执行一次"。** 部署、发消息、付款这类对外动作,靠的是幂等 key、对方系统去重、人工审批,以及一个明确的"不确定"状态——而不是承诺一个根本不存在的保证。
5. **显示层不能反过来变成真相。** 界面快照、事件流、监控、缓存、喂给模型的 context,全都是能重算的,不能拿来当唯一账本。
6. **一个零件坏了不能连坐。** 插件监听器抛异常、界面渲染器抛异常、模型请求失败、工具报错,各走各的诊断或错误返回路径;核心会话不因为一个订阅者崩掉就废了。

## 多个界面连同一个会话,正确的流程

```text
连上来
  → 先要一份完整快照
  → 再接带序号的增量事件
  → 发命令(带任务 ID)
  → 断开 / 重连时重新走一遍上面的流程
```

连接是**临时的显示通道**,不是业务数据。断线重连时重新要一份快照,而不是拿手里的旧事件猜现在什么状态。审批也一样:它必须是管家能路由的一次交互,不能永久绑在某个桌面端进程的内存里——那个进程一关,审批就丢了。

## 对"什么都做成插件"的修正

DeepSeek Harness 的 Cordis 模型很有价值:模型适配器、工具注册、会话存储、Agent 循环、Web 应用都能以可组合方式装进来;它也要求插件卸载时把注册和副作用回收干净,并且把"持久事件"和"实时事件"分开。[1][2][3]

但"没有特权核心"不等于"没有特权规矩"。不管实现上是不是也用插件方式装配,下面这些语义必须始终由**一个地方**统一收口:会话的唯一执行权、输入排队、状态迁移、权限、写入顺序、取消、恢复、连接协议。否则就是把复杂度从大泥球换成一张难以追踪的回调图。

所以要追求的不是**插件优先**,而是**协议优先**:

```text
插件 → 声明/提供一个零件
管家 → 校验 / 组装 / 授权 / 持久化 / 恢复
界面 → 显示 + 发命令
```

## 怎么一步步走到这

按接口切,不搞大迁移:

1. 先定一个很小的 `SessionRuntime` 接口:连接、拿快照、订阅事件、提交输入、干预、中止、审批、关闭。
2. 让现在进程内的实现先满足这个接口;调用方不再直接抓 Agent 内部对象。
3. 等真的需要第二个界面时,把同一份实现搬到独占 worker 里,再用同一个接口的 client 版本接上去。
4. 先做快照 / 事件 / 输入去重;只有在长任务、接管、副作用恢复有真实需求时,才去做"干到哪一步了"的持久化。
5. 跨进程插件、热重载、通用服务图放在最后——它们不是多端接入的前提。
