## 结论一：机制修复全部生效

| 指标 | 基线（同批题） | 本次 | 变化 |
| --- | ---: | ---: | --- |
| permission error | 63 | **0** | 消除 |
| turn > 40 | 8（最高 93） | **0**（最高 40） | 消除 |
| turn 均值 | 39.2 | 29.5 | −25% |
| 工具错误率 | 13.8% | **7.1%** | 接近腰斩 |
| 基础设施错误 | 21（首轮） | 0 | — |

工具错误率下降印证了基线的判断：permission error 占全部工具错误的 65.2%，消除它即消除大部分噪声。

`iteration_limit` 占 35%（17/49）。这不是新缺陷，而是原先失效的预算首次真正生效。

## 结论二：Reward 无显著变化，且现有方法测不出

| 指标 | 基线 | 本次 |
| --- | ---: | ---: |
| 平均 Reward | 0.4927 | 0.4563 |
| 测试通过率 | 51.6% | 47.7% |
| 改善 / 退化 / 持平 | — | 7 / 5 / 6 |

差值 −0.036，**但这个数字读不出信号**。原因是单题方差远大于它：

| task | 多次结果 | 极差 |
| --- | --- | ---: |
| `bug_fix-easy-a_crash_in_local` | 1.00, 0.00, 0.33 | **1.00** |
| `bug_fix-medium-incorrect_linenos_on_fstring` | 1.00, 0.17, 0.17 | **0.83** |
| `bug_fix-medium-matching_absolute_paths` | 1.00, 1.00, 0.25 | **0.75** |
| `api_contract-hard-openapi_params` | 1.00, 0.42, 0.33 | **0.67** |

**同一份代码、同一个模型，单题跑分极差可达 1.00；而总体差异只有 0.036，小了一个量级。**

按稳定性拆分后更清楚：

| 分组 | 题数 | delta 均值 |
| --- | ---: | ---: |
| 极差 = 0（完全稳定） | 7 | **+0.012** |
| 极差 < 0.4 | 4 | −0.025 |
| 极差 ≥ 0.4（剧烈波动） | 7 | −0.091 |

稳定题基本持平；负值全部来自高方差题。而基线是**每题 1 attempt**，那些 1.000 很可能是各自波动区间的高点——`openapi_params` 三次为 1.00 / 0.42 / 0.33，基线单次 0.67 恰在中间：基线若抽到 1.00，delta 显示 −0.42；抽到 0.33，则显示 +0.25。**同一事实，符号取决于基线抽中哪一次。**

因此正确结论是：**四项修复未带来可测量的 Reward 变化，且当前 attempt 数不足以测出 ±0.05 量级的效应。**

## 结论三：验证提醒未达预期，已移除

| 分组 | 题数 | Reward | 最终仍未验证 |
| --- | ---: | ---: | ---: |
| 收到提醒 | 24 | **0.3968** | 10/24 |
| 未收到提醒 | 25 | **0.5114** | 6/25 |

收到提醒的一组 Reward 更低、未验证比例更高。

这**不能**读作「提醒有害」——因果方向更可能相反：提醒只在模型改完没验证时触发，因此它本身就是「这次做得不扎实」的标记，而非原因。真正的问题是**提醒没有改变行为**：收到提醒后仍有 10/24 最终未验证。

同时，「验证过」与 Reward 的正相关依然成立，与基线一致：

| | 题数 | Reward |
| --- | ---: | ---: |
| `unverified_changes = false` | 33 | **0.4917** |
| `unverified_changes = true` | 16 | **0.3802** |

即：**验证有价值，但当前这条提醒推不动模型去验证。**

**该模块已于 2026-08-19 移除**，原因不止于效果不佳：它把一条具体策略硬编码进了 runtime。上游三家（Claude Code / OpenCode / pi-agent）都只提供机制，把「什么算验证充分」留给用户——因为它依赖具体项目。详见 `docs/point/3.md`。诊断字段中的 `unverified_changes` 随之移除，`stop_reason` / `tool_calls` / `tool_errors` 保留。

## 结论四：turn 截断不影响得分

| | 题数 | 本次 | 对应基线 | delta |
| --- | ---: | ---: | ---: | ---: |
| 被 `iteration_limit` 截断 | 17 | 0.3726 | 0.3529 | **+0.020** |
| 正常结束 | 32 | 0.4993 | 0.5658 | −0.067 |

被截断的题反而略有上升。`JAI_MAX_TURNS: 40` 够用，无需上调。

## 下一步

1. **不要用 Reward 判断 runtime 修复的收益。** 机制指标（permission error、turn 溢出、工具错误率、`stop_reason` 分布）方差小、可归因，是合适的验收口径；Reward 需要远多于 3 次的 attempt 才能测出 ±0.05 的效应。
2. **验证提醒已移除，不再迭代当前形式。** 若要重新解决「改完不验证」，应走 instructions（可被用户覆盖的默认建议）或通用扩展点，而非 runtime 内置状态机。
3. **补齐方差基线。** 若要继续用 Reward 做对比，应先测定各题的固有方差（同配置重复 5 次以上），据此确定可检测的最小效应量。
4. 全量 80 题回归的价值在于换模型对照（如 pro vs flash），而非验证这三项修复——它们对 Reward 无可测量影响。
