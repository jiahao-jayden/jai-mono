## 结论

1. Synara 有两套 UI 呈现同一份 reasoning/effort 状态：默认菜单模式把 Effort 作为 footer 子菜单行；开启 `composerEffortSlider` 后，模型菜单 footer 改为 stepped slider card，并把 Speed 合并进同一张卡。两套表面都通过同一个 `getComposerTraitSelection` 和 `planComposerEffortChange` 解析、提交，因此不会出现菜单与滑块各自维护一套映射。[`ComposerModelPickerTraitRows.tsx#L101-L105`](file:///Users/jayden/code/github_project/synara/apps/web/src/components/chat/ComposerModelPickerTraitRows.tsx#L101-L105) [`composerTraits.ts#L262-L294`](file:///Users/jayden/code/github_project/synara/apps/web/src/components/chat/composerTraits.ts#L262-L294)
2. 档位不是由 UI 写死为单一全局 ladder：冷启动由 `packages/contracts/src/model.ts` 的 provider/model capability 表提供；若选中模型有 runtime discovery descriptor，则 `runtimeModelCapabilities.ts` 用 `supportedReasoningEfforts` 覆盖静态 ladder，并以 runtime default 或仍然存在的静态 default 标记默认值。没有 runtime ladder 时才保留静态能力。[`runtimeModelCapabilities.ts#L88-L125`](file:///Users/jayden/code/github_project/synara/apps/web/src/components/chat/runtimeModelCapabilities.ts#L88-L125) [`runtimeModelCapabilities.ts#L135-L169`](file:///Users/jayden/code/github_project/synara/apps/web/src/components/chat/runtimeModelCapabilities.ts#L135-L169)
3. UI 的模型能力映射通过“模型选择 -> runtime descriptor -> capabilities -> provider option descriptor -> composer selection”完成：模型目录按 provider 汇总 runtime models，按 provider/model 规范化匹配当前 descriptor；随后 `getComposerTraitSelection` 选择 primary select descriptor，读取 options/current value/default，并区分普通 effort、prompt-injected effort、thinking toggle、fast mode 与 context window。[`useProviderModelCatalog.ts#L465-L501`](file:///Users/jayden/code/github_project/synara/apps/web/src/hooks/useProviderModelCatalog.ts#L465-L501) [`composerTraits.ts#L100-L182`](file:///Users/jayden/code/github_project/synara/apps/web/src/components/chat/composerTraits.ts#L100-L182)
4. 交互是即时提交、按 provider 语义落盘：菜单 radio 选择后关闭菜单；滑块每个 step 立即提交 option patch 并保持菜单打开；切换到带 ladder 的新模型时 slider 模式也保持打开，当前模型再次点击才关闭。Claude 的 Ultrathink 是例外：它由 prompt 控制，选择会改写 prompt，已被 prompt 锁定时 effort 控件禁用，并显示移除提示。[`TraitsPicker.tsx#L347-L372`](file:///Users/jayden/code/github_project/synara/apps/web/src/components/chat/TraitsPicker.tsx#L347-L372) [`ComposerEffortSliderCard.tsx#L64-L75`](file:///Users/jayden/code/github_project/synara/apps/web/src/components/chat/ComposerEffortSliderCard.tsx#L64-L75) [`ComposerModelPicker.tsx#L318-L331`](file:///Users/jayden/code/github_project/synara/apps/web/src/components/chat/ComposerModelPicker.tsx#L318-L331)

## 对本项目的影响

- 若在本项目复刻该 UI，优先复刻“统一 capability/descriptor -> 单一 selection -> 单一 change plan”的数据流，而不是分别为菜单与 slider 写 provider 分支；它是 Synara 避免 UI surface 漂移的关键边界。
- capability 数据模型至少需要表达：有序 effort options、展示 label/description、默认档位、provider-specific persisted option id，以及 prompt-injected 控制；单纯 `string[]` 只能覆盖最窄场景。
- runtime discovery 应被视为当前模型能力的权威来源，静态表只作为冷启动/无 discovery fallback；runtime ladder 为空时保留静态能力，避免 UI 突然消失。
- 交互上需要明确“选择后关闭”与“连续微调保持打开”的两种生命周期，并为 prompt-controlled effort（如 Ultrathink）提供锁定、提示和 prompt rewrite，而不是把它误当普通 option patch。
- 本调研没有验证 provider adapter 如何生成 `ProviderModelDescriptor`、设置值如何跨进程持久化，也没有查权限模式；这些属于本次边界之外，不能从本笔记推断。
