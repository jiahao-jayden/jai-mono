## WorkBuddy Benchmark

WorkBuddy harness 只启动固定版本的普通 `jai` CLI。Code、Web、Office、Security 测试集共享同一入口；任务镜像提供的 workspace、服务和环境决定能力差异。

Harness 应使用预构建的 `@jayden/jai-cli` npm tarball 或等价 split-mount，安装后只从 PATH 调用 `jai`；trial 不依赖 Jai monorepo 源码路径或运行时下载。

```bash
cat "$TASK_INSTRUCTION_FILE" |
  jai -p \
    --output-format stream-json \
    --permission-mode bypassPermissions \
    --no-session-persistence \
  --max-turns "$MAX_TURNS"
```

## 构建 WorkBuddy harness mount

先在 Jai 仓库打出固定 tarball，再在 WorkBuddy checkout 中将它构建成只读 mount。trial 中只会把 launcher 链接到 `PATH`，不会安装 CLI 或联网下载依赖。

```bash
# jai-mono
bun run cli:pack

# workbuddy-bench
scripts/harness/stage-jai-cli-tarball.sh \
  --tarball /absolute/path/to/jayden-jai-cli-0.0.0.tgz
scripts/harness/build-harness-mounts.sh --harness jai/0.0.0
```

Job 只需选择 `harness: jai/0.0.0`；Code、Web、Office、Security 的差异仍来自各自 task image 和 verifier，而不是 Jai CLI 参数或第二条 Agent 路径。

## 接入原则

1. 使用标准 CLI 参数，不新增 `--workbuddy-*` 特例。
2. 每个任务使用 ephemeral Session，避免测试之间共享 transcript 或 app state。
3. harness 负责镜像、workspace、环境变量、stdout/stderr、exit code 与清理；Agent 仍由 SDK 组装。
4. 先运行最小 smoke，再依次扩展 Code、Web、Office、Security。

Web 任务不需要专属 CLI mode：task image 提供 `agent-browser` 时，Agent 通过普通 Bash capability 发现并使用它；未提供时应返回能力阻断，而不是伪造浏览器验证结果。

## 验收

每次运行应记录 CLI exit code、`stream-json` 事件与最终 `result`（包括 `usage` 和 `total_cost_usd`）。测试失败时优先检查 workspace authority、模型配置、权限模式和任务环境，而不是为 benchmark 添加第二套 Agent 路径。
