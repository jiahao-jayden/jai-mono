在自主编程（Coding Agent）场景下，会话往往伴随着海量的代码阅读与持续的工具交互。单次任务的上下文动辄达到数十万 Token。如果不做针对性优化，每一轮交互都需要全量重新计算全部上下文，导致首字延迟（TTFT）恶化到数十秒，同时产生昂贵的 Token 账单。

在 jai-mono 中，**Prompt Cache 命中是一等公民约束**。

---

## 核心设计：前缀稳定性（Prefix Stability）

主流模型供应商（如 Anthropic Prompt Caching、OpenAI Prompt Caching、DeepSeek Context Caching）普遍依赖于**确定的最长公共前缀**来进行服务端 KV 缓存复用。

只要发给模型的请求前缀有一字节变动，该字节之后的所有缓存将全量失效。因此，SDK 的上下文序列化器严格遵循**只追加（Append-Only）与确定性前缀编排**：

```text
┌────────────────────────────────────────────────────────┐
│ 1. 静态系统指令（System Prompt）                        │  ◄── 绝对稳定，永远置顶
├────────────────────────────────────────────────────────┤
│ 2. 工具定义集（Tool Definitions & Schemas）            │  ◄── 静态锁定，顺序确定
├────────────────────────────────────────────────────────┤
│ 3. 历史对话流水（Historical Messages & Tool Results）    │  ◄── 单向只追加，禁止就地改写
├────────────────────────────────────────────────────────┤
│ 4. 本轮动态指令与瞬态状态（Current Ephemeral Input）     │  ◄── 易变内容严格后置
└────────────────────────────────────────────────────────┘
```

### 严禁在前缀中注入易变数据
- **无序集合遍历**：工具列表、扩展 Schema 必须拥有确定性排序，禁止依赖随机的字典迭代顺序。
- **动态时间戳与随机 ID**：绝不能在 System Prompt 或静态工具描述中注入诸如 `Current Time: 17:50:23` 或 `TraceID: a1b2c3`。这类瞬态信息只能通过独立的用户消息或尾部块表达。

## Anthropic 三级缓存断点实现

以 Anthropic Messages API 为例，SDK 会在上下文的关键分界线上精确设置三级 `cache_control: { type: "ephemeral" }` 断点：

```text
[System Prompt] ──────────────────────────► 【断点 1：锁定全局系统指令】
[Tool Definitions (1..N)] ────────────────► 【断点 2：在最后一个工具 Schema 上打点】
[Turn 1] (User + Assistant + ToolResult)
[Turn 2] (User + Assistant + ToolResult)
...
[Turn K-1]
[Turn K] (最新一条 User 或 ToolResult 尾部) ──► 【断点 3：锁定截止到上轮的历史流水】
```

1. **断点 1（System Prompt）**：在系统提示词末尾打点。只要系统提示词不变，跨会话均可命中缓存。
2. **断点 2（Tool Definitions）**：在最后一个工具定义上打点。确保所有工具的 Schema 被一次性锁定入缓存。
3. **断点 3（Dynamic Turns Tail）**：从后往前扫描，在倒数第一个已经落地的 `user` 或 `toolResult` 消息末尾打点。该断点锁定了从第 1 轮到当前轮之前的所有历史交互。

通过这三级断点，后续每一轮交互中，**前 95% 以上的历史对话与工具 Schema 均能直接命中服务端的 KV Cache**。

## 缓存与上下文压缩（Compaction）的关系

当长会话必然要触发上下文压缩时，旧消息被摘要替换，前缀必然发生改变，会导致本会话的 KV 缓存暂时失效。

SDK 将此视为显式的性能边界：
- 压缩切点（Compaction Cut）基于 Token 预算从后往前保留最新的轮次，保证截断次数尽量少。
- 引入**投机性后台压缩（Speculative Compaction）**：在会话逼近阈值时，在独立分支异步生成摘要，主会话继续使用原有前缀推进，直至最后一刻原子切换，最小化对交互延迟的影响。
