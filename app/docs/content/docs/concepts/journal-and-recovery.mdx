---

在生产环境中，Agent 在本地修改代码或执行 Shell 脚本具有不可逆的外部副作用（Side Effects）。如果在工具刚刚执行完毕、尚未将状态持久化时系统掉电或进程崩溃，传统的基于内存快照的框架往往会发生**状态撕裂**或**盲目重放非幂等操作**。

SDK 基于坚固的 **Append-Only 树形 Journal** 与 **两阶段效果边界** 解决这一难题。

---

## 树形 Journal（Append-Only Tree）

会话的唯一物理真相是一条追加写入的不可变条目流（Journal）。会话中的任何行为都被固化为以下四种原子 Entry：

- **`MessageEntry`**：用户输入、模型推理响应与工具执行结果消息。
- **`AppStateEntry`**：扩展状态、任务清单或应用状态的变更记录。
- **`CompactionEntry`**：上下文压缩摘要以及被折叠的历史消息区间。
- **`BranchEntry`**：会话分支点记录（支持无损的分支探索与版本回退）。

```text
(Root)
  └── Entry 1 [User: "分析项目"]
        └── Entry 2 [Assistant: "调用 Read"]
              └── Entry 3 [ToolResult: "文件内容..."]
                    ├── Entry 4 [分支 A: "方案 1 修改"]
                    └── Entry 5 [分支 B: "方案 2 修改"] (Active Leaf)
```

### 纯函数单向分支派生（`branchOf`）
每个 Entry 均持有 `parentId`。当用户在 UI 中回退历史或切换分支时，SDK **从不修改既有的历史记录**，而是将活跃游标（Active Leaf）切换到目标 Entry，通过纯函数 `branchOf(entries, leafId)` 沿指针回溯构建当前活跃分支视图。

这杜绝了在关系型数据库中直接修改某一行状态引发的“废弃分支幽灵复活”现象。

## 两阶段效果边界（T1 / T2 效应）

当 Agent 准备调用带有外部副作用的工具（如在磁盘上新建文件、运行数据库迁移）时，SDK 严格划分两个阶段：

```text
大模型发出 ToolCall
        │
        ▼
[ T1 阶段：意图落盘 ] ──► 在执行真实动作前，先将工具调用意图（参数哈希、调用 ID）写入 Journal
        │
        ▼
[ 外部实际调用 ] ───────► 调用操作系统底层 API 执行写入或执行 Shell
        │
        ▼
[ T2 阶段：结果结算 ] ──► 将实际返回内容与执行状态作为事实追加入 Journal
```

### 崩溃恢复裁决（Recovery Verdict）

如果进程在 **外部实际调用** 与 **T2 阶段** 之间发生致命崩溃或断电，当应用重启并重新恢复会话时：

1. **识别悬空意图**：SDK 回放 Journal 时会发现只有 T1（意图已宣告），但缺少对应的 T2（未拿到结算记录）。
2. **幂等性判定**：
   - 如果该工具属于**只读操作**（`sideEffect: "read"`，如文件检索），SDK 会安全重放该调用；
   - 如果该工具属于**破坏性或非幂等写操作**（如文件覆盖、Shell 部署脚本），SDK **绝不盲目重新调用**，而是将该工具标记为受控异常中断，向模型报告该工具在执行中途遭遇宿主崩溃。
3. **模型感知并自愈**：大模型在下一轮感知到“上一步执行遭遇异常中断”，自主触发检查（如使用 `Read` 或 `git status` 查看变更现场），再决定是重试还是修补，从根源上杜绝重复写入或双重扣费。
